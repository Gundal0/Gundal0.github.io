# 크레이트 섬의 탐정들

### — 빌림 검사관과 사라진 메모리 사건 —

*러스트(Rust)로 배우는 장편 프로그래밍 추리 소설*

---

> "컴파일러는 너를 괴롭히려는 게 아니야.
> 네가 내일 새벽 세 시에 깨지 않도록 지켜 주는 거지."
>
> — 빌림 검사관 보로, 『수사 일지』 첫 장에서

## 이 책을 펼친 당신에게

이 책은 추리 소설입니다. 그리고 동시에 러스트 교과서입니다.

주인공 **윤하랑**은 열네 살 중학생입니다. 코딩이라고는 학교 방과후 수업에서 파이썬으로 거북이 그림을 그려 본 게 전부지요. 그런 하랑이 어느 날 수수께끼 같은 초대장 한 장을 받고, 지도에도 없는 섬 **크레이트 섬**으로 떠납니다. 그곳에서는 메모리가 도둑맞고, 데이터가 동시에 두 번 바뀌고, 이미 사라진 주소를 가리키는 '유령 포인터'가 밤마다 출몰합니다.

하랑은 섬에서 가장 깐깐한 탐정, **빌림 검사관 보로**의 견습생이 되어 사건을 하나씩 풀어 갑니다. 사건을 풀 때마다 러스트의 문법 하나가, 설계 원리 하나가 하랑의 손에 단서처럼 쥐어지지요.

이 책을 끝까지 따라오면 여러분은 다음을 할 수 있게 됩니다.

- 소유권·빌림·라이프타임을 **설명할 수 있는** 수준으로 이해합니다.
- 트레이트와 제네릭으로 **재사용 가능한 라이브러리 API**를 설계합니다.
- `Rc`, `RefCell`, `Arc`, `Mutex`를 **언제, 왜** 쓰는지 판단합니다.
- 스레드와 `async`로 **동시성 프로그램**을 데이터 경쟁 없이 작성합니다.
- 빌더·뉴타입·타입 상태(Typestate)·RAII 같은 **러스트다운 디자인 패턴**을 씁니다.
- 매크로로 **코드를 생성하는 코드**를 만들고, `unsafe`의 경계를 **안전하게 감쌉니다**.

## 등장인물

**윤하랑** — 열네 살. 호기심이 많고, 틀리면 끝까지 이유를 캐묻는 성격. 크레이트 섬의 견습 탐정.

**빌림 검사관 보로** — 크레이트 섬 탐정 사무소의 소장. 회색 코트에 은테 안경. 규칙을 단 하나도 어기지 않으며, 수상한 코드는 절대 통과시키지 않는다. 말투는 차갑지만 한 번도 틀린 적이 없다.

**페리** — 사무소의 조수인 주황색 꽃게. 말은 못 하지만 집게발로 칠판에 글씨를 쓴다. 의외로 성능 최적화의 달인.

**카고 할머니** — 섬의 항구와 창고를 관리하는 할머니. 모든 짐(크레이트)의 목록과 버전을 외우고 있다.

**클리피 경위** — 섬의 순찰 경찰. "그건 이렇게 쓰는 게 더 좋아요"가 입버릇인 잔소리꾼이지만 늘 옳다.

**댕글링** — 정체불명의 괴도. 이미 비워진 집의 주소를 훔쳐다 팔아넘긴다는 소문이 있다.

**레이스 쌍둥이** — 같은 금고를 동시에 여는 쌍둥이 도둑. 둘 중 누가 범인인지 아무도 증명하지 못했다.

**UB 백작** — 섬의 전설 속 존재. "정의되지 않은 행동(Undefined Behavior)"의 화신. 그가 지나간 자리에서는 무슨 일이든 일어날 수 있다고 한다.

# 프롤로그 — 지도에 없는 섬

초대장은 편지 봉투가 아니라, 하랑의 노트북 바탕화면에 놓인 파일 하나로 도착했다.

`invitation.rs`

열어 보니 단 세 줄이었다.

```rust
fn main() {
    println!("윤하랑, 크레이트 섬으로 오라. 배는 내일 새벽에 떠난다.");
}
```

"이게 뭐야, 장난인가?"

하랑은 파일 이름 끝의 `.rs`를 한참 바라보았다. 러스트. 이름만 들어 본 언어였다. 어렵기로 유명하고, 한번 익히면 다른 언어로 돌아가기 싫어진다는 그 언어.

호기심이 이겼다. 하랑은 인터넷에서 찾은 대로 터미널에 명령어를 입력했다.

```text
$ cargo new invitation
$ cd invitation
```

`cargo`가 폴더를 하나 만들어 주었다. 안에는 `Cargo.toml`이라는 파일과 `src/main.rs`라는 파일이 있었다. 하랑은 초대장의 세 줄을 `main.rs`에 붙여 넣고 실행했다.

```text
$ cargo run
   Compiling invitation v0.1.0
    Finished dev profile [unoptimized + debuginfo]
     Running `target/debug/invitation`
윤하랑, 크레이트 섬으로 오라. 배는 내일 새벽에 떠난다.
```

글자가 화면에 찍힌 바로 그 순간, 노트북 화면이 바다처럼 일렁였다. 짠 바람 냄새가 났다. 갈매기 소리가 들렸다.

그리고 하랑은, 나무 부두 위에 서 있었다.

---

"짐 목록."

부두 끝에서 허리가 굽은 할머니가 커다란 장부를 들고 하랑을 올려다보고 있었다.

"네? 짐이요? 저 아무것도 안 가져왔는데요."

"그럴 리가. 여기 오는 사람은 다 `Cargo.toml`을 들고 와." 할머니가 하랑의 손을 가리켰다. 정말로 하랑의 손에는 종이 한 장이 들려 있었다.

```toml
[package]
name = "invitation"
version = "0.1.0"
edition = "2024"

[dependencies]
```

"이름, 버전, 에디션. 의존하는 짐은 없음. 깔끔하구먼." 할머니는 장부에 무언가를 적었다. "난 카고. 이 섬의 항구랑 창고를 맡고 있지. 앞으로 다른 섬에서 짐(크레이트)을 받아 와야 하면 `[dependencies]` 아래에 적어 두기만 해. 그럼 내가 `crates.io` 항구에서 알아서 실어다 줄 테니."

"크레이트가… 짐이에요?"

"러스트에서는 코드 꾸러미 하나를 크레이트(crate)라고 부른단다. 상자라는 뜻이지. 이 섬 이름이 괜히 크레이트 섬이겠니?"

할머니는 장부를 덮고, 언덕 위의 회색 건물을 턱으로 가리켰다.

"보로가 기다리고 있다. 늦으면 싫어하는 사람이야."

---

회색 건물의 문패에는 이렇게 적혀 있었다.

**크레이트 섬 탐정 사무소 — 소장: 빌림 검사관 보로**

문을 열자, 책상 너머에 회색 코트를 입은 남자가 앉아 있었다. 은테 안경 너머의 눈이 하랑을 위아래로 훑었다. 책상 위에는 주황색 꽃게 한 마리가 앉아 집게발을 딸깍거렸다.

"윤하랑." 남자가 말했다. "프로그램을 실행했더군."

"네. 그냥 출력만 하는 거였는데…"

"그냥이 아니야." 남자가 일어섰다. "넌 방금 **컴파일러의 검문을 통과했어.** 이 섬에서는 컴파일러를 통과하지 못한 코드는 단 한 줄도 실행될 수 없다. 대신, 통과한 코드는 메모리를 망가뜨리지 않는다고 보장받지. 그게 이 섬의 법이다."

그는 손을 내밀었다.

"나는 보로. 사람들은 빌림 검사관(Borrow Checker)이라고 부르지. 그리고 이쪽은 페리."

꽃게가 칠판에 집게발로 삐뚤빼뚤하게 썼다. `안녕!`

"요즘 섬에 사건이 끊이질 않아." 보로가 창밖을 바라보았다. "메모리가 사라지고, 이미 철거된 집의 주소가 거래되고, 같은 금고가 동시에 두 번 열린다. 이 사건들 뒤에는 한 존재가 있다고 나는 믿고 있다."

"누군데요?"

보로는 대답 대신 서랍에서 낡은 사진 한 장을 꺼냈다. 사진 속 인물은 얼굴 부분만 지워져 있었고, 아래에 두 글자가 쓰여 있었다.

**UB**

"정의되지 않은 행동(Undefined Behavior). 다른 섬의 언어들, 이를테면 C나 C++ 섬에서는 이 자가 지나간 자리에서 무슨 일이든 일어날 수 있었다. 프로그램이 멀쩡히 돌다가 갑자기 쓰러지고, 비밀번호가 새어 나가고, 어제는 됐던 게 오늘은 안 됐지. 러스트 섬은 그자를 막기 위해 세워졌다."

보로가 하랑을 똑바로 보았다.

"견습 탐정이 필요해. 할 수 있겠나?"

하랑은 자기도 모르게 고개를 끄덕였다.

> **단서 노트 — 프롤로그**
>
> - **`cargo`** 는 러스트의 빌드 도구이자 패키지 관리자다. `cargo new`(프로젝트 생성), `cargo run`(빌드+실행), `cargo build --release`(최적화 빌드), `cargo check`(빠른 검사), `cargo test`(테스트)를 가장 많이 쓴다.
> - **크레이트(crate)** 는 러스트의 컴파일 단위이자 코드 꾸러미다. 공개 크레이트는 `crates.io`에 모여 있다.
> - **`fn main()`** 은 프로그램의 시작점이다.
> - **`println!`** 끝의 `!`는 이것이 함수가 아니라 **매크로**라는 표시다. (제13장에서 매크로의 비밀을 파헤친다.)
> - 러스트의 약속: **컴파일을 통과한 안전한 코드는 메모리 오류를 일으키지 않는다.**

# 제1장 — 바뀌지 않는 증언

첫 번째 사건은 하랑이 사무소에 도착한 다음 날 아침에 들어왔다.

"빵집 주인의 증언이 바뀌었어." 보로가 서류철을 책상 위에 던졌다. "어젯밤 아홉 시에 가게 앞에서 키 큰 남자를 봤다고 했는데, 오늘 아침엔 키 작은 여자였다고 한다."

"기억이 헷갈린 거 아닐까요?"

"아니. 누군가가 증언을 **바꿔치기** 했어." 보로는 서류철을 펼쳤다. 거기에는 이런 코드가 적혀 있었다.

```rust
fn main() {
    let witness = "키 큰 남자";
    println!("증언: {witness}");
    witness = "키 작은 여자"; // ❌ 컴파일 에러
    println!("증언: {witness}");
}
```

"이 코드는 이 섬에서 실행될 수 없다." 보로가 말했다. "컴파일러가 이렇게 증언하지."

> **컴파일러의 증언**
>
> ```text
> error[E0384]: cannot assign twice to immutable variable `witness`
>  --> src/main.rs:4:5
>   |
> 2 |     let witness = "키 큰 남자";
>   |         ------- first assignment to `witness`
> 3 |     println!("증언: {witness}");
> 4 |     witness = "키 작은 여자";
>   |     ^^^^^^^^^^^^^^^^^^^^^^^^ cannot assign twice to immutable variable
> help: consider making this binding mutable
>   |
> 2 |     let mut witness = "키 큰 남자";
>   |         +++
> ```

"`let`으로 만든 변수는 기본적으로 **바뀌지 않아.**" 보로가 말했다. "한번 한 증언은 바꿀 수 없다. 이 섬의 첫 번째 법이다."

"그럼 진짜로 바꿔야 할 때는요? 게임 점수 같은 건 계속 올라가야 하잖아요."

"그럴 땐 미리 신고를 해야지." 보로가 칠판에 썼다.

### 증거물 #1 — 불변과 가변

```rust
fn main() {
    let name = "하랑";          // 불변: 바꿀 수 없다
    let mut score = 0;          // 가변: mut로 '바뀔 수 있음'을 신고했다

    score += 10;
    score += 5;

    println!("{name}의 점수: {score}");
}
```

"`mut`는 '이 값은 바뀔 거야'라는 **공개 선언**이야. 코드를 읽는 사람은 `mut`가 없는 변수를 보면 '아, 이건 끝까지 이 값이구나' 하고 안심할 수 있지. 수백 줄짜리 함수에서 그게 얼마나 큰 도움이 되는지 곧 알게 될 거다."

---

하랑은 서류를 다시 들여다보았다. 그런데 뒷장에 이상한 코드가 하나 더 있었다.

```rust
fn main() {
    let clue = "발자국";
    let clue = clue.len();     // 같은 이름으로 다시 let?
    println!("단서의 바이트 길이: {clue}");
}
```

"이건 컴파일이 돼요?" 하랑이 물었다. "`mut`도 없는데 `clue`가 바뀌었잖아요."

보로의 안경이 반짝였다. "좋은 눈이군. 이건 **바꾼 게 아니야.** 같은 이름의 **새 변수**를 만든 거지. 이걸 섀도잉(shadowing)이라고 한다. 처음 `clue`는 문자열이었고, 두 번째 `clue`는 숫자야. 타입까지 다르지. 첫 번째 `clue`는 그림자에 가려져 더 이상 이름으로 부를 수 없을 뿐, 덮어쓴 게 아니다."

페리가 칠판에 표를 그렸다.

|       | `let mut x` 후 `x = ...` | `let x` 후 `let x = ...` |
| ----- | ----------------------- | ----------------------- |
| 이름    | 같은 변수                   | **새 변수**                |
| 타입 변경 | 불가                      | **가능**                  |
| 쓰는 곳  | 값이 계속 변하는 상태            | 값을 단계별로 가공할 때           |

### 섬의 기본 증거물들 — 타입

"증언에는 종류가 있어." 보로가 이어서 말했다. "숫자, 참/거짓, 글자. 러스트는 ==🟠**정적 타입** 언어라서 모든 값의 종류가 컴파일할 때 정해져. 대부분은 컴파일러가 알아서 추론해 주지만.=="

### 증거물 #2 — 기본 타입

```rust
fn main() {
    // 정수: i는 부호 있음, u는 부호 없음. 숫자는 비트 수
    let floor: i32 = -3;          // 지하 3층
    let visitors: u64 = 1_000_000; // _는 읽기 편하게 넣는 구분자
    let index: usize = 2;         // 인덱스와 길이에는 usize

    // 실수
    let temperature: f64 = 36.5;

    // 불리언
    let is_guilty: bool = false;

    // 문자 (char는 유니코드 문자 '하나', 4바이트)
    let initial: char = '하';

    // 튜플: 여러 타입을 하나로 묶기
    let alibi: (&str, u32) = ("도서관", 21);
    let (place, hour) = alibi;     // 구조 분해

    // 배열: 같은 타입, 고정 길이
    let suspects: [&str; 3] = ["빵집 주인", "우체부", "정원사"];

    println!("{floor}층, 방문자 {visitors}명, 체온 {temperature}");
    println!("유죄? {is_guilty}, 이니셜 {initial}");
    println!("알리바이: {place}에서 {hour}시");
    println!("두 번째 용의자: {}", suspects[index - 1]);
}
```

"정수가 왜 이렇게 많아요? `i8`, `i16`, `i32`, `i64`, `u8`…"

"==🔴메모리를 얼마나 쓸지 **네가 정하라는 거지.**== 이 섬의 프로그램들은 작은 센서 장치에서도 돌고, 거대한 서버에서도 돈다. 1바이트가 아까운 곳이 있거든." 보로가 덧붙였다. "그리고 하나 더. 러스트는 정수가 넘치는 것도 그냥 넘어가지 않아. 디버그 빌드에서는 넘치는 순간 프로그램을 멈추지(패닉). 일부러 감싸서 돌아가게 하고 싶으면 의도를 밝혀야 하고."

```rust
fn main() {
    let x: u8 = 250;
    println!("{:?}", x.checked_add(10));    // None — 넘치면 '없음'
    println!("{}", x.wrapping_add(10));     // 4 — 한 바퀴 돌아서
    println!("{}", x.saturating_add(10));   // 255 — 최댓값에서 멈춤
}
```

"넘칠 수 있는 곳에서는 '넘치면 어떻게 할지'를 코드에 **적어 두라는** 거다. 이게 이 섬 사람들의 습관이야."

"`return`도 없고, 세미콜론도 없는데요?"

"==🟠러스트에서 거의 모든 것은 **표현식(expression)**, 즉 값을 만들어 내는 식이야. 블록 `{ }`의 마지막 줄에 세미콜론이 없으면, 그 값이 블록 전체의 값이 되지. 세미콜론을 붙이면? 그건 '값을 버리고 끝낸다'는 **문장(statement)** 이 된다.=="

보로는 칠판에 썼다.

### 증거물 #3 — 모든 것이 값이다

```rust
fn main() {
    let hour = 22;

    // if도 값이다
    let time_of_day = if hour < 12 { "오전" } else { "오후" };

    // 블록도 값이다
    let suspicious = {
        let late = hour >= 21;
        let dark = true;
        late && dark            // 세미콜론 없음 → 이 블록의 값
    };

    // loop도 break로 값을 돌려줄 수 있다
    let mut tries = 0;
    let found_at = loop {
        tries += 1;
        if tries * tries > 50 {
            break tries;        // loop의 값
        }
    };

    println!("{time_of_day}, 수상함: {suspicious}, 발견 시도: {found_at}");

    // 반복문들
    for i in 1..=3 {            // 1, 2, 3 (..=는 끝 포함)
        println!("{i}번째 탐문");
    }

    let mut countdown = 3;
    while countdown > 0 {
        println!("{countdown}...");
        countdown -= 1;
    }
}
```

"그래서," 보로가 서류철을 덮으며 말했다. "빵집 주인의 증언 사건. 어떻게 된 건지 알겠나?"

하랑은 서류를 다시 넘겼다. 그리고 마지막 페이지에서 그것을 발견했다.

```rust
    {
        let witness = "키 작은 여자";   // 안쪽 블록의 섀도잉

```

"아!" 하랑이 외쳤다. "증언은 바뀐 적이 없어요! 누군가가 **안쪽 블록에서 같은 이름으로 새 증언을 만들어서** 원래 증언을 가렸던 거예요. 블록이 끝나면 그림자는 사라지고, 원래 증언 '키 큰 남자'가 그대로 남아 있어요!"

```text
(블록 안) 증언: 키 작은 여자
(블록 밖) 증언: 키 큰 남자
```

보로는 처음으로 아주 조금 웃었다.

"원래 증언은 **불변**이었다. 아무도 그것을 바꿀 수 없었지. 범인은 증언을 바꾼 게 아니라 **가렸을 뿐**이야. 그리고 가려진 증언은 블록이 끝나는 순간 다시 드러난다."

그는 하랑에게 탐정 수첩 한 권을 건넸다.

"첫 사건 해결. 하지만 기억해 둬. 오늘 범인이 쓴 수법—같은 이름으로 무언가를 가리는 것—은 앞으로 훨씬 교묘하게 돌아올 거다."

> [!abstract] **단서 노트 — 제1장**
> - 변수는 기본적으로 **불변**이다. 바꾸려면 `let mut`로 선언한다.
> - **섀도잉**은 같은 이름의 새 변수를 만드는 것. 타입도 바꿀 수 있다. 값을 단계별로 가공할 때 유용하다.
> - 정수 타입은 크기와 부호에 따라 `i8`~`i128`, `u8`~`u128`, `isize`/`usize`가 있다. 인덱스와 길이는 `usize`.
> - 오버플로는 디버그 빌드에서 패닉. 의도를 밝히려면 `checked_*`, `wrapping_*`, `saturating_*`.
> - 러스트는 **표현식 중심 언어**다. `if`, 블록, `loop`, `match`가 모두 값을 만든다. 마지막 줄에 세미콜론이 없으면 그 값이 반환된다.

### 사건 파일 정리

불변성은 제약이 아니라 **보증**이다. `mut`가 없는 변수는 절대 바뀌지 않으므로, 코드를 읽는 사람이 추적해야 할 것이 줄어든다. 러스트는 "바뀌는 것"을 눈에 띄게 만들어서 버그가 숨을 곳을 없앤다.

### 탐정의 숙제

1. ★ 섭씨를 화씨로 바꾸는 함수 `fn to_fahrenheit(c: f64) -> f64`를 `return` 없이 작성하라. (화씨 = 섭씨 × 1.8 + 32)
2. ★★ `loop`와 `break 값`을 이용해, 1부터 더해 나갈 때 합이 처음으로 100을 넘는 순간의 숫자를 구하라.
3. ★★ `let x = 5; let x = x * 2; { let x = x + 1; }` 이후 `x`의 값은 무엇이며 왜 그런지 설명하라.

# 제2장 — 단 한 명의 주인

이틀 뒤, 섬의 박물관에서 다이아몬드 '루비 하트'가 사라졌다.

정확히 말하면, 사라진 게 아니었다. 다이아몬드는 분명 **누군가에게 넘겨졌다.** 문제는 넘겨준 쪽인 관장이 여전히 다이아몬드를 가지고 있다고 주장한다는 것이었다.

"제가 경비원 민수에게 다이아몬드를 맡긴 건 맞아요." 관장이 말했다. "하지만 전 여전히 그걸 갖고 있다고요! 장부에 그렇게 적혀 있잖아요!"

보로는 관장의 장부를 하랑에게 내밀었다.

```rust
fn main() {
    let director = String::from("루비 하트");
    let guard = director;              // 다이아몬드를 경비원에게 넘김

    println!("관장이 가진 것: {director}"); // ❌ 컴파일 에러
    println!("경비원이 가진 것: {guard}");
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0382]: borrow of moved value: `director`
>  --> src/main.rs:5:30
>   |
> 2 |     let director = String::from("루비 하트");
>   |         -------- move occurs because `director` has type `String`,
>   |                  which does not implement the `Copy` trait
> 3 |     let guard = director;
>   |                 -------- value moved here
> 4 |
> 5 |     println!("관장이 가진 것: {director}");
>   |                              ^^^^^^^^^^ value borrowed here after move
> ```

"value moved here." 하랑이 소리 내어 읽었다. "값이 여기서 **이동했다**?"

"이 섬의 두 번째 법이다." 보로가 말했다. 그리고 이번에는 칠판 대신 벽에 걸린 낡은 액자를 가리켰다. 거기엔 세 줄의 문장이 새겨져 있었다.

> [!abstract] **소유권의 세 가지 법칙**
> 1. 러스트의 모든 값에는 **주인(owner)** 이라 불리는 변수가 있다.
> 2. 한 값의 주인은 **한 번에 오직 하나**뿐이다.
> 3. 주인이 범위(scope)를 벗어나면, 값은 **버려진다(drop).**

"`let guard = director;`를 하는 순간, 다이아몬드의 주인은 경비원이 됐다. 관장은 이제 **빈손**이야. 관장의 장부에 아무리 이름이 남아 있어도, 이 섬의 법은 그 이름으로 다이아몬드를 만지는 걸 허락하지 않아."

"그런데 왜 그렇게까지 해요? 그냥 둘 다 가지면 안 돼요?"

보로는 창가로 걸어갔다. "C++ 섬에서 실제로 있었던 일을 이야기해 주지."

---

### 이중 해제 — 다른 섬의 비극

"`String`은 겉보기엔 변수 하나지만, 실제로는 두 부분으로 되어 있어."

페리가 칠판에 그림을 그렸다.

```text
   스택 (director)                 힙
  ┌───────────────┐          ┌───┬───┬───┬───┬───┐
  │ ptr       ────┼────────▶│ 루 │ 비 │   │ 하 │ 트 │ ...
  │ len  = 13     │          └───┴───┴───┴───┴───┘
  │ capacity = 13 │
  └───────────────┘
```


==🟠"**스택**에는 주소(ptr), 길이(len), 용량(capacity)만 있고, 진짜 글자들은 **힙**이라는 넓은 창고에 있다. 스택은 빠르지만 크기가 정해진 것만 둘 수 있고, 힙은 느리지만 크기가 자유롭지."==

"만약 `let guard = director;`가 스택의 세 칸만 복사한다면?"

```text
  director ──┐
             ├──▶ [ 루 비 하 트 ] (힙)
  guard    ──┘
```

"두 변수가 **같은 창고 칸**을 가리키게 되지. 그리고 둘 다 범위를 벗어날 때, 둘 다 창고를 비우려 할 거야. 같은 칸을 **두 번** 비우는 거다. 이게 **이중 해제(double free)** 다. C++ 섬에서는 이 사고로 수많은 프로그램이 무너졌고, 해커들은 이 틈으로 남의 컴퓨터에 들어갔지."

하랑은 침을 꿀꺽 삼켰다.

==🟠"그래서 러스트는 이렇게 정했다. 스택의 세 칸을 복사하되, **원래 주인을 무효로 만든다.** 이게 **이동(move)** 이다. 창고 열쇠는 언제나 한 명만 가진다. 그러니 창고는 정확히 한 번만 비워지지."==


---

### 그럼 정수는 왜 괜찮을까?

"잠깐만요." 하랑이 손을 들었다. "어제 제가 짠 코드에서는 이게 됐는데요?"

```rust
fn main() {
    let a = 42;
    let b = a;
    println!("a = {a}, b = {b}");   // 잘 된다!
}
```

"정수는 **전부 스택에 있어.** 창고를 쓰지 않으니 복사해도 문제가 없지. 이런 타입은 `Copy`라는 표식을 달고 있다. 대입하면 이동하는 대신 **복사**돼."

| `Copy`인 타입 (복사됨) | `Copy`가 아닌 타입 (이동함) |
|---|---|
| 정수, 실수, `bool`, `char` | `String` |
| `Copy` 타입만 담은 튜플·배열 | `Vec<T>`, `Box<T>` |
| 공유 참조 `&T` | 가변 참조 `&mut T` |
| | 힙 자원을 가진 대부분의 타입 |

"그럼 `String`을 진짜로 두 개 만들고 싶으면요?"

"명시적으로 요청해. `.clone()`. 창고에 똑같은 다이아몬드를 **새로 하나 더** 만드는 거지. 비용이 드는 일이니, 러스트는 그걸 몰래 해 주지 않아. 네가 직접 `clone`이라고 써야 한다."

### 증거물 #4 — 이동, 복사, 복제

```rust
fn main() {
    // 1) Copy: 정수는 복사된다
    let a = 7;
    let b = a;
    println!("a={a}, b={b}");

    // 2) Move: String은 이동한다
    let s1 = String::from("지문");
    let s2 = s1;
    // println!("{s1}"); // ❌ s1은 이미 이동됨
    println!("s2={s2}");

    // 3) Clone: 명시적으로 깊은 복사
    let s3 = s2.clone();
    println!("s2={s2}, s3={s3}");
}
```

### 함수에 넘기는 것도 이동이다

보로는 장부의 다음 장을 넘겼다. 그리고 거기서 사건의 진짜 열쇠가 드러났다.

```rust
fn hand_over(item: String) {
    println!("경비원이 {item}을(를) 받았다.");
}   // ← 여기서 item이 범위를 벗어난다. 그리고 drop된다!

fn main() {
    let diamond = String::from("루비 하트");
    hand_over(diamond);
    // 이 시점에서 diamond는 이미 없다.
}
```

"함수에 값을 넘기는 것도 **이동**이다." 보로가 말했다. "관장은 다이아몬드를 경비원에게 '맡긴' 줄 알았지만, 실제로는 **소유권을 통째로 넘겼어.** 그리고 경비원의 근무 시간(함수)이 끝나는 순간—"

"다이아몬드가 버려졌어요!" 하랑이 외쳤다. "`hand_over`가 끝나면서 `item`이 범위를 벗어나니까, 루비 하트가 drop된 거예요! 그래서 사라진 거고요!"

"정확해." 보로가 고개를 끄덕였다. "범인은 없다. 관장의 **설계 실수**였지. 맡기려면 돌려받을 방법을 정했어야 했다."

"어떻게요?"

"방법은 두 가지다. 하나는 돌려받는 것."

```rust
fn inspect(item: String) -> String {
    println!("{item}을(를) 검사했다.");
    item                    // 소유권을 다시 돌려준다
}

fn main() {
    let diamond = String::from("루비 하트");
    let diamond = inspect(diamond);   // 넘겼다가 돌려받음
    println!("관장이 다시 가진 것: {diamond}");
}
```

"하지만 매번 이렇게 주고받는 건 번거롭지. 그래서 두 번째 방법이 있다. **빌려주는 것**. 그건 다음 사건에서 배우게 될 거다."

### Drop — 마지막 순간에 일어나는 일

그날 밤, 하랑은 사무소에 남아 혼자 코드를 만지작거렸다. 값이 '버려지는' 순간을 눈으로 보고 싶었다.

페리가 칠판에 힌트를 적어 주었다. `Drop 트레이트를 구현해 봐.`

### 증거물 #5 — 버려지는 순간을 목격하다

```rust
struct Evidence {
    name: String,
}

impl Drop for Evidence {
    fn drop(&mut self) {
        println!("  [폐기] 증거물 '{}'이(가) 처리되었습니다.", self.name);
    }
}

fn main() {
    let _a = Evidence { name: String::from("장갑") };
    {
        let _b = Evidence { name: String::from("머리카락") };
        println!("안쪽 블록 끝");
    } // ← _b가 여기서 drop

    let c = Evidence { name: String::from("쪽지") };
    drop(c); // 직접 일찍 버릴 수도 있다
    println!("main 끝");
} // ← _a가 여기서 drop
```

```text
안쪽 블록 끝
  [폐기] 증거물 '머리카락'이(가) 처리되었습니다.
  [폐기] 증거물 '쪽지'이(가) 처리되었습니다.
main 끝
  [폐기] 증거물 '장갑'이(가) 처리되었습니다.
```

하랑은 출력을 보며 소름이 돋았다. 아무도 `free`나 `delete`를 부르지 않았는데, 값들은 **정확히 범위가 끝나는 그 자리에서** 하나씩 정리되고 있었다.

"가비지 컬렉터도 없는데…" 하랑이 중얼거렸다.

언제 들어왔는지, 등 뒤에서 보로의 목소리가 들렸다.

"그게 러스트의 첫 번째 마법이다. 쓰레기를 주우러 다니는 청소부(가비지 컬렉터)도 없고, 사람이 직접 치우다 실수할 일도 없지. **주인이 떠나면 물건도 떠난다.** 그 시점은 컴파일할 때 이미 정해져 있어. 이 원리를 이용하면 파일, 네트워크 연결, 잠금(lock) 같은 모든 자원을 자동으로 정리할 수 있다. 사람들은 이걸 **RAII**라고 부르지. 제12장쯤 가면 너도 이걸로 무기를 만들게 될 거다."

> **단서 노트 — 제2장**
>
> - **소유권 3법칙**: 모든 값엔 주인이 있다 / 주인은 한 번에 하나 / 주인이 범위를 벗어나면 값은 drop된다.
> - 힙 자원을 가진 타입(`String`, `Vec` 등)은 대입·함수 전달 시 **이동(move)** 한다. 원래 변수는 무효가 된다.
> - 스택에만 있는 단순한 타입은 **`Copy`**: 대입 시 복사된다.
> - 깊은 복사가 필요하면 **`.clone()`** 을 명시적으로 호출한다. 비용이 눈에 보이게 하려는 설계다.
> - **`Drop`** 트레이트로 값이 버려질 때의 동작을 정의할 수 있다. 이것이 **RAII**의 기반이다.

### 사건 파일 정리

소유권은 "메모리를 누가 언제 해제하는가?"라는 질문에 **컴파일 시점**에 답하는 체계다. 덕분에 러스트는 가비지 컬렉터 없이도 이중 해제와 메모리 누수의 대부분을 원천 차단한다. 처음엔 불편하지만, 이 규칙은 곧 설계의 나침반이 된다. "이 데이터의 주인은 누구인가?"를 묻는 습관이 좋은 아키텍처를 만든다.

### 탐정의 숙제

1. ★ `let v = vec![1, 2, 3]; let w = v;` 다음에 `v.len()`을 호출하면 어떤 에러가 날까? 고치는 방법 두 가지를 제시하라.
2. ★★ 증거물 #5에서 `let _ = Evidence { ... };`처럼 이름을 `_`로만 주면 drop 시점이 어떻게 달라지는지 실험하고 이유를 추리하라.
3. ★★★ `String`을 받아 앞뒤 공백을 제거한 새 `String`을 돌려주는 함수를 만들어라. 인자를 `String`으로 받는 것과 `&str`로 받는 것 중 무엇이 더 좋은 설계인지는 제3장을 읽은 뒤 다시 생각해 보라.

### 참조 — 주인은 그대로, 잠깐 빌리기만

보로가 칠판에 썼다.

### 증거물 #6 — 빌려주기

```rust
fn count_pages(book: &String) -> usize {   // &String: 빌려서 '보기만' 한다
    book.len()
}

fn main() {
    let manuscript = String::from("고문서: 크레이트 섬의 기원");
    let n = count_pages(&manuscript);       // &로 빌려준다
    println!("{manuscript}의 길이: {n}");   // 주인은 여전히 manuscript!
}
```

"`&`는 **참조(reference)** 를 만든다. 값을 빌려주는 거지. 소유권은 넘어가지 않아. 함수가 끝나도 빌려 간 사람이 돌려줄 뿐, 고문서는 버려지지 않는다."

"그럼 빌린 사람이 고칠 수도 있어요?"

"그냥 `&`로는 안 돼. 읽기 전용 열쇠야. 고치려면 **가변 참조** `&mut`가 필요하다."

```rust
fn add_footnote(book: &mut String) {
    book.push_str(" [주석: 사서 확인]");
}

fn main() {
    let mut manuscript = String::from("고문서");
    add_footnote(&mut manuscript);
    println!("{manuscript}");
}
```

"이제 사건의 핵심 법칙을 알려 주지." 보로가 액자를 하나 더 가리켰다.

> **빌림의 법칙**
>
> 어느 한 순간, 하나의 값에 대해 다음 둘 중 **하나만** 가능하다.
>
> - **여러 개의** 불변 참조 `&T` (읽는 사람은 몇 명이든 괜찮다)
> - **단 하나의** 가변 참조 `&mut T` (고치는 사람은 혼자여야 한다)
>
> 그리고 참조는 언제나 **유효한 값**을 가리켜야 한다.

"읽는 사람이 여럿일 때는 아무도 고칠 수 없다. 고치는 사람이 있을 때는 아무도 읽을 수 없다. 이걸 사람들은 **'공유 XOR 가변(aliasing XOR mutability)'** 이라고 부르지."

### 사건의 재구성

하랑은 사서의 대출 기록을 받아 들었다.

```rust
fn main() {
    let mut page3 = String::from("섬은 300년 전에 세워졌다.");

    let scholar_a = &page3;            // 학자 A가 읽기 시작
    let scholar_b = &page3;            // 학자 B도 읽기 시작
    let forger = &mut page3;           // ❌ 누군가 고치려 함!
    forger.push_str(" (사실은 30년 전)");

    println!("A: {scholar_a}");
    println!("B: {scholar_b}");
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0502]: cannot borrow `page3` as mutable because it is also
>               borrowed as immutable
>  --> src/main.rs:6:18
>   |
> 4 |     let scholar_a = &page3;
>   |                     ------ immutable borrow occurs here
> 5 |     let scholar_b = &page3;
> 6 |     let forger = &mut page3;
>   |                  ^^^^^^^^^^ mutable borrow occurs here
> ...
> 9 |     println!("A: {scholar_a}");
>   |                  ----------- immutable borrow later used here
> ```

"이 섬에서는 이 코드가 **컴파일조차 되지 않아요.**" 하랑이 말했다. "그런데 어떻게 이런 일이 일어났죠?"

보로는 대출 기록 맨 아래의 작은 글씨를 가리켰다. **"외부 섬 방문객 — C 언어 섬 출신"**

"범인은 이 섬의 법을 모르는 방문객이었어. C 섬에서는 누구나 포인터를 들고 다니며 아무 때나 쓸 수 있으니까. 그는 이 도서관을 C 섬의 도서관처럼 썼고, 우리 사서는 그 사람이 들고 온 '외부 열쇠'를 확인하지 못했다." 보로가 서류를 덮었다. "이 섬의 코드 안에서라면 결코 일어날 수 없는 일이지. 외부와의 경계—이걸 FFI라고 하는데—를 어떻게 지킬지는 제14장에서 다시 다루자."

### 빌림은 '마지막으로 쓰인 곳'에서 끝난다

하랑은 수첩에 법칙을 옮겨 적다가 문득 이상한 점을 발견했다.

```rust
fn main() {
    let mut page = String::from("원본");

    let reader = &page;
    println!("읽기: {reader}");     // reader의 마지막 사용

    let writer = &mut page;          // 이건 왜 괜찮지?
    writer.push_str(" + 수정");
    println!("수정 후: {page}");
}
```

"이건 컴파일이 돼요! `reader`랑 `writer`가 같은 함수 안에 있는데요?"

"`reader`는 `println!` 이후로 **다시는 쓰이지 않아.** 컴파일러는 빌림이 **마지막으로 사용된 지점에서 끝난다**는 걸 알아. 이 기능을 **NLL(Non-Lexical Lifetimes)** 이라고 부른다. 빌림의 수명은 중괄호가 아니라 **실제 사용 흐름**을 따라가지."

### 슬라이스 — 일부만 빌리기

"고문서 전체가 아니라 한 구절만 빌려주고 싶을 때는?"

"그게 **슬라이스(slice)** 다."

### 증거물 #7 — 문자열 슬라이스와 첫 단어 찾기

```rust
fn first_word(text: &str) -> &str {
    for (i, ch) in text.char_indices() {
        if ch == ' ' {
            return &text[..i];   // 처음부터 공백 직전까지
        }
    }
    text                         // 공백이 없으면 전체
}

fn main() {
    let record = String::from("댕글링 목격 보고서");
    let word = first_word(&record);   // &String은 자동으로 &str이 된다
    println!("첫 단어: {word}");

    let literal = "레이스 쌍둥이";      // 문자열 리터럴은 원래 &str
    println!("첫 단어: {}", first_word(literal));

    let numbers = [10, 20, 30, 40, 50];
    let middle: &[i32] = &numbers[1..4];   // 배열 슬라이스
    println!("가운데: {middle:?}");
}
```

"`&str`은 '어딘가에 있는 문자열의 일부를 가리키는 창문'이야. 문자열 그 자체가 아니라 **시작 주소와 길이**만 갖고 있지. 그래서 함수 인자로는 `&String`보다 `&str`이 훨씬 좋다. `String`이든, 문자열 리터럴이든, 다른 문자열의 일부든 다 받을 수 있으니까."

"아, 제2장 숙제 3번의 답이 이거였군요!"

"그렇다." 보로가 덧붙였다. "그리고 이걸 보라고."

```rust
fn first_word(text: &str) -> &str {
    text.split(' ').next().unwrap_or("")
}

fn main() {
    let mut record = String::from("댕글링 목격 보고서");
    let word = first_word(&record);
    record.clear();                 // ❌ 컴파일 에러: word가 아직 record를 빌리고 있다
    println!("첫 단어: {word}");
}
```

"`word`는 `record`의 일부를 가리키는 창문이야. 그런데 `record.clear()`는 창고를 비우려 하지. 창문이 열려 있는데 방을 철거하려는 거야. 다른 섬이었다면 `word`는 빈 방을 가리키는 **유령**이 되었겠지만, 이 섬의 컴파일러는 그걸 미리 막는다."

하랑은 등골이 서늘해졌다. "유령…"

"그래." 보로의 표정이 어두워졌다. "오늘 밤 그 유령이 출몰한다는 제보가 들어왔다."

> **단서 노트 — 제3장**
>
> - `&T`는 **불변 참조**(공유 빌림), `&mut T`는 **가변 참조**(독점 빌림).
> - 빌림의 법칙: 한 순간에 **여러 개의 `&T`** 또는 **하나의 `&mut T`**. 둘을 섞을 수 없다.
> - 빌림은 **마지막으로 사용된 지점**에서 끝난다(NLL).
> - **슬라이스** `&str`, `&[T]`는 연속된 데이터의 일부를 가리키는 '창문'이다.
> - 함수 인자는 가능하면 `&String` 대신 `&str`, `&Vec<T>` 대신 `&[T]`로 받자. 더 유연하다.
> - 이 규칙들은 **데이터 경쟁**과 **반복자 무효화** 같은 버그를 컴파일 시점에 막는다.

### 사건 파일 정리

빌림 검사기는 "누가 읽고 있을 때 아무도 쓰지 않는다"는 단순한 원칙을 강제한다. 이 원칙 하나가 단일 스레드에서는 반복자 무효화를, 멀티 스레드에서는 데이터 경쟁을 막는다. 같은 규칙이 두 종류의 버그를 동시에 없애는 것—이것이 러스트 설계의 우아함이다.

### 탐정의 숙제

1. ★ `fn longest_len(words: &[&str]) -> usize`를 작성하라. 단어 목록 중 가장 긴 단어의 바이트 길이를 돌려준다.
2. ★★ 다음 코드가 컴파일되지 않는 이유를 빌림의 법칙으로 설명하라.
   ```rust
   let mut v = vec![1, 2, 3];
   let first = &v[0];
   v.push(4);
   println!("{first}");
   ```
   (힌트: `push`는 창고가 꽉 차면 **더 큰 창고로 이사**한다.)
3. ★★★ 한글 문자열 `"탐정"`에 대해 `&s[0..1]`을 하면 어떤 일이 벌어지는가? 왜 그런가? `char_indices()`를 쓰는 이유와 연결해 설명하라.

# 제4장 — 유령 포인터의 밤

자정. 섬의 북쪽, 오래된 주택가.

하랑과 보로는 가로등 아래 숨어 3번지 집을 지켜보고 있었다. 3번지는 일주일 전에 철거가 결정된 빈집이었다.

"아무것도 없겠죠."

"아니. 더 나빠. **다른 사람이 새로 지은 집**이 있을 수도 있고, 공사 현장일 수도 있고, 그냥 허공일 수도 있다. 무엇이 있을지 아무도 몰라. 그게 UB 백작이 좋아하는 상황이지."

바로 그때, 그림자 하나가 3번지 앞을 스쳐 지나갔다. 검은 망토. 손에는 주소가 적힌 쪽지.

보로가 뛰쳐나갔지만, 그림자는 골목 너머로 사라졌다. 바닥에 떨어진 것은 쪽지 한 장뿐이었다. 하랑이 주워 들었다.

```rust
fn steal_address() -> &String {
    let house = String::from("3번지의 집");
    &house
}
```

### 댕글링 참조 — 사라진 집의 주소

"이게 댕글링의 수법이야." 보로가 쪽지를 불빛에 비추었다. "함수 안에서 집(`house`)을 짓고, 그 **주소**(`&house`)를 밖으로 내보내지. 그런데 함수가 끝나면?"

"`house`가 범위를 벗어나니까… drop돼요. 집이 철거돼요!"

"그래. 그럼 밖으로 나간 주소는 **철거된 집**을 가리키게 된다. 이게 **댕글링 참조(dangling reference)** 다."

하랑은 쪽지를 뒤집었다. 뒷면에는 컴파일러의 판결문이 찍혀 있었다.

> **컴파일러의 증언**
>
> ```text
> error[E0106]: missing lifetime specifier
>  --> src/main.rs:1:23
>   |
> 1 | fn steal_address() -> &String {
>   |                       ^ expected named lifetime parameter
>   |
>   = help: this function's return type contains a borrowed value,
>           but there is no value for it to be borrowed from
> help: instead, you are more likely to want to return an owned value
>   |
> 1 - fn steal_address() -> &String {
> 1 + fn steal_address() -> String {
> ```

"컴파일러가 이미 잡았네요!" 하랑이 말했다. "'빌려 올 원래 값이 없는데 빌린 값을 돌려주려 한다'고요. 그리고 해결책까지 줬어요. **주소 말고 집 자체를 넘겨라**(`String`을 반환하라)."

"이 섬에서 댕글링이 단 한 번도 성공하지 못한 이유다." 보로가 말했다. "하지만 이번엔 그자가 더 교묘한 쪽지를 남겼어. 이거 봐."

쪽지는 한 장이 아니었다. 아래에 또 한 장이 붙어 있었다.

```rust
fn longer(a: &str, b: &str) -> &str {
    if a.len() > b.len() { a } else { b }
}
```

"이번엔 집을 함수 안에서 짓지도 않았어요. 밖에서 받은 주소 중 하나를 그대로 돌려주는 것뿐인데… 이것도 안 돼요?"

"안 된다. 컴파일러가 묻지. **'돌려주는 주소가 `a`의 것이냐, `b`의 것이냐? 그 집은 얼마나 오래 서 있느냐?'** 이 함수만 봐서는 알 수가 없거든."

---

### 라이프타임 — 집이 서 있는 기간

보로는 하랑을 데리고 사무소로 돌아왔다. 페리가 벌써 칠판에 무언가를 그려 놓고 있었다.

```text
     'a 의 기간  ├────────────────────────┤
     'b 의 기간        ├──────────┤
     반환값은?   ├?????????????????????????┤
```

"모든 참조에는 **라이프타임(lifetime)**, 즉 '이 주소가 유효한 기간'이 있다. 대부분은 컴파일러가 알아서 계산하지만, 함수가 여러 참조를 받아서 하나를 돌려줄 때는 우리가 관계를 **알려 줘야** 해."

### 증거물 #8 — 라이프타임 표기

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let alibi1 = String::from("도서관에 있었다");
    let result;
    {
        let alibi2 = String::from("집에 있었다");
        result = longer(&alibi1, &alibi2);
        println!("더 긴 알리바이: {result}");   // OK: alibi2가 살아 있는 동안 사용
    }
    // println!("{result}"); // ❌ alibi2는 이미 철거됨. result가 그걸 가리킬 수도 있다.
}
```

"`'a`는 이름일 뿐이야. 작은따옴표로 시작하는 걸 빼면 그냥 제네릭 매개변수와 같지. 이 표기는 이렇게 읽는다."

> **"`a`와 `b`가 둘 다 최소한 `'a` 동안은 살아 있다. 반환값도 `'a` 동안만 유효하다."**

"즉, 반환값은 **둘 중 더 일찍 철거되는 집**만큼만 믿을 수 있다는 뜻이지. 라이프타임 표기는 수명을 **늘려 주지 않아.** 그저 관계를 **설명**할 뿐이야. 그 설명을 근거로 컴파일러가 호출하는 쪽을 검사하는 거고."

하랑은 수첩에 크게 적었다. **라이프타임 = 늘리는 게 아니라 설명하는 것.**

---

### 생략 규칙 — 대부분은 안 써도 되는 이유

"그런데 제3장의 `first_word`는 라이프타임을 안 썼잖아요."

"컴파일러가 흔한 경우를 알아서 채워 주기 때문이다. 이걸 **라이프타임 생략 규칙(elision rules)** 이라고 하지." 보로가 세 줄을 적었다.

> **생략 규칙**
>
> 1. 참조 매개변수마다 각자의 라이프타임이 붙는다.
> 2. 참조 매개변수가 **딱 하나**면, 반환 참조는 그것과 같은 라이프타임을 갖는다.
> 3. 메서드에서 `&self`나 `&mut self`가 있으면, 반환 참조는 `self`의 라이프타임을 갖는다.

"`first_word(text: &str) -> &str`은 규칙 2에 해당해서 자동으로 `fn first_word<'a>(text: &'a str) -> &'a str`이 되는 거다. `longer`는 참조가 두 개라서 규칙으로 정할 수 없었던 거고."

---

### 참조를 품은 구조체

"마지막 단서." 보로가 서랍에서 봉투를 꺼냈다. "댕글링이 쓰는 가방이다. 지난달 압수했지."

```rust
struct Satchel<'a> {
    stolen_address: &'a str,
}

impl<'a> Satchel<'a> {
    fn peek(&self) -> &'a str {
        self.stolen_address
    }
}

fn main() {
    let town_registry = String::from("북쪽 주택가 3번지");
    let bag = Satchel { stolen_address: &town_registry };
    println!("가방 속 주소: {}", bag.peek());
}
```

"구조체가 참조를 품으려면, 그 구조체는 **참조된 원본보다 오래 살 수 없다**고 선언해야 해. `Satchel<'a>`는 '`'a`가 끝나기 전에 나도 끝난다'는 서약서야. 그래서 이 가방은 철거된 집의 주소를 **담고 있을 수조차 없다.** 컴파일러가 서약서를 검사하니까."

하랑은 가방을 내려다보았다. "그럼 댕글링은… 이 섬에선 절대 못 이기는 거네요."

"안전한 러스트 안에서는." 보로가 안경을 고쳐 썼다. "하지만 그 녀석이 단순히 실패를 거듭하려고 이 섬에 오는 건 아닐 거다. 녀석은 우리 섬의 **경계**를 시험하고 있어. 컴파일러가 볼 수 없는 곳을."

### `'static` — 섬이 가라앉을 때까지

다음 날 아침, 하랑은 수첩을 정리하다가 한 가지를 더 물었다.

"`&'static str`은 뭐예요? 에러 메시지에서 자주 봤어요."

"**프로그램이 끝날 때까지** 유효한 참조다. 문자열 리터럴이 대표적이지. `"안녕"`이라는 글자는 프로그램 실행 파일 안에 새겨져 있으니까, 섬이 가라앉을 때까지 사라지지 않아."

```rust
fn island_motto() -> &'static str {
    "컴파일되면, 믿을 수 있다."
}

fn main() {
    println!("{}", island_motto());
}
```

"하나 주의할 점. `T: 'static`이라는 조건은 '영원히 살아야 한다'가 아니라 **'빌린 짧은 참조를 품고 있지 않다'** 는 뜻이야. `String`처럼 스스로 데이터를 소유한 타입은 `'static` 조건을 만족하지. 스레드를 만들 때 이 조건을 자주 만나게 될 거다."

> **단서 노트 — 제4장**
>
> - **댕글링 참조**: 이미 해제된 메모리를 가리키는 참조. 러스트는 컴파일 시점에 금지한다.
> - **라이프타임** `'a`는 참조가 유효한 기간의 **이름**이다. 수명을 늘리지 않고, 참조들 사이의 **관계를 설명**한다.
> - 대부분의 경우 **생략 규칙** 덕분에 쓰지 않아도 된다. 입력 참조가 여럿이고 반환 참조가 있을 때 명시가 필요하다.
> - 참조를 가진 구조체는 `struct S<'a>`처럼 라이프타임을 선언해야 한다.
> - **`'static`**: 프로그램 전체 기간 동안 유효. `T: 'static`은 "짧은 빌림을 품지 않는다"는 뜻.
> - 막히면 **참조 대신 소유한 값을 반환**하는 것이 가장 흔한 해법이다.

### 사건 파일 정리

C와 C++에서 가장 악명 높은 버그인 use-after-free를 러스트는 '라이프타임'이라는 개념으로 타입 시스템에 편입시켰다. 라이프타임 표기가 어렵게 느껴진다면, 그것은 대개 설계가 "누가 누구를 얼마나 오래 빌리는가"를 명확히 하지 않았다는 신호다. 라이프타임과 싸우지 말고, 데이터 흐름을 다시 그려 보라.

### 탐정의 숙제

1. ★ `fn pick_first<'a, 'b>(x: &'a str, _y: &'b str) -> &'a str`가 왜 `longer`와 달리 `y`의 수명과 무관한지 설명하라.
2. ★★ 문장을 받아 가장 긴 단어를 반환하는 `fn longest_word(s: &str) -> &str`를 작성하라. 라이프타임을 명시하지 않아도 되는 이유는?
3. ★★★ `struct Parser<'a> { input: &'a str, pos: usize }`를 만들고, 다음 단어를 하나씩 꺼내는 `fn next_word(&mut self) -> Option<&'a str>`를 구현하라. 반환 타입이 `&'a str`인 것과 `&str`(즉, `&self`의 수명)인 것의 차이를 설명하라.

# 제5장 — 가면을 쓴 용의자들

"그럼 증언을 **정리하는 틀**을 만들어야지." 보로가 말했다. "흩어진 정보를 하나로 묶는 것. 그게 구조체다."

### 구조체 — 용의자 카드

### 증거물 #9 — 구조체와 메서드

```rust
#[derive(Debug, Clone, PartialEq)]
struct Suspect {
    name: String,
    height_cm: u32,
    has_alibi: bool,
}

impl Suspect {
    // 연관 함수(생성자 관례): self가 없다
    fn new(name: &str, height_cm: u32) -> Self {
        Self { name: name.to_string(), height_cm, has_alibi: false }
    }

    // 읽기 메서드: &self
    fn is_tall(&self) -> bool {
        self.height_cm >= 175
    }

    // 수정 메서드: &mut self
    fn confirm_alibi(&mut self) {
        self.has_alibi = true;
    }

    // 소비 메서드: self (호출 후 원래 값은 사용 불가)
    fn into_report(self) -> String {
        format!("{} ({}cm) — 알리바이: {}", self.name, self.height_cm, self.has_alibi)
    }
}

fn main() {
    let mut s = Suspect::new("우체부 김씨", 182);
    println!("{s:?}");                 // Debug 출력
    println!("키가 큰가? {}", s.is_tall());

    s.confirm_alibi();
    let report = s.into_report();      // s는 여기서 소비된다
    println!("{report}");
}
```

"`impl` 블록 안에 함수를 넣으면 그 타입의 **메서드**가 된다. 첫 번째 인자를 보면 그 메서드가 무슨 짓을 할지 알 수 있지."

| 첫 인자 | 의미 | 비유 |
|---|---|---|
| `&self` | 읽기만 한다 | 카드를 들여다본다 |
| `&mut self` | 고친다 | 카드에 메모를 덧붙인다 |
| `self` | 소비한다 | 카드를 보고서로 만들어 제출해 버린다 |
| (없음) | 연관 함수 | 새 카드를 만든다 (`Suspect::new`) |

"그리고 `#[derive(...)]`는 컴파일러에게 '흔한 기능을 대신 만들어 달라'고 부탁하는 주문이야. `Debug`는 `{:?}`로 출력하는 기능, `Clone`은 복제, `PartialEq`는 `==` 비교. 이 주문이 내부적으로 어떻게 작동하는지는 제13장에서 밝혀질 거다."

---

### 열거형 — 여러 얼굴 중 하나

"그런데 목격 증언은 종류가 다 달라요." 하랑이 말했다. "이름을 본 사람, 키만 본 사람, 아무것도 못 본 사람… 구조체 하나로는 다 담을 수가 없어요."

"그럴 때 쓰는 게 **열거형(enum)** 이다. 다른 언어의 enum과는 차원이 달라. 러스트의 열거형은 **각 경우마다 다른 데이터를 품을 수 있지.**"

### 증거물 #10 — 데이터를 품은 열거형과 match

```rust
enum Testimony {
    SawName(String),                       // 이름을 봤다
    SawHeight { min: u32, max: u32 },      // 키 범위를 봤다
    SawItem(String, String),               // (물건, 색깔)
    SawNothing,                            // 아무것도 못 봤다
}

fn analyze(t: &Testimony) -> String {
    match t {
        Testimony::SawName(name) => format!("이름 확보: {name}"),
        Testimony::SawHeight { min, max } if max - min <= 5 => {
            format!("정확한 키 증언: {min}~{max}cm")
        }
        Testimony::SawHeight { min, max } => format!("애매한 키 증언: {min}~{max}cm"),
        Testimony::SawItem(item, color) => format!("{color} {item}을(를) 든 사람"),
        Testimony::SawNothing => String::from("증거 가치 없음"),
    }
}

fn main() {
    let testimonies = vec![
        Testimony::SawName(String::from("모자 장수")),
        Testimony::SawHeight { min: 170, max: 173 },
        Testimony::SawHeight { min: 150, max: 190 },
        Testimony::SawItem(String::from("우산"), String::from("빨간")),
        Testimony::SawNothing,
    ];

    for t in &testimonies {
        println!("{}", analyze(t));
    }
}
```

"`match`는 탐정의 **추리 분기표**다." 보로가 말했다. "그리고 가장 강력한 점은 이거야. **모든 경우를 다루지 않으면 컴파일이 안 돼.**"

"모든 경우요?"

### 사건 해결

하랑은 모든 증언을 `Testimony`로 정리하고, 용의자 명단을 `Suspect`로 만든 뒤, 각 용의자가 증언과 일치하는지 검사하는 함수를 짰다.

```rust
#[derive(Debug)]
struct Suspect { name: String, height_cm: u32, items: Vec<String> }

enum Testimony {
    SawHeight { min: u32, max: u32 },
    SawItem(String),
    SawNothing,
}

fn matches(s: &Suspect, t: &Testimony) -> bool {
    match t {
        Testimony::SawHeight { min, max } => (*min..=*max).contains(&s.height_cm),
        Testimony::SawItem(item) => s.items.contains(item),
        Testimony::SawNothing => true,   // 아무 정보가 없으면 배제할 수 없다
    }
}

fn main() {
    let suspects = vec![
        Suspect { name: "모자 장수".into(), height_cm: 168, items: vec!["모자".into()] },
        Suspect { name: "우산 장수".into(), height_cm: 140, items: vec!["우산".into(), "모자".into()] },
        Suspect { name: "꽃 장수".into(), height_cm: 142, items: vec!["꽃".into()] },
    ];
    let testimonies = vec![
        Testimony::SawHeight { min: 135, max: 145 },
        Testimony::SawItem("우산".into()),
        Testimony::SawNothing,
    ];

    for s in &suspects {
        if testimonies.iter().all(|t| matches(s, t)) {
            println!("범인 후보: {s:?}");
        }
    }
}
```

```text
범인 후보: Suspect { name: "우산 장수", height_cm: 140, items: ["우산", "모자"] }
```

보로는 수첩에 무언가를 적었다.

"하나의 대상이 여러 측면을 가진다. 열거형은 '여러 개 중 정확히 하나', 구조체는 '여러 개를 전부 함께'. 이 두 가지를 조합하는 것—프로그래머들은 이걸 **대수적 자료형(Algebraic Data Types)** 이라고 부른다—이 러스트 설계의 뼈대다. 잘 만든 타입은 **잘못된 상태를 표현할 수조차 없게** 만들지."

> **단서 노트 — 제5장**
>
> - **구조체**는 여러 데이터를 '모두 함께' 묶는다(곱 타입). **열거형**은 여러 경우 중 '정확히 하나'를 표현한다(합 타입).
> - `impl` 블록에서 메서드를 정의한다. 첫 인자 `&self` / `&mut self` / `self`로 의도가 드러난다.
> - `#[derive(Debug, Clone, PartialEq, ...)]`로 흔한 트레이트를 자동 구현한다.
> - `match`는 **완전성(exhaustiveness)** 을 검사한다. 빠뜨린 경우가 있으면 컴파일 에러.
> - 패턴: 리터럴, `|`, 범위 `..=`, 가드 `if`, 분해, `..`, `@` 바인딩, 슬라이스 패턴.
> - 한 경우만 볼 땐 `if let`, 실패 시 일찍 빠져나갈 땐 `let ... else`.
> - 설계 원칙: **"잘못된 상태를 표현할 수 없게 만들어라(Make invalid states unrepresentable)."**

### 탐정의 숙제

### 증거물 #13 — 커스텀 에러와 ? 연산자

```rust
use std::collections::HashMap;
use std::fmt;

#[derive(Debug)]
enum BankError {
    AccountNotFound(String),
    InsufficientFunds { needed: u64, available: u64 },
    LimitExceeded(u64),
}

impl fmt::Display for BankError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            BankError::AccountNotFound(id) => write!(f, "계좌 '{id}'를 찾을 수 없음"),
            BankError::InsufficientFunds { needed, available } => {
                write!(f, "잔액 부족: {needed}원 필요, {available}원 있음")
            }
            BankError::LimitExceeded(limit) => write!(f, "1회 한도 {limit}원 초과"),
        }
    }
}

impl std::error::Error for BankError {}

struct Bank {
    accounts: HashMap<String, u64>,
}

impl Bank {
    const LIMIT: u64 = 1_000_000;

    fn balance(&self, id: &str) -> Result<u64, BankError> {
        self.accounts
            .get(id)
            .copied()
            .ok_or_else(|| BankError::AccountNotFound(id.to_string()))
    }

    fn transfer(&mut self, from: &str, to: &str, amount: u64) -> Result<(), BankError> {
        if amount > Self::LIMIT {
            return Err(BankError::LimitExceeded(Self::LIMIT));
        }
        let available = self.balance(from)?;   // 실패하면 즉시 Err 반환
        self.balance(to)?;                     // 받는 계좌 존재 확인
        if available < amount {
            return Err(BankError::InsufficientFunds { needed: amount, available });
        }
        *self.accounts.get_mut(from).unwrap() -= amount;
        *self.accounts.get_mut(to).unwrap() += amount;
        Ok(())
    }
}

fn main() {
    let mut bank = Bank {
        accounts: HashMap::from([
            ("하랑".to_string(), 50_000),
            ("보로".to_string(), 900_000),
        ]),
    };

    let attempts = [
        ("하랑", "보로", 10_000),
        ("하랑", "보로", 100_000),
        ("유령", "보로", 1),
        ("보로", "하랑", 2_000_000),
    ];

    for (from, to, amount) in attempts {
        match bank.transfer(from, to, amount) {
            Ok(()) => println!("성공: {from} → {to} {amount}원"),
            Err(e) => println!("실패: {e}"),
        }
    }
}
```

```text

실패: 잔액 부족: 100000원 필요, 40000원 있음
실패: 계좌 '유령'를 찾을 수 없음
실패: 1회 한도 1000000원 초과
```

"`?`는 뭐예요? 물음표 하나로 뭔가 엄청난 일을 하는 것 같은데요."

"`?`는 이렇게 읽어. **'성공이면 값을 꺼내고, 실패면 지금 당장 그 에러를 들고 함수를 빠져나가라.'**"

### 증거물 #14 — From으로 에러 합치기

```rust
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum CaseError {
    Parse(ParseIntError),
    Invalid(String),
}

impl fmt::Display for CaseError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            CaseError::Parse(e) => write!(f, "숫자 해석 실패: {e}"),
            CaseError::Invalid(msg) => write!(f, "잘못된 기록: {msg}"),
        }
    }
}

impl std::error::Error for CaseError {}

// ParseIntError → CaseError 변환 방법을 알려 준다
impl From<ParseIntError> for CaseError {
    fn from(e: ParseIntError) -> Self {
        CaseError::Parse(e)
    }
}

// "21:30" 같은 문자열을 자정 이후 분으로 바꾼다
fn parse_time(s: &str) -> Result<u32, CaseError> {
    let (h, m) = s
        .split_once(':')
        .ok_or_else(|| CaseError::Invalid(format!("콜론이 없음: {s}")))?;
    let h: u32 = h.parse()?;   // ParseIntError가 자동으로 CaseError로!
    let m: u32 = m.parse()?;
    if h >= 24 || m >= 60 {
        return Err(CaseError::Invalid(format!("범위를 벗어난 시각: {s}")));
    }
    Ok(h * 60 + m)
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    for input in ["21:30", "9시", "25:00", "ab:10"] {
        match parse_time(input) {
            Ok(min) => println!("{input} → {min}분"),
            Err(e) => println!("{input} → 에러: {e}"),
        }
    }
    let t = parse_time("08:15")?;   // main도 Result를 돌려줄 수 있다
    println!("최종 확인: {t}분");
    Ok(())
}
```

"실무에서는 이걸 매번 손으로 쓰지 않는다." 보로가 덧붙였다. "라이브러리를 만들 땐 `thiserror`라는 크레이트로 `#[derive(Error)]` 한 줄이면 위의 `Display`와 `From`이 자동으로 만들어지고, 애플리케이션에서는 `anyhow`라는 크레이트로 모든 에러를 한 바구니에 담지. 카고 할머니께 부탁하면 바로 실어다 주실 거다."

### unwrap의 유혹

"그런데요," 하랑이 말했다. "인터넷 예제에는 `.unwrap()`이 엄청 많던데요. 그냥 그걸 쓰면 안 돼요?"

보로의 표정이 굳었다.

"`unwrap()`은 **'실패하면 프로그램을 즉시 죽여라'** 라는 뜻이다. 예제나 테스트, 또는 **논리적으로 절대 실패할 수 없는 곳**에서만 쓴다. 그럴 때도 `expect("이유")`로 왜 실패할 수 없는지 적어 두는 게 예의지."

```rust
fn main() {
    let config_port = "8080";
    // 하드코딩된 값이라 실패할 수 없다 — 이유를 남긴다
    let port: u16 = config_port.parse().expect("하드코딩된 포트는 항상 유효한 숫자");
    println!("포트: {port}");
}
```

| 상황 | 추천 |
|---|---|
| 호출자가 실패를 처리할 수 있다 | `Result`를 반환하고 `?` 사용 |
| 값이 없을 수 있는 게 정상이다 | `Option` 반환 |
| 기본값으로 대체 가능하다 | `unwrap_or`, `unwrap_or_default`, `unwrap_or_else` |
| 실패는 곧 **프로그래머의 버그**다 | `expect("왜 불가능한지")` |
| 프로토타입, 테스트 | `unwrap()` (나중에 반드시 정리) |

"`panic!`은 **'이건 복구할 수 없는 버그다'** 라는 선언이야. `Result`는 **'이건 일어날 수 있는 일이다'** 라는 선언이고. 둘을 구분하는 것이 숙련된 탐정의 감각이다."

---

은행 사건은 그날 저녁 해결되었다. 이체 시스템의 로그를 `Result`와 커스텀 에러로 다시 짜자, 범인이 드러났다. 실패한 이체의 대부분이 `AccountNotFound("유령")`이었다.

"존재하지 않는 계좌로 반복해서 이체를 시도한 흔적이에요." 하랑이 말했다. "누군가 시스템의 약점을 **탐색**하고 있었던 거예요."

"그리고 예전 시스템은 실패 이유를 기록하지 않았기 때문에 아무도 몰랐지." 보로가 로그를 넘기며 말했다. "'유령'이라… 댕글링의 짓이다. 녀석은 섬 전체를 조사하고 있어."

> **단서 노트 — 제6장**
>
> - 러스트엔 null이 없다. 없을 수 있는 값은 **`Option<T>`**(`Some`/`None`)로 표현한다.
> - 실패할 수 있는 연산은 **`Result<T, E>`**(`Ok`/`Err`)를 반환한다.
> - **`?` 연산자**: 성공이면 값을 꺼내고, 실패면 `From`으로 변환하여 즉시 반환한다.
> - 커스텀 에러는 `enum` + `Display` + `std::error::Error` + `From`. 실무에선 `thiserror`(라이브러리), `anyhow`(애플리케이션).
> - 유용한 조합기: `map`, `and_then`, `ok_or`, `ok_or_else`, `unwrap_or`, `filter`, `as_deref`.
> - `panic!`/`unwrap`은 **버그**를 위한 것, `Result`는 **예상 가능한 실패**를 위한 것.

### 탐정의 숙제

1. ★ `fn divide(a: i32, b: i32) -> Option<i32>`를 작성하라. 0으로 나누면 `None`.
2. ★★ 설정 파일의 한 줄 `"timeout=30"`을 `(String, u32)`로 파싱하는 함수를 `Result`와 `?`로 작성하라. 등호가 없을 때와 숫자가 아닐 때 다른 에러를 반환하라.
3. ★★★ `Option<Option<T>>`와 `Result<Option<T>, E>`가 각각 어떤 상황을 표현하는지 예를 들어 설명하고, `transpose()`가 무엇을 하는지 조사하라.

### Vec — 한 줄로 늘어선 책장

### 증거물 #15 — 벡터 기초

```rust
fn main() {
    let mut shelf: Vec<&str> = Vec::new();
    shelf.push("섬의 역사");
    shelf.push("컴파일러 연대기");
    shelf.push("섬의 역사");          // 중복!

    let mut shelf2 = vec!["항해술", "등대지기"];   // vec! 매크로
    shelf2.extend(["별자리"]);

    println!("첫 번째 책: {}", shelf[0]);          // 범위 밖이면 패닉
    println!("열 번째 책: {:?}", shelf.get(9));     // 범위 밖이면 None (안전)

    for book in &shelf {                            // 빌려서 순회
        println!("- {book}");
    }

    for book in shelf2.iter_mut() {                 // 고치면서 순회
        *book = if book.chars().count() > 3 { "긴 제목" } else { *book };
    }
    println!("{shelf2:?}");

    if let Some(last) = shelf.pop() {
        println!("마지막 책을 뺐다: {last}");
    }

    shelf.sort();
    shelf.dedup();                                  // 연속된 중복 제거
    println!("정리 후: {shelf:?}, 길이 {}, 용량 {}", shelf.len(), shelf.capacity());
}
```

"`v[i]`는 범위를 벗어나면 패닉, `v.get(i)`는 `Option`을 돌려줘. 이 섬에서는 **경계를 벗어난 접근이 절대 조용히 넘어가지 않아.** C 섬에서는 배열 끝을 넘어서 읽으면 옆집 메모리가 그대로 읽혔다고 하지. 그런 사고로 수많은 비밀번호가 새어 나갔다."

### String과 &str — 두루마리의 두 얼굴

문자열관의 사서는 매우 지쳐 보였다.

### HashMap — 이름표의 마법

### 증거물 #16 — 해시맵과 Entry API

```rust
use std::collections::HashMap;

fn main() {
    let deliveries = [
        "섬의 역사", "항해술", "섬의 역사", "등대지기",
        "섬의 역사", "항해술", "컴파일러 연대기",
    ];

    // 각 책이 몇 번 배달됐는지 센다
    let mut count: HashMap<&str, usize> = HashMap::new();
    for book in deliveries {
        *count.entry(book).or_insert(0) += 1;
    }

    // HashMap은 순서가 없으니, 정렬해서 출력한다
    let mut sorted: Vec<_> = count.iter().collect();
    sorted.sort_by(|a, b| b.1.cmp(a.1).then(a.0.cmp(b.0)));
    for (book, n) in sorted {
        println!("{book}: {n}권");
    }

    // 조회
    match count.get("항해술") {
        Some(n) => println!("항해술은 {n}권"),
        None => println!("항해술 없음"),
    }

    // 그룹화: entry + or_default
    let mut by_len: HashMap<usize, Vec<&str>> = HashMap::new();
    for book in deliveries {
        by_len.entry(book.chars().count()).or_default().push(book);
    }
    println!("4글자 제목: {:?}", by_len.get(&4));
}
```

"`entry` API가 이 도서관의 비밀 무기예요." 해시맵관 사서가 자랑스럽게 말했다. "다른 섬에서는 '있는지 확인하고, 없으면 넣고, 있으면 꺼내서 고치고'를 따로 해야 했지만, 여기서는 `entry(키).or_insert(기본값)` 한 번이면 끝나요. 키를 두 번 찾지 않으니 빠르기도 하고요."

### 증거물 #17 — 클로저와 캡처

```rust
fn main() {
    let night_start = 22;

    // 주변 변수 night_start를 '빌려서' 기억한다
    let is_night = |hour: u32| hour >= night_start || hour < 5;
    println!("23시는 밤? {}", is_night(23));

    // 주변 변수를 '고치는' 클로저 → FnMut
    let mut suspicious_count = 0;
    let mut record = |hour: u32| {
        if hour >= 22 {
            suspicious_count += 1;
        }
    };
    record(23);
    record(10);
    record(2);
    println!("밤 10시 이후 배달: {suspicious_count}건");

    // move: 주변 변수의 소유권을 클로저 안으로 가져간다 → 스레드에서 필수
    let suspect = String::from("야간 배달원");
    let report = move || format!("용의자: {suspect}");
    println!("{}", report());
    // println!("{suspect}"); // ❌ suspect는 클로저로 이동했다
}
```

"클로저에는 세 종류가 있어. 무엇을 하느냐에 따라 컴파일러가 자동으로 정하지."

| 트레이트 | 캡처 방식 | 호출 횟수 |
|---|---|---|
| `Fn` | 불변으로 빌림 | 여러 번 |
| `FnMut` | 가변으로 빌림 | 여러 번 (단, `mut` 필요) |
| `FnOnce` | 소유권을 가져가서 소비 | **한 번만** |

### 증거물 #18 — 이터레이터 체인으로 범인 찾기

```rust
#[derive(Debug)]
struct Delivery {
    book: &'static str,
    courier: &'static str,
    hour: u32,
}

fn main() {
    let log = vec![
        Delivery { book: "섬의 역사", courier: "김씨", hour: 9 },
        Delivery { book: "섬의 역사", courier: "그림자", hour: 23 },
        Delivery { book: "항해술", courier: "박씨", hour: 14 },
        Delivery { book: "항해술", courier: "그림자", hour: 2 },
        Delivery { book: "등대지기", courier: "김씨", hour: 11 },
        Delivery { book: "섬의 역사", courier: "그림자", hour: 1 },
    ];

    // 1) 밤(22시~5시) 배달만 골라 배달원 이름만 뽑는다
    let night_couriers: Vec<&str> = log
        .iter()
        .filter(|d| d.hour >= 22 || d.hour < 5)
        .map(|d| d.courier)
        .collect();
    println!("밤 배달원: {night_couriers:?}");

    // 2) 모든 야간 배달이 같은 사람인가?
    let all_same = night_couriers.windows(2).all(|w| w[0] == w[1]);
    println!("모두 같은 사람? {all_same}");

    // 3) 위치와 함께: 몇 번째 기록인지
    for (i, d) in log.iter().enumerate().filter(|(_, d)| d.courier == "그림자") {
        println!("기록 #{i}: {} ({}시)", d.book, d.hour);
    }

    // 4) 집계: 배달 시각의 합, 최대값, 개수
    let total: u32 = log.iter().map(|d| d.hour).sum();
    let latest = log.iter().max_by_key(|d| (d.hour + 19) % 24);  // 오전 5시 기준 '가장 늦은'
    let shadow_count = log.iter().filter(|d| d.courier == "그림자").count();
    println!("시각 합 {total}, 가장 늦은 배달 {:?}, 그림자 {shadow_count}회", latest.map(|d| d.hour));

    // 5) 첫 번째로 조건을 만족하는 것
    let first_shadow = log.iter().position(|d| d.courier == "그림자");
    println!("그림자 첫 등장: {first_shadow:?}");

    // 6) 두 목록 묶기, 접기(fold)
    let hours: Vec<u32> = log.iter().map(|d| d.hour).collect();
    let summary = hours.iter().zip(log.iter()).fold(String::new(), |mut acc, (h, d)| {
        if !acc.is_empty() { acc.push_str(", "); }
        acc.push_str(&format!("{h}시:{}", d.courier));
        acc
    });
    println!("{summary}");
}
```

하랑은 출력을 보고 숨을 들이켰다.

```text
밤 배달원: ["그림자", "그림자", "그림자"]
모두 같은 사람? true
```

"야간 배달은 전부 '그림자'라는 배달원이었어요!"

"이터레이터 체인의 진짜 장점은 두 가지다." 보로가 말했다.

"첫째, **게으르다(lazy).** `filter`와 `map`은 아무것도 하지 않아. `collect`, `sum`, `count`처럼 결과를 요구하는 마지막 단계가 와야 비로소 데이터를 한 번 훑으며 모든 단계를 처리하지. 중간 목록을 만들지 않아."

"둘째, **빠르다.** 컴파일러가 이 체인을 손으로 짠 `for` 루프만큼, 때로는 그보다 더 빠른 기계어로 바꿔 놓는다. 추상화를 썼는데 비용이 들지 않는 것—이걸 **제로 코스트 추상화**라고 해. 제15장 법정에서 증거로 쓰일 개념이니 기억해 둬."

### 증거물 #19 — 커스텀 이터레이터

```rust
/// 시작 시각부터 일정 간격으로 순찰 시각을 만들어 낸다 (24시간제, 무한)
struct Patrol {
    hour: u32,
    step: u32,
}

impl Iterator for Patrol {
    type Item = u32;

    fn next(&mut self) -> Option<Self::Item> {
        let current = self.hour;
        self.hour = (self.hour + self.step) % 24;
        Some(current)
    }
}

fn main() {
    let patrol = Patrol { hour: 22, step: 3 };

    // 무한 이터레이터도 take로 잘라 쓰면 된다
    let schedule: Vec<u32> = patrol.take(8).collect();
    println!("순찰 시각: {schedule:?}");

    // 다른 이터레이터 메서드도 전부 공짜
    let night_patrols: Vec<u32> = Patrol { hour: 22, step: 3 }
        .take(8)
        .filter(|h| *h >= 22 || *h < 5)
        .collect();
    println!("야간 순찰: {night_patrols:?}");
}
```

> **단서 노트 — 제7장**
>
> - **`Vec<T>`**: 연속 메모리, 끝 추가/삭제 O(1). `v[i]`는 패닉 가능, `v.get(i)`는 `Option`.
> - **`String`** 은 소유·가변, **`&str`** 은 빌린 창문. 모두 UTF-8이므로 정수 인덱싱 불가. `chars()`, `char_indices()` 사용.
> - **`HashMap<K, V>`**: `entry(k).or_insert(v)` / `or_default()`로 조회와 삽입을 한 번에. 순서가 필요하면 `BTreeMap`.
> - **클로저**는 주변을 캡처한다. `Fn`(불변) / `FnMut`(가변) / `FnOnce`(소비). `move`로 소유권 이전.
> - **이터레이터**는 게으르고(lazy), 제로 코스트다. `iter()` / `iter_mut()` / `into_iter()`로 빌림 방식이 달라진다.
> - 핵심 어댑터: `map`, `filter`, `enumerate`, `zip`, `take`, `skip`, `chain`, `flat_map`, `windows`. 소비자: `collect`, `sum`, `count`, `fold`, `any`, `all`, `find`, `position`, `max_by_key`.
> - 커스텀 이터레이터: `Iterator` 구현 시 `type Item`과 `next()`만 정의하면 나머지 수십 개 메서드는 공짜.

### 탐정의 숙제

1. ★ 문장에서 각 단어의 출현 횟수를 세는 함수를 `HashMap`과 `entry`로 작성하라.
2. ★★ `Vec<i32>`에서 짝수만 골라 제곱한 뒤 합을 구하는 것을 `for` 루프 없이 한 줄의 이터레이터 체인으로 작성하라.
3. ★★★ 피보나치 수열을 만드는 `struct Fib`에 `Iterator`를 구현하고, "처음으로 1000을 넘는 피보나치 수"를 `find`로 구하라. `u64` 오버플로를 어떻게 처리할지도 고민하라. (힌트: `checked_add`가 `None`이면 `next`도 `None`.)

### 트레이트 — '할 수 있음'의 약속

"트레이트는 **행동의 약속**이다. '이 타입은 이런 메서드를 가지고 있다'는 계약서지. 다른 언어의 인터페이스와 비슷하지만, 훨씬 강력해."

### 증거물 #20 — 트레이트 정의와 구현

```rust
trait Dancer {
    // 반드시 구현해야 하는 메서드
    fn name(&self) -> String;
    fn signature_move(&self) -> String;

    // 기본 구현이 있는 메서드 (원하면 덮어쓸 수 있다)
    fn perform(&self) -> String {
        format!("{}이(가) {}을(를) 선보입니다!", self.name(), self.signature_move())
    }
}

struct Detective { name: String }
struct Crab;

impl Dancer for Detective {
    fn name(&self) -> String { self.name.clone() }
    fn signature_move(&self) -> String { String::from("논리의 왈츠") }
}

impl Dancer for Crab {
    fn name(&self) -> String { String::from("페리") }
    fn signature_move(&self) -> String { String::from("옆걸음 탱고") }
    fn perform(&self) -> String {
        format!("{}: 딸깍딸깍! {}!", self.name(), self.signature_move())  // 덮어쓰기
    }
}

fn main() {
    let boro = Detective { name: String::from("보로") };
    println!("{}", boro.perform());
    println!("{}", Crab.perform());
}
```

### 제네릭 — 누구든, 단 조건을 만족한다면

"무도회장 입구에서 문지기가 참석자를 검사해야 해." 보로가 말했다. "그런데 문지기 함수를 탐정용, 꽃게용, 시장용으로 따로 만들 거야?"

### 증거물 #21 — 제네릭과 트레이트 바운드

```rust
use std::fmt::Display;

trait Dancer {
    fn name(&self) -> String;
}

struct Detective;
struct Crab;
impl Dancer for Detective { fn name(&self) -> String { "보로".into() } }
impl Dancer for Crab { fn name(&self) -> String { "페리".into() } }

// 1) 꺾쇠 문법: T는 Dancer를 구현한 어떤 타입이든
fn admit<T: Dancer>(guest: &T) {
    println!("입장 허가: {}", guest.name());
}

// 2) impl Trait 문법: 위와 같은 의미, 더 짧다
fn admit_short(guest: &impl Dancer) {
    println!("입장 허가(간단): {}", guest.name());
}

// 3) where 절: 조건이 복잡할 때 읽기 좋게
fn announce<T, U>(guest: &T, title: U) -> String
where
    T: Dancer,
    U: Display,
{
    format!("[{title}] {}", guest.name())
}

// 4) 제네릭 구조체
struct Pair<T> {
    left: T,
    right: T,
}

impl<T: PartialOrd + Display> Pair<T> {
    fn larger(&self) -> &T {
        if self.left >= self.right { &self.left } else { &self.right }
    }
}

fn main() {
    admit(&Detective);
    admit_short(&Crab);
    println!("{}", announce(&Detective, "수석 탐정"));
    println!("{}", announce(&Crab, 2026));

    let p = Pair { left: 17, right: 42 };
    println!("더 큰 값: {}", p.larger());
    let q = Pair { left: "가면", right: "망토" };
    println!("사전순으로 뒤: {}", q.larger());
}
```

"제네릭 함수는 컴파일할 때 **실제로 쓰인 타입마다 따로 복사본이 만들어져.** `admit::<Detective>`와 `admit::<Crab>`이 별개의 기계어가 되는 거지. 이걸 **단형화(monomorphization)** 라고 한다. 실행할 때는 '이게 어떤 타입이지?' 하고 물어볼 필요가 전혀 없어. 그래서 빠르다. 대신 실행 파일이 조금 커질 수 있지."

### dyn Trait — 무도회장 안의 혼돈

무도회 당일 밤. 시청 대연회장에는 온갖 가면을 쓴 참석자들이 뒤섞여 있었다. 탐정, 꽃게, 시장, 악사…

"무도회장 명단을 만들어야 해요." 하랑이 말했다. "그런데 참석자들이 다 다른 타입이에요. `Vec<Detective>`에는 꽃게를 넣을 수 없고…"

"그럴 때는 **트레이트 객체**를 쓴다." 보로가 말했다. "`dyn Dancer`. '어떤 타입인지는 모르지만, 춤출 수 있는 무언가'라는 뜻이야."

### 증거물 #22 — 트레이트 객체와 동적 디스패치

```rust
trait Dancer {
    fn name(&self) -> String;
    fn dance(&self) -> String;
}

struct Detective;
struct Crab;
struct Mayor { years_in_office: u32 }

impl Dancer for Detective {
    fn name(&self) -> String { "탐정".into() }
    fn dance(&self) -> String { "논리의 왈츠".into() }
}
impl Dancer for Crab {
    fn name(&self) -> String { "꽃게".into() }
    fn dance(&self) -> String { "옆걸음 탱고".into() }
}
impl Dancer for Mayor {
    fn name(&self) -> String { format!("시장({}년차)", self.years_in_office) }
    fn dance(&self) -> String { "근엄한 미뉴에트".into() }
}

fn main() {
    // 서로 다른 타입들을 Box<dyn Dancer>로 한 목록에!
    let ballroom: Vec<Box<dyn Dancer>> = vec![
        Box::new(Detective),
        Box::new(Crab),
        Box::new(Mayor { years_in_office: 3 }),
    ];

    for guest in &ballroom {
        println!("{}: {}", guest.name(), guest.dance());
    }
}
```

"`Box<dyn Dancer>`는 두 개의 포인터로 되어 있어." 보로가 칠판에 그렸다.

```text
  Box<dyn Dancer>
 ┌──────────────┐        ┌──────────────┐
 │ data ptr  ───┼──────▶│  Mayor 데이터  │
 │ vtable ptr ──┼──┐     └──────────────┘
 └──────────────┘  │     ┌──────────────────────┐
                   └───▶│ vtable (Mayor용)        │
                         │  name  → Mayor::name   │
                         │  dance → Mayor::dance  │
                         │  drop  → Mayor::drop   │
                         └──────────────────────┘
```

"데이터를 가리키는 포인터 하나, 그리고 **그 타입의 메서드 목록표(vtable)** 를 가리키는 포인터 하나. 메서드를 부를 때마다 목록표를 보고 찾아가지. 이걸 **동적 디스패치**라고 한다. 약간 느리지만, 실행 중에 타입이 정해지는 유연함을 얻는다."

| | 제네릭 `<T: Trait>` / `impl Trait` | 트레이트 객체 `dyn Trait` |
|---|---|---|
| 디스패치 | 정적 (컴파일 시점) | 동적 (실행 시점, vtable) |
| 속도 | 가장 빠름, 인라인 가능 | 간접 호출 비용 |
| 서로 다른 타입 섞기 | 불가 | **가능** (`Vec<Box<dyn T>>`) |
| 코드 크기 | 타입마다 복사본 | 하나 |
| 언제 | 기본 선택 | 이질적 컬렉션, 플러그인, 실행 시점 선택 |

### 고급 트레이트 기술

그날 밤, 사무소로 돌아온 보로는 트레이트의 숨겨진 기술들을 하랑에게 전수했다.

### 증거물 #23 — 연관 타입, 연산자 오버로딩, 표준 트레이트

```rust
use std::fmt;
use std::ops::Add;

// 1) 연산자 오버로딩: + 를 정의한다
#[derive(Debug, Clone, Copy, PartialEq)]
struct Evidence { weight: u32 }

impl Add for Evidence {
    type Output = Evidence;          // 연관 타입: '더하면 무엇이 되는가'
    fn add(self, other: Evidence) -> Evidence {
        Evidence { weight: self.weight + other.weight }
    }
}

// 2) Display: 사람이 읽는 출력 형식 ({})
impl fmt::Display for Evidence {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "증거 가중치 {}점", self.weight)
    }
}

// 3) From/Into: 타입 변환
impl From<u32> for Evidence {
    fn from(weight: u32) -> Self { Evidence { weight } }
}

// 4) Default: 기본값
#[derive(Debug, Default)]
struct CaseFile {
    title: String,
    priority: u8,
    closed: bool,
}

// 5) 연관 타입을 가진 나만의 트레이트
trait Investigator {
    type Clue;                                   // 구현하는 쪽이 정한다
    fn investigate(&self) -> Vec<Self::Clue>;
}

struct ForensicLab;
impl Investigator for ForensicLab {
    type Clue = (String, f64);                   // (증거명, 신뢰도)
    fn investigate(&self) -> Vec<Self::Clue> {
        vec![("지문".into(), 0.97), ("섬유".into(), 0.62)]
    }
}

// 6) 슈퍼트레이트: Display를 구현한 타입만 Reportable이 될 수 있다
trait Reportable: fmt::Display {
    fn headline(&self) -> String {
        format!("[속보] {self}")
    }
}
impl Reportable for Evidence {}

fn main() {
    let a = Evidence { weight: 30 };
    let b: Evidence = 45.into();                 // From 덕분에 into()가 공짜
    let total = a + b;
    println!("{total}");
    println!("{}", total.headline());

    let case = CaseFile { title: "무도회 사건".into(), ..Default::default() };
    println!("{case:?}");

    for (clue, confidence) in ForensicLab.investigate() {
        println!("{clue}: 신뢰도 {:.0}%", confidence * 100.0);
    }
}
```

"표준 라이브러리에는 꼭 알아야 할 트레이트들이 있다." 보로가 목록을 적었다.

| 트레이트 | 역할 | derive 가능? |
|---|---|---|
| `Debug` | `{:?}` 디버그 출력 | O |
| `Display` | `{}` 사용자용 출력 | X (직접 구현) |
| `Clone` / `Copy` | 복제 / 암묵적 복사 | O |
| `PartialEq` / `Eq` | `==` 비교 | O |
| `PartialOrd` / `Ord` | `<`, 정렬 | O |
| `Hash` | `HashMap` 키로 쓰기 | O |
| `Default` | 기본값 | O |
| `From` / `Into` | 타입 변환 | X |
| `AsRef` / `Borrow` | 저렴한 참조 변환 | X |
| `Iterator` / `IntoIterator` | `for` 루프 지원 | X |
| `Drop` | 소멸 시 동작 | X |
| `Deref` | `*`와 자동 역참조 | X |
| `Send` / `Sync` | 스레드 안전성 표식 | 자동 |

"그리고 하나 더. **고아 규칙(orphan rule)**. 트레이트를 구현하려면, 트레이트나 타입 중 **적어도 하나는 네 크레이트 것**이어야 해. 남의 타입에 남의 트레이트를 구현할 수는 없지. 서로 다른 두 크레이트가 같은 구현을 만들어 충돌하는 걸 막기 위해서다. 이 규칙을 우회하는 방법은 제12장의 '뉴타입 패턴'에서 배운다."

> **단서 노트 — 제8장**
>
> - **트레이트**는 행동의 계약이다. 기본 구현을 가질 수 있다.
> - **제네릭 + 트레이트 바운드**(`T: Trait`, `impl Trait`, `where`)는 **정적 디스패치**. 단형화로 빠르다.
> - **트레이트 객체**(`&dyn Trait`, `Box<dyn Trait>`)는 **동적 디스패치**. vtable을 통해 서로 다른 타입을 한 컬렉션에 담을 수 있다.
> - **연관 타입**(`type Item;`)은 "구현마다 하나로 정해지는 타입"에 쓴다. 제네릭 매개변수는 "여러 번 구현 가능"할 때.
> - 연산자 오버로딩은 `std::ops`의 트레이트(`Add`, `Mul`, `Index` …)로 한다.
> - **고아 규칙**: 트레이트나 타입 중 하나는 내 크레이트 소속이어야 한다.
> - 타입 시스템은 "할 수 있음"을 보증하지만 "올바르게 함"은 테스트와 문서의 몫이다.

### 탐정의 숙제

1. ★ `trait Area { fn area(&self) -> f64; }`를 정의하고 `Circle`, `Square`에 구현한 뒤, `Vec<Box<dyn Area>>`의 넓이 합을 구하라.
2. ★★ 2차원 벡터 `struct V2 { x: f64, y: f64 }`에 `Add`, `Sub`, `Mul<f64>`(스칼라 곱)를 구현하라.
3. ★★★ `fn largest<T: PartialOrd>(items: &[T]) -> Option<&T>`를 작성하라. 바운드를 `T: PartialOrd + Copy`로 바꿔 `Option<T>`를 반환하는 버전과 비교해 장단점을 설명하라. 그리고 `f64`의 `NaN` 때문에 `Ord`가 아니라 `PartialOrd`만 구현된 이유를 조사하라.

# 제9장 — 스마트 포인터 저택

섬의 동쪽 언덕 위에는 아무도 살지 않는 오래된 저택이 있었다. 사람들은 그곳을 **스마트 포인터 저택**이라고 불렀다. 저택의 방들은 서로 복도로 이어져 있었는데, 어떤 방은 여러 복도가 동시에 가리키고 있었고, 어떤 방은 자기 자신을 가리키는 복도도 있다고 했다.

"저택의 관리인이 실종됐어." 보로가 말했다. "마지막으로 목격된 건 사흘 전. 저택 안으로 들어가는 모습이었다. 그런데 나오는 모습은 아무도 못 봤지."

저택의 대문을 열자, 현관에 네 개의 상자가 놓여 있었다. 상자마다 이름표가 붙어 있었다.

`Box` · `Rc` · `RefCell` · `Weak`

"저택의 열쇠들이다." 보로가 말했다. "하나씩 이해하지 못하면, 우리도 관리인처럼 이 안에서 길을 잃을 거야."

### Box — 힙에 놓인 상자

"첫 번째 방. `Box<T>`."

### 증거물 #24 — Box와 재귀 타입

```rust
// 저택의 복도 지도: 방 → 다음 방 → ... → 막다른 길
#[derive(Debug)]
enum Corridor {
    Room(String, Box<Corridor>),   // Box 없이는 크기를 알 수 없다!
    DeadEnd,
}

use Corridor::{DeadEnd, Room};

fn count_rooms(c: &Corridor) -> usize {
    match c {
        Room(_, next) => 1 + count_rooms(next),
        DeadEnd => 0,
    }
}

fn main() {
    // 1) 큰 데이터를 힙으로 옮기기
    let big_archive = Box::new([0u8; 1024]);
    println!("기록 보관소 크기: {}바이트 (스택에는 포인터 하나만)", big_archive.len());

    // 2) 재귀 타입
    let map = Room(
        "현관".into(),
        Box::new(Room("응접실".into(), Box::new(Room("서재".into(), Box::new(DeadEnd))))),
    );
    println!("{map:?}");
    println!("방 개수: {}", count_rooms(&map));
}
```

"`Box` 없이 `Room(String, Corridor)`라고 쓰면, 컴파일러는 `Corridor`의 크기를 계산하다가 무한히 빠져들어. 방 안에 복도가 있고, 그 복도 안에 방이 있고… 끝이 없지. `Box`는 **크기가 정해진 포인터 하나**니까 이 무한의 고리를 끊어 준다."

> **컴파일러의 증언 (Box를 뺐을 때)**
>
> ```text
> error[E0072]: recursive type `Corridor` has infinite size
> help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
> ```

"`Box`를 쓰는 때는 세 가지야. 재귀 타입, 큰 데이터를 옮길 때 복사를 피하고 싶을 때, 그리고 제8장의 `Box<dyn Trait>`처럼 **크기를 모르는 타입**을 다룰 때."

### Rc — 여러 명이 함께 가진 방

두 번째 방에 들어서자, 벽에 걸린 그림 한 점이 보였다. 그 그림 아래에는 세 개의 명패가 붙어 있었다. '응접실 소유', '서재 소유', '복도 소유'.

"그림 한 점을 세 방이 함께 소유하고 있어요." 하랑이 말했다. "그런데 소유권은 한 명만 가질 수 있다면서요?"

"그래서 `Rc<T>`가 있다. **Reference Counted**, 참조 카운트. 소유자가 몇 명인지 **세는** 상자야. 마지막 소유자가 떠날 때 비로소 그림이 치워지지."

### 증거물 #25 — Rc와 공유 소유

```rust
use std::rc::Rc;

#[derive(Debug)]
struct Painting { title: String }

impl Drop for Painting {
    fn drop(&mut self) {
        println!("  [철거] 그림 '{}'이(가) 치워졌다", self.title);
    }
}

fn main() {
    let painting = Rc::new(Painting { title: "등대의 밤".into() });
    println!("소유자 수: {}", Rc::strong_count(&painting));    // 1

    let parlor = Rc::clone(&painting);   // 데이터 복제가 아니라 '카운트 +1'
    let study = Rc::clone(&painting);
    println!("소유자 수: {}", Rc::strong_count(&painting));    // 3
    println!("응접실이 보는 그림: {}", parlor.title);

    drop(parlor);
    println!("응접실 퇴장 후: {}", Rc::strong_count(&painting)); // 2
    drop(study);
    println!("서재 퇴장 후: {}", Rc::strong_count(&painting));   // 1
    println!("main 끝");
}   // 마지막 소유자 painting이 떠나면서 그림이 치워진다
```

"`Rc::clone`은 그림을 복제하지 않아. 카운트만 하나 올리지. 그래서 아주 싸다. 관례적으로 `painting.clone()` 대신 `Rc::clone(&painting)`이라고 써서 '이건 깊은 복사가 아니다'를 드러내는 사람이 많아."

"이게 댕글링이 말한 거군요." 하랑이 말했다. "생각 없이 `clone`하지 말고, 진짜 공유가 필요하면 그에 맞는 도구를 쓰라고."

"단, `Rc`에는 두 가지 제약이 있다. 하나, 안의 데이터는 **읽기만** 할 수 있어. 여럿이 함께 가진 걸 아무나 고치면 안 되니까. 둘, **한 스레드 안에서만** 쓸 수 있어. 카운트를 세는 방식이 스레드 안전하지 않거든. 스레드 사이에서는 `Arc`를 쓴다. 다음 장에서 보게 될 거다."

### RefCell — 규칙을 실행 시간에 검사하는 방

세 번째 방은 이상한 방이었다. 문에는 이렇게 적혀 있었다.

> *이 방에서는 빌림 검사관이 문 앞에 서지 않는다.*
> *대신 방 안의 경비원이 들어오는 사람을 하나하나 센다.*
> *규칙을 어기면, 그 자리에서 쓰러질 것이다.*

"`RefCell<T>`." 보로가 낮게 말했다. "**내부 가변성(interior mutability)** 의 방이다. 바깥에서는 불변으로 보이지만, 안에서는 고칠 수 있지. 단, 빌림의 법칙은 사라지지 않아. **컴파일 시점이 아니라 실행 시점에** 검사할 뿐이다."

### 증거물 #26 — RefCell과 실행 시간 빌림 검사

```rust
use std::cell::RefCell;

struct GuestBook {
    entries: RefCell<Vec<String>>,   // &self로도 고칠 수 있게
}

impl GuestBook {
    // &self인데도 기록을 추가할 수 있다!
    fn sign(&self, name: &str) {
        self.entries.borrow_mut().push(name.to_string());
    }

    fn count(&self) -> usize {
        self.entries.borrow().len()
    }
}

fn main() {
    let book = GuestBook { entries: RefCell::new(Vec::new()) };
    book.sign("관리인");
    book.sign("정체불명의 방문객");
    println!("방명록 {}명", book.count());

    // 규칙을 어기면? → 실행 시간 패닉 대신 try_borrow로 확인할 수 있다
    let reading = book.entries.borrow();
    match book.entries.try_borrow_mut() {
        Ok(_) => println!("쓰기 가능"),
        Err(_) => println!("누군가 읽는 중이라 쓸 수 없음! (그냥 borrow_mut였다면 패닉)"),
    }
    drop(reading);
    println!("이제 쓰기 가능? {}", book.entries.try_borrow_mut().is_ok());
}
```

"`RefCell`은 탈출구가 아니야. **약속을 미루는 것**이지. 컴파일러가 증명할 수 없지만, 네가 '실행할 때는 절대 겹치지 않는다'고 확신할 때만 써야 한다. 확신이 틀리면 프로그램은 패닉으로 쓰러진다."

| 타입 | 검사 시점 | 용도 |
|---|---|---|
| `&T` / `&mut T` | 컴파일 | 기본 |
| `Cell<T>` | (검사 없음, 값 통째로 교체) | `Copy` 타입의 작은 값 |
| `RefCell<T>` | 실행 (단일 스레드) | 공유된 값을 가끔 고칠 때 |
| `Mutex<T>` / `RwLock<T>` | 실행 (멀티 스레드, 잠금) | 스레드 간 공유 수정 |

### Rc<RefCell<T>> — 여럿이 함께 갖고, 함께 고치기

"`Rc`는 공유하지만 고칠 수 없고, `RefCell`은 고칠 수 있지만 공유는 못 하고…" 하랑이 중얼거렸다. "둘을 합치면요?"

"바로 그거다. `Rc<RefCell<T>>`. 단일 스레드에서 '여럿이 함께 가지면서 고칠 수도 있는' 데이터를 만드는 표준 조합이지."

### 순환 참조 — 관리인은 어디에

네 번째 방. 마지막 상자 `Weak`가 놓인 방에서, 그들은 마침내 관리인의 흔적을 찾았다. 벽에 남은 쪽지였다.

> *"방 A는 방 B를 가리키고, 방 B는 방 A를 가리킨다.*
> *둘 다 서로를 놓지 않는다. 그래서 둘 다 사라지지 않는다.*
> *나는 이 저택의 메모리에서 나갈 수 없다."*

"순환 참조…" 보로의 얼굴이 굳었다.

### 증거물 #27 — 메모리 누수를 만드는 순환

```rust
use std::cell::RefCell;
use std::rc::Rc;

struct Room {
    name: String,
    next: RefCell<Option<Rc<Room>>>,
}

impl Drop for Room {
    fn drop(&mut self) {
        println!("  [정리] 방 '{}'", self.name);
    }
}

fn main() {
    let a = Rc::new(Room { name: "A".into(), next: RefCell::new(None) });
    let b = Rc::new(Room { name: "B".into(), next: RefCell::new(None) });

    *a.next.borrow_mut() = Some(Rc::clone(&b));   // A → B
    *b.next.borrow_mut() = Some(Rc::clone(&a));   // B → A  (순환!)

    println!("A의 소유자 수: {}", Rc::strong_count(&a));   // 2
    println!("B의 소유자 수: {}", Rc::strong_count(&b));   // 2
    println!("main 끝 — 그런데 '[정리]' 메시지가 나오지 않는다...");
}
```

```text
A의 소유자 수: 2
B의 소유자 수: 2
main 끝 — 그런데 '[정리]' 메시지가 나오지 않는다...
```

"`main`이 끝날 때 변수 `a`와 `b`가 사라지면서 카운트가 각각 1씩 줄어. 하지만 여전히 1이야. A는 B가, B는 A가 붙잡고 있으니까. 카운트는 영원히 0이 되지 않고, 두 방은 **영원히 메모리에 남는다.** 이게 **메모리 누수**다."

"잠깐만요, 러스트는 메모리 안전하다면서요!"

"메모리 **안전**과 메모리 **누수 없음**은 달라." 보로가 말했다. "누수된 메모리는 낭비일 뿐, 위험하지는 않아. 아무도 그걸 잘못 읽거나 쓰지 않으니까. 그래서 러스트는 누수를 '안전하지 않은 일'로 보지 않는다. 하지만 좋은 탐정이라면 막아야지."

### Weak — 붙잡지 않고 가리키기

"해결책은 `Weak<T>`다. **약한 참조.** 가리키긴 하지만 소유하지는 않아. 카운트를 올리지 않으니 순환이 생겨도 누수가 없지. 대신 쓸 때마다 '아직 살아 있나?' 확인해야 해."

### 증거물 #28 — Weak로 부모-자식 트리 만들기

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    name: String,
    parent: RefCell<Weak<Node>>,          // 부모는 약하게 (소유 X)
    children: RefCell<Vec<Rc<Node>>>,     // 자식은 강하게 (소유 O)
}

impl Node {
    fn new(name: &str) -> Rc<Node> {
        Rc::new(Node {
            name: name.into(),
            parent: RefCell::new(Weak::new()),
            children: RefCell::new(vec![]),
        })
    }

    fn add_child(parent: &Rc<Node>, child: Rc<Node>) {
        *child.parent.borrow_mut() = Rc::downgrade(parent);
        parent.children.borrow_mut().push(child);
    }
}

impl Drop for Node {
    fn drop(&mut self) {
        println!("  [정리] {}", self.name);
    }
}

fn main() {
    let mansion = Node::new("저택");
    let attic = Node::new("다락방");
    Node::add_child(&mansion, Rc::clone(&attic));

    // 자식에서 부모로 올라가기: upgrade()는 Option<Rc<T>>
    match attic.parent.borrow().upgrade() {
        Some(p) => println!("다락방의 부모: {}", p.name),
        None => println!("부모가 이미 사라짐"),
    }

    println!("저택 strong={}, weak={}", Rc::strong_count(&mansion), Rc::weak_count(&mansion));
    println!("다락방 strong={}", Rc::strong_count(&attic));

    drop(mansion);
    println!("저택을 놓은 뒤, 다락방의 부모: {:?}",
             attic.parent.borrow().upgrade().map(|p| p.name.clone()));
    println!("main 끝");
}
```

```text
다락방의 부모: 저택
저택 strong=1, weak=1
다락방 strong=2
  [정리] 저택
저택을 놓은 뒤, 다락방의 부모: None
main 끝
  [정리] 다락방
```

"부모는 자식을 **강하게** 소유하고, 자식은 부모를 **약하게** 기억한다." 보로가 말했다. "트리, 그래프, GUI 위젯, 관찰자 패턴… 서로를 가리켜야 하는 모든 구조에서 쓰이는 원칙이다."

하랑과 보로가 순환을 끊자, 저택 어딘가에서 '딸깍' 소리가 났다. 그리고 지하로 통하는 문이 열렸다. 그 안에서 관리인이 비틀거리며 걸어 나왔다.

"사흘 동안… 메모리 속을 맴돌았어요." 관리인이 말했다. "검은 망토를 쓴 자가 방 두 개를 서로 묶어 놓고 사라졌어요. 그러면서 이렇게 말했죠. '다음은 쌍둥이 차례다'라고."

> **단서 노트 — 제9장**
>
> - **`Box<T>`**: 힙 할당, 단일 소유. 재귀 타입, 큰 데이터, `dyn Trait`에 사용.
> - **`Rc<T>`**: 참조 카운트로 **공유 소유**(단일 스레드). `Rc::clone`은 카운트만 증가. 내용은 불변.
> - **`RefCell<T>`**: **내부 가변성**. 빌림 규칙을 **실행 시점**에 검사. 위반 시 패닉(`try_borrow*`로 회피 가능).
> - **`Cell<T>`**: `Copy` 값의 교체용. 참조를 꺼내지 않으니 패닉도 없다.
> - **`Rc<RefCell<T>>`**: 단일 스레드에서 공유+수정. 멀티 스레드에서는 **`Arc<Mutex<T>>`**.
> - `Rc` 순환은 **메모리 누수**를 만든다. 누수는 "불안전"이 아니지만 피해야 한다.
> - **`Weak<T>`**: 소유하지 않는 참조. `upgrade()`로 `Option<Rc<T>>`를 얻는다. 부모 포인터, 캐시, 관찰자에 사용.

### 탐정의 숙제

1. ★ `Rc<String>`을 세 변수가 공유하게 한 뒤, 각 시점의 `strong_count`를 예측하고 실행해 확인하라.
2. ★★ `Rc<RefCell<Vec<i32>>>`를 두 개의 '관찰자'가 공유하고, 한쪽에서 추가한 값이 다른 쪽에서 보이는 것을 확인하라.
3. ★★★ 이중 연결 리스트(doubly linked list)를 `Rc`/`Weak`/`RefCell`로 구현하라. `next`는 `Option<Rc<...>>`, `prev`는 `Option<Weak<...>>`. 왜 반대로 하면 안 되는지도 설명하라. (도전 정신이 있다면, 왜 러스트 커뮤니티에서 "연결 리스트는 러스트 입문용으로 최악"이라는 농담이 있는지 생각해 보라.)

# 제10장 — 레이스 쌍둥이의 금고

은행의 지하 금고. 잔액이 맞지 않았다.

"백만 원을 두 번 입금했는데, 잔액이 백만 원만 늘었어요." 은행장이 땀을 흘리며 말했다. "기록에는 분명히 두 번 입금됐다고 나와 있는데요."

"두 번의 입금이 **동시에** 일어났나요?" 하랑이 물었다.

은행장이 고개를 끄덕였다. "창구 두 곳에서 정확히 같은 순간에요. 그리고 그 두 창구에 있던 손님은… 똑같이 생긴 쌍둥이였어요."

"레이스 쌍둥이." 보로가 낮게 말했다. "다른 섬에서 수십 년 동안 잡히지 않은 도둑들이다. 증거를 남기지 않거든. 매번 결과가 다르고, 재현도 안 돼."

### 데이터 경쟁 — 쌍둥이의 수법

보로가 칠판에 그렸다.

```text
  잔액 = 0

  창구 1 (쌍둥이 A)              창구 2 (쌍둥이 B)
  ──────────────────           ──────────────────
  1. 잔액 읽기 → 0
                                2. 잔액 읽기 → 0
  3. 0 + 100만 계산
                                4. 0 + 100만 계산
  5. 잔액 쓰기 ← 100만
                                6. 잔액 쓰기 ← 100만

  최종 잔액 = 100만  (200만이어야 하는데!)
```

"두 스레드가 같은 데이터를 **동시에** 읽고 쓸 때, 순서가 꼬이면 한쪽의 작업이 사라진다. 이게 **데이터 경쟁(data race)** 이다. 실행할 때마다 순서가 달라지니까 어떨 땐 맞고 어떨 땐 틀리지. 그래서 잡기가 그토록 어려웠던 거야."

"그럼 이 섬에서는요?"

"이 섬에서는…" 보로가 미소를 지었다. "쌍둥이가 **애초에 금고에 접근할 수 없다.**"

### 스레드 — 동시에 일하는 탐정들

### 증거물 #29 — 스레드 만들기

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let mut handles = Vec::new();

    for id in 1..=3 {
        // move: id를 스레드 안으로 가져간다
        let handle = thread::spawn(move || {
            for step in 1..=2 {
                println!("  탐정 {id}: {step}단계 수사 중");
                thread::sleep(Duration::from_millis(10));
            }
            id * 100   // 스레드의 반환값
        });
        handles.push(handle);
    }

    // join: 스레드가 끝날 때까지 기다리고 결과를 받는다
    let results: Vec<i32> = handles.into_iter().map(|h| h.join().unwrap()).collect();
    println!("수사 결과: {results:?}");
}
```

"스레드 안으로 들어가는 클로저에는 거의 항상 `move`가 필요해. 새 스레드가 **언제까지 살지** 모르니까, 바깥 변수를 빌려 가는 건 위험하지. 소유권째 가져가야 한다. 제4장에서 말한 `'static` 조건이 바로 여기서 등장하는 거다."

### 컴파일러가 쌍둥이를 막는 방법

하랑은 쌍둥이의 수법을 그대로 러스트로 옮겨 보았다.

```rust
use std::thread;

fn main() {
    let mut balance = 0;
    let a = thread::spawn(|| { balance += 1_000_000; });   // ❌ 컴파일 에러
    let b = thread::spawn(|| { balance += 1_000_000; });
    a.join().unwrap();
    b.join().unwrap();
    println!("{balance}");
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0499]: cannot borrow `balance` as mutable more than once at a time
> error[E0373]: closure may outlive the current function, but it borrows `balance`,
>               which is owned by the current function
> ```

"두 스레드가 동시에 `&mut balance`를 가지려 하니까 막혔어요!" 하랑이 외쳤다. "제3장의 빌림 법칙이요! 가변 참조는 단 하나만!"

"그렇다. 같은 규칙이 스레드에서도 그대로 적용돼. 이 섬에서 데이터 경쟁이 **컴파일조차 되지 않는** 이유지. 이걸 사람들은 **'겁 없는 동시성(Fearless Concurrency)'** 이라고 부른다."

---

### Arc와 Mutex — 금고를 지키는 방법

"그럼 진짜로 두 창구에서 입금을 받아야 하면요?"

"두 가지가 필요해. 여러 스레드가 함께 소유할 수 있는 `Arc`(Atomic Rc), 그리고 한 번에 한 명만 금고를 열게 하는 `Mutex`(상호 배제 잠금)."

### 증거물 #30 — Arc<Mutex<T>>로 안전한 공유

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let vault = Arc::new(Mutex::new(0u64));   // 금고: 공유 + 잠금
    let mut tellers = vec![];

    for teller_id in 0..10 {
        let vault = Arc::clone(&vault);       // 스레드마다 소유권 하나씩
        tellers.push(thread::spawn(move || {
            for _ in 0..1000 {
                let mut balance = vault.lock().unwrap();   // 잠금 획득 (다른 스레드는 대기)
                *balance += 1;
            }   // ← balance(MutexGuard)가 drop되면서 자동으로 잠금 해제!
            teller_id
        }));
    }

    for t in tellers {
        t.join().unwrap();
    }

    println!("최종 잔액: {}", *vault.lock().unwrap());   // 언제나 정확히 10000
}
```

"`lock()`이 돌려주는 `MutexGuard`가 핵심이다." 보로가 말했다. "이 가드가 살아 있는 동안만 금고 안을 만질 수 있고, 가드가 범위를 벗어나는 순간 **자동으로** 잠금이 풀려. 잠금을 풀어야 한다는 걸 잊을 수가 없지. 제2장에서 말한 RAII가 여기서 빛을 발하는 거다."

"그리고 가장 중요한 점. **`Mutex` 안의 데이터는 잠금 없이는 꺼낼 방법이 아예 없다.** 다른 섬에서는 잠금과 데이터가 따로 있어서, 잠금을 깜빡하고 데이터를 만지는 사고가 끊이지 않았어. 여기서는 데이터가 잠금 **안에** 들어 있지."

---

### Send와 Sync — 보이지 않는 통행증

"그런데 컴파일러는 어떻게 알아요? `Rc`는 스레드에 못 보내고 `Arc`는 된다는 걸요."

"모든 타입에는 보이지 않는 통행증 두 장이 붙어 있어."

> - **`Send`**: 이 타입의 **소유권**을 다른 스레드로 **보내도** 안전하다.
> - **`Sync`**: 이 타입의 **참조**(`&T`)를 여러 스레드가 **동시에 가져도** 안전하다.

"이 통행증은 컴파일러가 **자동으로** 발급한다. 구성 요소가 전부 `Send`면 그 타입도 `Send`가 되지. `Rc`는 카운트를 원자적이지 않은 방식으로 세니까 `Send`도 `Sync`도 아니야. 그래서 `Rc`를 `thread::spawn`에 넣으면—"

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let shared = Rc::new(42);
    thread::spawn(move || println!("{shared}"));   // ❌ 컴파일 에러
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0277]: `Rc<i32>` cannot be sent between threads safely
>   = help: within `{closure}`, the trait `Send` is not implemented for `Rc<i32>`
> ```

"쌍둥이가 `Rc`라는 위조 통행증을 들고 다른 창구로 넘어가려다가 국경에서 걸린 셈이지."

| 타입 | `Send` | `Sync` | 비고 |
|---|---|---|---|
| `i32`, `String`, `Vec<T>` | O | O | (T가 그렇다면) |
| `Rc<T>` | X | X | 단일 스레드 전용 |
| `Arc<T>` | O | O | T가 `Send + Sync`일 때 |
| `RefCell<T>` | O | **X** | 동시 참조 불가 |
| `Mutex<T>` | O | O | T가 `Send`일 때 |
| `MutexGuard<T>` | **X** | O | 잠근 스레드에서 풀어야 함 |

### 채널 — 메시지로 대화하기

"공유 메모리가 아닌 다른 방법도 있다." 보로가 말했다. "아예 데이터를 공유하지 않고, **메시지를 주고받는** 거야."

> *"메모리를 공유하여 소통하지 말고, 소통하여 메모리를 공유하라."*

### 증거물 #31 — 채널로 수사 보고 모으기

```rust
use std::sync::mpsc;
use std::thread;

#[derive(Debug)]
enum Report {
    Clue { from: u32, text: String },
    Done(u32),
}

fn main() {
    let (tx, rx) = mpsc::channel::<Report>();   // 송신기, 수신기

    for detective in 1..=3 {
        let tx = tx.clone();                    // 송신기는 복제 가능 (multi-producer)
        thread::spawn(move || {
            tx.send(Report::Clue { from: detective, text: format!("{detective}번 구역 이상 무") }).unwrap();
            tx.send(Report::Done(detective)).unwrap();
        });
    }
    drop(tx);   // 원본 송신기를 닫아야 수신 루프가 끝난다

    // 모든 송신기가 사라질 때까지 받는다
    let mut finished = 0;
    for report in rx {
        match report {
            Report::Clue { from, text } => println!("[{from}번 탐정] {text}"),
            Report::Done(_) => finished += 1,
        }
    }
    println!("보고 완료한 탐정: {finished}명");
}
```

### 범위 스레드와 RwLock

"`Arc`를 쓰지 않고도 스레드에 빌려줄 수 있는 방법이 있다." 보로가 하나 더 보여 주었다. "`thread::scope`. 범위가 끝나기 전에 모든 스레드가 **반드시** 끝난다는 걸 컴파일러가 아니까, 지역 변수를 그냥 빌려줄 수 있지."

### 증거물 #32 — scope와 RwLock

```rust
use std::sync::RwLock;
use std::thread;

fn main() {
    let evidence = vec![3, 1, 4, 1, 5, 9, 2, 6, 5, 3];
    let case_notes = RwLock::new(Vec::<String>::new());   // 읽기 여럿 / 쓰기 하나

    // 증거를 반으로 나눠 두 스레드가 '빌려서' 분석 — Arc 불필요!
    let (left, right) = evidence.split_at(evidence.len() / 2);

    thread::scope(|s| {

        s.spawn(|| {
            let sum: i32 = left.iter().sum();
            case_notes.write().unwrap().push(format!("왼쪽 합계 {sum}"));
        });
        s.spawn(|| {
            let max = right.iter().max().unwrap();
            case_notes.write().unwrap().push(format!("오른쪽 최댓값 {max}"));
        });
        s.spawn(|| {
            // 읽기 잠금은 여러 스레드가 동시에 가질 수 있다
            let n = case_notes.read().unwrap().len();
            println!("(중간 점검) 현재 메모 {n}개");
        });
    }); // ← 여기서 모든 스레드가 끝났음이 보장된다

    let mut notes = case_notes.into_inner().unwrap();
    notes.sort();
    println!("최종 수사 메모: {notes:?}");
}
```

### 교착 상태 — 이 섬도 막지 못하는 것

쌍둥이 사건이 해결되는 듯했던 그날 밤, 은행에서 또 다른 신고가 들어왔다. 이번엔 금고 두 개가 **완전히 멈춰 버렸다**는 것이었다.

```text
  쌍둥이 A: 금고 1을 잠금 → 금고 2를 기다림...
  쌍둥이 B: 금고 2를 잠금 → 금고 1을 기다림...
  (둘 다 영원히 기다린다)
```

"교착 상태(deadlock)." 보로의 목소리가 무거워졌다. "이건 러스트도 컴파일 시점에 막지 못해. 데이터 경쟁은 막지만, 잠금을 거는 **순서**가 꼬이는 것까지는 증명할 수 없거든."

"그럼 어떻게 해요?"

"규칙을 정하는 거다. **항상 같은 순서로 잠근다.** 금고 1 다음에 금고 2. 절대 거꾸로 하지 않는다. 잠금은 짧게 쥐고 빨리 놓는다. 잠근 채로 다른 잠금을 기다리지 않는다. 그리고 가능하면 공유 상태 대신 **채널**을 쓴다."

은행의 모든 창구에 '금고 1 → 금고 2' 순서 규칙이 붙자, 쌍둥이는 더 이상 금고를 멈추게 할 수 없었다. 다음 날 아침, 은행 앞에서 쌍둥이 중 한 명이 경찰에 붙잡혔다. 그는 체념한 듯 말했다.

"우린 그냥 고용된 거예요. 진짜 주인은… 우리한테 이렇게만 말했어요. '이 섬의 컴파일러가 볼 수 없는 곳이 딱 하나 있다. 지하실이다.'"

> **단서 노트 — 제10장**
>
> - **`thread::spawn(move || ...)`** 로 스레드 생성, **`join()`** 으로 대기 및 결과 수신.
> - **데이터 경쟁**은 빌림 규칙 때문에 **컴파일되지 않는다**. (Fearless Concurrency)
> - **`Arc<T>`**: 스레드 간 공유 소유(원자적 카운트). **`Mutex<T>`**: 상호 배제. **`RwLock<T>`**: 다중 읽기/단일 쓰기.
> - `MutexGuard`는 RAII. 범위를 벗어나면 자동 해제. 데이터는 잠금 **안에** 있으므로 잠금 없이 접근 불가.
> - **`Send`**(소유권 이동 가능), **`Sync`**(공유 참조 가능)는 자동 구현되는 마커 트레이트.
> - **채널**(`mpsc::channel`)로 메시지 전달. 모든 송신기가 drop되면 수신 루프가 끝난다.
> - **`thread::scope`** 로 지역 데이터를 스레드에 빌려줄 수 있다.
> - **교착 상태**는 러스트도 막지 못한다. 잠금 순서를 일정하게, 잠금 범위는 짧게.
> - 단순 카운터라면 `AtomicU64` 같은 **원자 타입**이 `Mutex`보다 가볍다. 데이터 병렬 처리에는 `rayon` 크레이트(`par_iter()`)가 강력하다.

### 탐정의 숙제

1. ★ 증거물 #30을 `Mutex<u64>` 대신 `std::sync::atomic::AtomicU64`와 `fetch_add`로 바꿔라.
2. ★★ 1부터 1,000,000까지의 합을 4개의 스레드로 나눠 계산하라. `thread::scope`와 채널 두 가지 방식으로 모두 구현해 보라.
3. ★★★ 일부러 교착 상태를 만드는 프로그램을 작성하고(두 `Mutex`, 반대 순서), 잠금 순서를 통일해 해결하라. `try_lock`으로 해결하는 방식과 비교하라.

# 제11장 — 기다리는 자들의 항구

카고 할머니의 항구는 언제나 붐볐다. 하루에도 수백 척의 배가 드나들었고, 할머니는 그 모든 배를 혼자 관리했다.

"할머니, 어떻게 혼자서 이 많은 배를 다 처리하세요?" 하랑이 물었다.

"내가 배 한 척이 짐을 다 내릴 때까지 옆에 서서 기다린다면, 하루에 열 척도 못 받겠지." 할머니가 웃었다. "배가 짐을 내리는 동안 나는 다른 배로 가. 그 배가 밧줄을 묶는 동안 또 다른 배로 가고. 누군가 '다 됐어요!' 하고 부르면 그때 다시 돌아가는 거야."

"그게 `async`다." 보로가 말했다.

그때, 항구에 비상 경보가 울렸다. 수십 척의 배가 동시에 입항 신호를 보내고 있었다. 그중 몇 척은 **유령선**이었다. 신호만 보내고, 실제로는 오지 않는 배들. 항구의 일꾼들은 오지 않을 배를 기다리느라 다른 배들을 놓치고 있었다.

"누군가 항구를 마비시키려 하고 있어." 보로가 말했다. "기다리는 방법을 모르는 항구는 유령선 하나에 무너진다."

### 스레드와 async의 차이

"스레드로 하면 안 돼요? 배마다 일꾼을 한 명씩 붙이면…"

"배가 만 척이면? 일꾼 만 명이 필요하지. 스레드는 하나당 메모리를 꽤 먹고, 운영체제가 스레드 사이를 오가는 데도 비용이 든다. 그런데 일꾼들 대부분은 **그냥 기다리고 있을 뿐**이야. 짐이 내려지기를, 네트워크 응답이 오기를."

| | 스레드 | async 태스크 |
|---|---|---|
| 비유 | 배마다 일꾼 한 명 | 일꾼 몇 명이 여러 배를 돌아가며 |
| 비용 | 스레드마다 큰 스택(보통 MB 단위) | 태스크마다 작은 상태 기계 |
| 강점 | CPU를 많이 쓰는 계산 | **기다림이 많은 I/O** (네트워크, 파일, 타이머) |
| 수만 개 동시 처리 | 어려움 | 쉬움 |

### Future — 아직 오지 않은 결과

"러스트에서 `async fn`을 부르면, 그 함수는 **바로 실행되지 않아.** 대신 `Future`라는 '약속 증서'를 돌려주지. '언젠가 결과를 주겠다'는 증서."

```rust
async fn unload_ship(name: &str) -> String {
    // ... 짐 내리기 ...
    format!("{name} 하역 완료")
}
```

"이 증서는 누군가 **`.await`** 하거나 **런타임**에 넘겨야 비로소 실행된다. 러스트의 `Future`는 게을러. 제7장의 이터레이터처럼."

"그리고 러스트의 표준 라이브러리에는 그 증서를 실행해 주는 **런타임**이 들어 있지 않아. 용도에 따라 고를 수 있게 말이지. 가장 널리 쓰이는 건 `tokio`다."

```toml
[dependencies]
```

### 증거물 #33 — tokio로 여러 배를 동시에 처리하기

```rust
use std::time::Duration;
use tokio::time::{sleep, Instant};

async fn unload_ship(name: &str, secs: u64) -> String {
    println!("  > {name} 입항, 하역 시작");
    sleep(Duration::from_millis(secs * 100)).await;   // 기다리는 동안 다른 일을 한다
    println!("  < {name} 하역 완료");
    format!("{name}({secs})")
}

#[tokio::main]
async fn main() {
    let start = Instant::now();

    // 1) 순서대로 await: 하나씩 기다린다 (느림)
    let a = unload_ship("화물선 A", 3).await;
    let b = unload_ship("화물선 B", 2).await;
    println!("순차 처리: {a}, {b} — {:?}", start.elapsed());

    // 2) join!: 동시에 진행하고 모두 기다린다 (빠름)
    let start = Instant::now();
    let (c, d, e) = tokio::join!(
        unload_ship("어선 C", 3),
        unload_ship("어선 D", 2),
        unload_ship("어선 E", 1),
    );
    println!("동시 처리: {c}, {d}, {e} — {:?}", start.elapsed());

    // 3) spawn: 독립된 태스크로 띄우기 (스레드처럼, 하지만 훨씬 가볍게)
    let mut handles = Vec::new();
    for i in 0..5 {
        handles.push(tokio::spawn(async move {
            sleep(Duration::from_millis(50)).await;
            i * i
        }));
    }
    let mut squares = Vec::new();
    for h in handles {
        squares.push(h.await.unwrap());
    }
    println!("태스크 결과: {squares:?}");
}
```

"순차 처리는 0.5초, 동시 처리는 0.3초가 걸려. 가장 오래 걸리는 배만큼만. 일꾼은 한 명인데도!"

### select! — 유령선을 걸러 내는 법

"이제 유령선 문제를 풀어 보자." 보로가 말했다. "오지 않을 배를 영원히 기다리면 안 돼. **시간 제한**이 필요하다."

### 증거물 #34 — 타임아웃과 select!

```rust
use std::time::Duration;
use tokio::sync::mpsc;
use tokio::time::{sleep, timeout};

async fn wait_for_ship(name: &'static str, arrives_in_ms: Option<u64>) -> &'static str {
    match arrives_in_ms {
        Some(ms) => {
            sleep(Duration::from_millis(ms)).await;
            name
        }
        None => std::future::pending().await,   // 유령선: 영원히 오지 않는다
    }
}

#[tokio::main]
async fn main() {
    // 1) timeout: 정해진 시간 안에 안 오면 포기
    let ships = [("진짜 배", Some(100)), ("유령선", None), ("느린 배", Some(800))];
    for (name, eta) in ships {
        match timeout(Duration::from_millis(300), wait_for_ship(name, eta)).await {
            Ok(n) => println!("입항 확인: {n}"),
            Err(_) => println!("시간 초과: {name} — 유령선으로 의심"),
        }
    }

    // 2) select!: 여러 사건 중 '먼저 일어난 것'에 반응
    let (alarm_tx, mut alarm_rx) = mpsc::channel::<&str>(8);
    tokio::spawn(async move {
        sleep(Duration::from_millis(150)).await;
        let _ = alarm_tx.send("등대에서 수상한 불빛!").await;
    });

    tokio::select! {
        ship = wait_for_ship("정기선", Some(500)) => println!("먼저 온 것: {ship}"),
        Some(alarm) = alarm_rx.recv() => println!("먼저 온 것: 경보 — {alarm}"),
        _ = sleep(Duration::from_secs(1)) => println!("아무 일도 없었다"),
    }
}
```

```text
입항 확인: 진짜 배
시간 초과: 유령선 — 유령선으로 의심
시간 초과: 느린 배 — 유령선으로 의심
먼저 온 것: 경보 — 등대에서 수상한 불빛!
```

"`select!`는 여러 `Future`를 동시에 지켜보다가 **가장 먼저 끝난 것** 하나를 처리하고, 나머지는 **취소**한다." 보로가 말했다. "러스트의 `Future`는 `.await`하지 않으면 그냥 drop되면서 멈추니까, 취소가 아주 자연스럽지. 단, 그 때문에 '반쯤 하다 만' 상태가 남지 않도록 설계해야 해. 이걸 **취소 안전성(cancellation safety)** 이라고 한다."

---

### async의 내부 — 상태 기계

그날 밤, 하랑은 궁금증을 참지 못하고 물었다. "`await`에서 멈췄다가 나중에 다시 시작하는 건 어떻게 하는 거예요? 함수가 중간에 멈추다니."

보로가 칠판에 그렸다.

```text
 async fn trip() {            컴파일러가 만드는 상태 기계 (개념도)
     let a = step1().await;   enum TripFuture {
     let b = step2(a).await;      Start,
     done(b)                      WaitingStep1 { fut: Step1Future },
 }                                WaitingStep2 { a: A, fut: Step2Future },
                                  Done,
                              }
```

"컴파일러는 `async fn`을 **열거형으로 된 상태 기계**로 바꿔. `.await` 지점마다 상태가 하나씩 생기고, 그 시점에 필요한 지역 변수들을 상태 안에 저장하지. 런타임은 이 `Future`의 `poll` 메서드를 불러서 '진행할 수 있으면 진행해'라고 요청하고, 아직 준비가 안 됐으면 `Pending`을, 끝났으면 `Ready(값)`를 받는다."

```rust
// 표준 라이브러리의 Future 트레이트 (단순화)
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

"`Pin`은 뭐예요?"

"상태 기계 안에는 자기 자신의 다른 부분을 가리키는 참조가 들어 있을 수 있어. 그런데 그 상태 기계가 메모리에서 **이사**하면? 참조는 옛 주소를 가리키는 유령이 되지. `Pin`은 '이 값은 이제 메모리에서 움직이지 않는다'는 **고정 핀**이다. 대부분의 경우 `async`/`.await`와 `tokio::spawn`이 알아서 처리해 주니까, 직접 `Future`를 구현할 때가 아니면 깊이 신경 쓸 일은 드물어."

---

### async에서 조심할 것들

| 함정 | 설명 | 해결 |
|---|---|---|
| async 안에서 무거운 계산 | 일꾼이 한 배에 묶여 다른 배를 못 봄 | `tokio::task::spawn_blocking` |
| async 안에서 `std::thread::sleep` | 런타임 스레드 전체가 멈춤 | `tokio::time::sleep().await` |
| `.await` 너머로 `std::sync::MutexGuard` 쥐기 | 다른 태스크와 교착, `Send` 문제 | 잠금 범위를 `.await` 전에 끝내거나 `tokio::sync::Mutex` |
| `spawn`에 빌린 데이터 넘기기 | 태스크가 `'static`이어야 함 | `Arc`로 감싸거나 `move`로 소유권 이전 |
| `Future`를 만들고 `.await` 안 함 | 아무 일도 일어나지 않음 | 컴파일러 경고 `unused_must_use`에 주의 |

---

유령선 사건은 항구의 모든 대기 작업에 `timeout`이 걸리면서 해결되었다. 진짜 배들은 다시 원활하게 들어오기 시작했다.

그런데 그날 밤, 마지막으로 들어온 배 한 척에서 쪽지가 발견되었다. 받는 사람은 보로였다.

> *"검사관, 네 컴파일러는 훌륭하다.*
> *그러나 그것도 결국 너희가 'unsafe'라고 적어 둔 문 앞에서는 눈을 감는다.*
> *지하실에서 기다리겠다.*
> *— UB"*

보로는 쪽지를 오래도록 바라보았다. 그리고 처음으로, 하랑은 보로의 손이 아주 조금 떨리는 것을 보았다.

> **단서 노트 — 제11장**
>
> - `async fn`은 호출 즉시 실행되지 않고 **`Future`** 를 반환한다. `Future`는 게으르다.
> - `.await`는 결과를 기다리는 동안 **스레드를 놓아주고** 다른 태스크가 실행되게 한다.
> - 표준 라이브러리에는 런타임이 없다. **`tokio`**(범용), `smol` 등을 선택한다.
> - 동시 실행: `join!`(모두 기다림), `select!`(먼저 끝난 것), `spawn`(독립 태스크), `timeout`(시간 제한).
> - `async fn`은 컴파일러에 의해 **상태 기계**로 변환된다. `Future::poll` → `Poll::Pending` / `Poll::Ready`.
> - **`Pin`** 은 자기 참조 상태 기계가 메모리에서 이동하지 않도록 고정한다.
> - async 안에서 블로킹 작업 금지. CPU 작업은 `spawn_blocking`이나 `rayon`으로.
> - I/O가 많은 서버·클라이언트에는 async, CPU 계산에는 스레드—목적에 맞게 고른다.

### 탐정의 숙제

1. ★ 세 개의 URL을 '가짜로' 가져오는 `async fn fetch(url: &str, ms: u64) -> String`을 만들고, `join!`과 순차 `.await`의 걸린 시간을 비교하라.
2. ★★ `tokio::sync::mpsc` 채널로 생산자 태스크 3개, 소비자 태스크 1개를 만들어라. 생산자가 모두 끝나면 소비자도 끝나게 하라.
3. ★★★ `tokio::sync::Semaphore`를 사용해 "동시에 최대 2척만 하역"하는 항구를 구현하라. 10척의 배가 들어올 때 출력 순서를 관찰하라.

# 제12장 — 설계자의 일곱 개의 열쇠

지하실로 가는 길은 쉽게 열리지 않았다. 섬의 오래된 지도에 따르면, 지하실 입구는 **설계자의 서재** 안쪽에 있었다. 그리고 서재의 문에는 일곱 개의 자물쇠가 달려 있었다.

"섬을 처음 설계한 사람들이 남긴 서재다." 보로가 말했다. "그들은 문법만으로는 좋은 프로그램을 만들 수 없다는 걸 알았어. 문법은 벽돌이고, 패턴은 **설계도**지. 일곱 개의 자물쇠는 일곱 가지 설계 원리를 이해한 사람만 열 수 있다."

자물쇠마다 동판이 붙어 있었다. 하랑은 첫 번째 동판의 글을 읽었다.

### 첫 번째 열쇠 — 뉴타입 패턴

> *"같은 모양이라도 같은 의미는 아니다."*

"1999년, 다른 행성으로 날아가던 우주선 한 대가 사라졌다." 보로가 말했다. "한 팀은 힘을 '파운드' 단위로 계산했고, 다른 팀은 '뉴턴' 단위로 받아들였어. 둘 다 그냥 `f64`였지. 컴파일러는 아무 문제도 찾지 못했고, 우주선은 너무 낮게 날다가 사라졌다."

### 증거물 #35 — 뉴타입으로 의미를 타입에 새기기

```rust
use std::fmt;
use std::ops::Add;

#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]
struct Meters(f64);

#[derive(Debug, Clone, Copy, PartialEq, PartialOrd)]
struct Feet(f64);

impl From<Feet> for Meters {
    fn from(f: Feet) -> Self { Meters(f.0 * 0.3048) }
}

impl Add for Meters {
    type Output = Meters;
    fn add(self, rhs: Meters) -> Meters { Meters(self.0 + rhs.0) }
}

// ID도 뉴타입으로: 탐정 ID와 사건 ID를 절대 헷갈리지 않게
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
struct DetectiveId(u32);
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
struct CaseId(u32);

fn assign(detective: DetectiveId, case: CaseId) {
    println!("탐정 {:?} → 사건 {:?}", detective, case);
}

// 고아 규칙 우회: 남의 타입(Vec<String>)에 남의 트레이트(Display) 구현
struct Suspects(Vec<String>);
impl fmt::Display for Suspects {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "용의자: [{}]", self.0.join(", "))
    }
}

fn main() {
    let altitude = Meters(1000.0);
    let climb = Feet(500.0);
    // let wrong = altitude + climb;          // ❌ Meters + Feet는 컴파일 에러!
    let total = altitude + Meters::from(climb);
    println!("고도: {:.1}m", total.0);

    assign(DetectiveId(7), CaseId(42));
    // assign(CaseId(42), DetectiveId(7));    // ❌ 순서를 바꾸면 컴파일 에러!

    println!("{}", Suspects(vec!["우산 장수".into(), "그림자".into()]));

```

"뉴타입은 **실행 시간 비용이 전혀 없어.** `Meters(f64)`는 메모리에서 그냥 `f64`와 똑같지. 하지만 컴파일러는 둘을 완전히 다른 타입으로 본다. 비용 없이 실수를 막는 것—이 섬의 설계 철학이다."

첫 번째 자물쇠가 철컥 열렸다.

### 두 번째 열쇠 — 빌더 패턴

### 증거물 #36 — 빌더


두 번째 자물쇠가 열렸다.

### 세 번째 열쇠 — 타입 상태 패턴

> *"잘못된 순서는 실행되기 전에 거부되어야 한다."*

세 번째 동판 아래에는 작은 그림이 있었다. 문 하나. 그 문은 **잠김 → 열림 → 닫힘** 순서로만 움직일 수 있었다.

"빌더는 `build()`에서 실행 중에 에러를 내지. 그런데 **잘못된 순서 자체를 컴파일 에러로** 만들 수 있다면?" 보로의 눈이 빛났다. "그게 타입 상태(Typestate) 패턴이다. 러스트에서만 이렇게 우아하게 쓸 수 있는 패턴이지."

### 증거물 #37 — 타입 상태로 지하실 문 열기

```rust
use std::marker::PhantomData;

// 상태를 나타내는 빈 타입들 (크기 0)
struct Locked;
struct Unlocked;
struct Open;

struct VaultDoor<State> {
    attempts: u32,
    _state: PhantomData<State>,   // 상태는 타입에만 존재, 메모리는 0
}

impl VaultDoor<Locked> {
    fn new() -> Self {
        VaultDoor { attempts: 0, _state: PhantomData }
    }

    // 잠긴 문에서만 열쇠를 꽂을 수 있다. 성공하면 '타입'이 바뀐다.
    fn unlock(self, code: u32) -> Result<VaultDoor<Unlocked>, VaultDoor<Locked>> {
        if code == 1999 {
            Ok(VaultDoor { attempts: self.attempts + 1, _state: PhantomData })
        } else {
            Err(VaultDoor { attempts: self.attempts + 1, _state: PhantomData })
        }
    }
}

impl VaultDoor<Unlocked> {
    fn open(self) -> VaultDoor<Open> {
        println!("  끼이익... 문이 열렸다.");
        VaultDoor { attempts: self.attempts, _state: PhantomData }
    }
}

impl VaultDoor<Open> {
    fn enter(&self) {
        println!("  지하실에 들어섰다. (시도 횟수: {})", self.attempts);
    }
}

fn main() {
    let door = VaultDoor::new();

    // door.open();    // ❌ 컴파일 에러: Locked 상태에는 open 메서드가 없다!
    // door.enter();   // ❌ 컴파일 에러

    let door = match door.unlock(1234) {
        Ok(d) => d,
        Err(d) => {
            println!("  틀린 암호. 다시 시도.");
            d.unlock(1999).unwrap_or_else(|_| panic!("두 번째도 실패"))
        }
    };
    let door = door.open();
    door.enter();
}
```

"`open()`은 `VaultDoor<Unlocked>`에만 있고, `enter()`는 `VaultDoor<Open>`에만 있다. 잠긴 문을 열려고 하면 **실행할 기회조차 없이** 컴파일 에러가 나. 그리고 각 메서드가 `self`를 소비하니까, 이전 상태의 문은 더 이상 쓸 수 없어. 열린 문을 '잠긴 문'인 척하고 다시 쓸 수 없는 거지."

"이걸로 뭘 할 수 있어요?"

"네트워크 연결(연결 전 → 인증 완료 → 전송 가능), 파일(열기 → 쓰기 → 닫기), 결제(장바구니 → 결제 대기 → 완료)… **순서가 중요한 모든 것.** 실수로 인증 전에 데이터를 보내는 코드가 아예 존재할 수 없게 만들 수 있다."

세 번째 자물쇠가 열렸다.

### 증거물 #38 — 자동으로 정리되는 수사 현장

```rust
use std::cell::Cell;

struct CrimeScene<'a> {
    name: &'static str,
    active_scenes: &'a Cell<u32>,
}

impl<'a> CrimeScene<'a> {
    fn seal(name: &'static str, counter: &'a Cell<u32>) -> Self {
        counter.set(counter.get() + 1);
        println!("  [봉쇄] {name} (현재 봉쇄 중: {})", counter.get());
        CrimeScene { name, active_scenes: counter }
    }
}

impl Drop for CrimeScene<'_> {
    fn drop(&mut self) {
        self.active_scenes.set(self.active_scenes.get() - 1);
        println!("  [해제] {} (현재 봉쇄 중: {})", self.name, self.active_scenes.get());
    }
}

fn investigate(counter: &Cell<u32>, fail: bool) -> Result<(), String> {
    let _scene = CrimeScene::seal("북쪽 창고", counter);
    if fail {
        return Err("증거 불충분".into());   // 일찍 return해도 Drop은 실행된다!
    }
    println!("  수사 완료");
    Ok(())
}

fn main() {
    let counter = Cell::new(0);
    println!("{:?}", investigate(&counter, false));
    println!("{:?}", investigate(&counter, true));
    println!("최종 봉쇄 현장 수: {}", counter.get());   // 언제나 0
}
```

"`return`, `?`, 심지어 패닉으로 함수를 빠져나가도 `Drop`은 실행된다." 보로가 말했다. "그래서 '정리를 깜빡하는' 버그가 구조적으로 사라지지. `MutexGuard`, `File`, 데이터베이스 트랜잭션… 이 섬의 모든 자원은 이 원리로 관리된다."

### 증거물 #39 — 열거형 상태 기계

```rust
#[derive(Debug, Clone, PartialEq)]
enum CaseState {
    Reported { by: String },
    Investigating { lead: String, clues: u32 },
    Solved { culprit: String },
    Cold { reason: String },
}

#[derive(Debug)]
enum Event {
    Assign(String),
    FindClue,
    Accuse(String),
    GiveUp(String),
}

impl CaseState {
    // 상태 전이: 현재 상태를 소비하고 새 상태를 반환한다
    fn on(self, event: Event) -> Result<CaseState, (CaseState, String)> {
        use CaseState::*;
        match (self, event) {
            (Reported { .. }, Event::Assign(lead)) => Ok(Investigating { lead, clues: 0 }),
            (Investigating { lead, clues }, Event::FindClue) => {
                Ok(Investigating { lead, clues: clues + 1 })
            }
            (Investigating { clues, .. }, Event::Accuse(who)) if clues >= 3 => {
                Ok(Solved { culprit: who })
            }
            (s @ Investigating { .. }, Event::Accuse(_)) => {
                Err((s, "단서가 3개 미만이라 기소할 수 없음".into()))
            }
            (Investigating { .. }, Event::GiveUp(reason)) => Ok(Cold { reason }),
            (s, e) => {
                let msg = format!("{s:?} 상태에서 {e:?}는 허용되지 않음");
                Err((s, msg))
            }
        }
    }
}

fn main() {
    let mut state = CaseState::Reported { by: "관리인".into() };
    let events = vec![
        Event::FindClue,                       // 거부: 아직 배정 전
        Event::Assign("하랑".into()),
        Event::FindClue,
        Event::Accuse("그림자".into()),        // 거부: 단서 부족
        Event::FindClue,
        Event::FindClue,
        Event::Accuse("그림자".into()),
    ];

    for e in events {
        state = match state.on(e) {
            Ok(next) => { println!("→ {next:?}"); next }
            Err((same, why)) => { println!("✗ {why}"); same }
        };
    }
}
```

"`match (상태, 이벤트)` 형태로 쓰면, 모든 전이 규칙이 **한 곳에 표처럼** 모인다. 그리고 상태에 새 종류를 추가하면 컴파일러가 처리하지 않은 조합을 알려 주지. 다른 언어의 '상태 패턴'은 클래스를 여러 개 만들어야 하지만, 러스트에서는 열거형 하나와 `match` 하나면 충분해."

### 증거물 #40 — 정적 전략과 동적 전략

```rust
trait Interrogation {
    fn ask(&self, suspect: &str) -> String;
}

struct GoodCop;
struct BadCop;

impl Interrogation for GoodCop {
    fn ask(&self, s: &str) -> String { format!("{s}씨, 따뜻한 차 한잔 하시죠.") }
}
impl Interrogation for BadCop {
    fn ask(&self, s: &str) -> String { format!("{s}! 어젯밤 어디 있었어!") }
}

// 1) 정적 전략: 제네릭 — 컴파일 시점에 결정, 인라인되어 비용 0
struct Detective<S: Interrogation> {
    style: S,
}
impl<S: Interrogation> Detective<S> {
    fn question(&self, s: &str) -> String { self.style.ask(s) }
}

// 2) 동적 전략: 트레이트 객체 — 실행 중에 바꿀 수 있다
struct FlexibleDetective {
    style: Box<dyn Interrogation>,
}
impl FlexibleDetective {
    fn switch(&mut self, new_style: Box<dyn Interrogation>) { self.style = new_style; }
    fn question(&self, s: &str) -> String { self.style.ask(s) }
}

// 3) 클로저 전략: 가장 가벼운 방법
fn interrogate_all(suspects: &[&str], strategy: impl Fn(&str) -> String) {
    for s in suspects {
        println!("  {}", strategy(s));
    }
}

fn main() {
    let d = Detective { style: GoodCop };
    println!("{}", d.question("우산 장수"));

    let mut f = FlexibleDetective { style: Box::new(GoodCop) };
    println!("{}", f.question("그림자"));
    f.switch(Box::new(BadCop));
    println!("{}", f.question("그림자"));

    let tone = "단호하게";
    interrogate_all(&["쌍둥이 A", "쌍둥이 B"], |s| format!("({tone}) {s}, 진실을 말하시오."));
}
```

```rust
// 표준 타입 str에 새로운 메서드를 '추가'한다

impl DetectiveExt for str {

    println!("수상한가? {}", memo.is_suspicious());

    println!("{}", 42_u32.labeled("증거번호"));
```

`unsafe`

1. ★ `Celsius(f64)`와 `Fahrenheit(f64)` 뉴타입을 만들고 `From`으로 상호 변환하라.

# 제13장 — 주문서를 쓰는 마법사

지하실로 내려가기 전날 밤, 보로는 하랑을 섬의 북쪽 탑으로 데려갔다. 탑의 꼭대기에는 늙은 마법사가 살고 있었다.

"이분은 매크로 마법사다." 보로가 말했다. "코드를 쓰는 코드를 쓰는 분이지."

마법사는 하랑을 보며 웃었다. "자네, `println!`의 느낌표가 무슨 뜻인지 아는가?"

"매크로라는 표시요. 프롤로그에서 배웠어요."

"그럼 왜 `println`은 함수가 아니라 매크로여야 했을까?"

하랑은 생각에 잠겼다. "음… `println!("{} {}", a, b)`는 인자 개수가 그때그때 다르니까요? 러스트 함수는 인자 개수가 정해져 있어야 하고요."

"그것도 맞고. 하나 더 있지. `"{} {}"` 안의 중괄호 개수와 실제 인자 개수가 맞는지 **컴파일 시점에** 검사하려면, 문자열을 컴파일할 때 읽어야 해. 함수는 그걸 못 하지. 매크로는 **컴파일러가 코드를 이해하기 전에** 코드를 만들어 내니까 가능한 거라네."

### 선언적 매크로 — 패턴으로 코드를 찍어 내다

### 증거물 #42 — macro_rules! 기초

```rust
// 1) 가장 단순한 매크로
macro_rules! shout {
    ($msg:expr) => {
        println!("!!! {} !!!", $msg)
    };
}

// 2) 여러 패턴 (match처럼 위에서부터 시도)
macro_rules! clue {
    () => { "단서 없음" };
    ($name:expr) => { format!("단서: {}", $name) };
    ($name:expr, weight = $w:expr) => { format!("단서: {} (가중치 {})", $name, $w) };
}

// 3) 반복: $( ... ),* 는 '쉼표로 구분된 0개 이상'
macro_rules! suspects {
    ( $( $name:expr ),* $(,)? ) => {{
        let mut v = Vec::new();
        $( v.push(String::from($name)); )*
        v
    }};
}

// 4) 반복 + 계산: 최댓값 매크로 (재귀)
macro_rules! max_of {
    ($x:expr) => { $x };
    ($x:expr, $($rest:expr),+) => {{
        let a = $x;
        let b = max_of!($($rest),+);
        if a > b { a } else { b }
    }};
}

fn main() {
    shout!("지하실을 조사한다");
    println!("{}", clue!());
    println!("{}", clue!("발자국"));
    println!("{}", clue!("장갑", weight = 0.8));

    let list = suspects!["그림자", "쌍둥이 A", "쌍둥이 B",];
    println!("{list:?}");

    println!("최댓값: {}", max_of!(3, 17, 8, 42, 5));
}
```

마법사가 설명했다. "`$msg:expr`의 `expr`은 **조각 지정자(fragment specifier)** 라네. '여기에는 표현식이 온다'는 뜻이지."

| 지정자 | 매칭 대상 | 예 |
|---|---|---|
| `expr` | 표현식 | `1 + 2`, `foo()` |
| `ident` | 식별자 | `x`, `my_func` |
| `ty` | 타입 | `i32`, `Vec<String>` |
| `pat` | 패턴 | `Some(x)`, `1..=5` |
| `stmt` | 문장 | `let x = 1` |
| `block` | 블록 | `{ ... }` |
| `item` | 아이템 | `fn`, `struct` 정의 |
| `literal` | 리터럴 | `42`, `"hi"` |
| `tt` | 토큰 트리 하나 | 거의 무엇이든 |

"그리고 러스트 매크로는 **위생적(hygienic)** 이야. 매크로 안에서 만든 변수 `v`나 `a`가 바깥의 같은 이름 변수와 섞이지 않지. 제1장에서 본 섀도잉 사고가 매크로에서는 일어나지 않도록 설계된 거라네."

### 증거물 #43 — 매크로로 뉴타입 일괄 생성

```rust

            #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
            pub struct $name(pub u32);

            impl std::fmt::Display for $name {

                    write!(f, "{}#{}", stringify!($name), self.0)
                }
            }

            impl From<u32> for $name {
                fn from(v: u32) -> Self { $name(v) }
            }
        )+
    };
}

```

"`stringify!`는 토큰을 문자열로 바꿔 주는 내장 매크로라네. 수십 줄의 반복 코드가 한 줄로 줄었지? 하지만 조심하게. 매크로는 강력한 만큼 **읽기 어렵다.** 함수나 제네릭으로 해결할 수 있다면 그쪽이 먼저야. 매크로는 최후의 수단이지."

### 절차적 매크로 — 코드를 읽고 코드를 쓰는 프로그램

"`#[derive(Debug)]`는 어떻게 동작하는 걸까?" 마법사가 물었다.

"구조체의 필드를 보고… 출력 코드를 만들어 주는 거요?"

"그렇지. 그건 `macro_rules!`보다 훨씬 강력한 **절차적 매크로(procedural macro)** 라네. 러스트 코드를 **토큰의 흐름**으로 받아서, 분석하고, 새 토큰을 만들어 돌려주는 **러스트 프로그램**이지. 컴파일러의 플러그인 같은 거야."

| 종류 | 모양 | 예 |
|---|---|---|
| derive 매크로 | `#[derive(MyTrait)]` | `serde::Serialize`, `thiserror::Error` |
| 속성 매크로 | `#[my_attr]` | `#[tokio::main]`, `#[test]` |
| 함수형 매크로 | `my_macro!(...)` | `sqlx::query!` |

"절차적 매크로는 별도의 크레이트(`proc-macro = true`)에 만들어야 하고, 보통 `syn`(코드 분석), `quote`(코드 생성) 크레이트를 함께 쓰지. 맛보기로 보여 주겠네."

```toml
# describe_derive/Cargo.toml
[lib]
proc-macro = true

[dependencies]
syn = "2"
quote = "1"
proc-macro2 = "1"
```

```rust
// describe_derive/src/lib.rs
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, Data, DeriveInput, Fields};

#[proc_macro_derive(Describe)]
pub fn derive_describe(input: TokenStream) -> TokenStream {
    let ast = parse_macro_input!(input as DeriveInput);
    let name = &ast.ident;

    // 구조체의 필드 이름들을 모은다
    let field_names: Vec<String> = match &ast.data {
        Data::Struct(s) => match &s.fields {
            Fields::Named(named) => named
                .named
                .iter()
                .map(|f| f.ident.as_ref().unwrap().to_string())
                .collect(),
            _ => vec![],
        },
        _ => vec![],
    };
    let joined = field_names.join(", ");

    // 생성할 코드
    quote! {
        impl #name {
            pub fn describe() -> String {
                format!("{} {{ {} }}", stringify!(#name), #joined)
            }
        }
    }
    .into()
}
```

```rust
// 사용하는 쪽
use describe_derive::Describe;

#[derive(Describe)]
struct Suspect { name: String, height_cm: u32, has_alibi: bool }

fn main() {
    println!("{}", Suspect::describe());   // Suspect { name, height_cm, has_alibi }
}
```

"`#[tokio::main]`도 이런 속성 매크로라네. 네가 쓴 `async fn main`을 받아서, 런타임을 만들고 그 안에서 실행하는 평범한 `fn main`으로 **다시 써 주는** 거지."

하랑은 입을 다물지 못했다. "그럼 제가 이제까지 쓴 `#[derive(...)]`, `#[tokio::main]`, `println!`, `vec!`… 전부 누군가 만든 코드 생성기였던 거예요?"

"그렇다네. 러스트의 많은 '마법'은 사실 이렇게 **보이는 곳에 있는 평범한 러스트 코드**야. `cargo expand`라는 도구를 쓰면 매크로가 펼쳐진 결과를 눈으로 볼 수 있지. 마법은 원리를 알면 기술이 된다네."

마법사는 하랑에게 작은 두루마리를 건넸다.

"지하실에서 필요할 거야. UB는 컴파일러가 보지 못하는 곳에 숨어. 하지만 매크로와 타입으로 **경계를 좁히면**, 그자가 숨을 곳도 좁아지지."

> **단서 노트 — 제13장**
>
> - 매크로는 **컴파일 전에 코드를 생성**한다. 가변 인자, 컴파일 시점 검사, 반복 제거에 사용.
> - **`macro_rules!`**: 패턴 매칭 기반 선언적 매크로. `$x:expr`, `$( ... ),*`, `$(,)?` 등.
> - 러스트 매크로는 **위생적**이다. 매크로 내부 변수가 외부와 충돌하지 않는다.
> - **절차적 매크로**: derive / 속성 / 함수형. `TokenStream → TokenStream` 변환 프로그램. `syn` + `quote`.
> - `cargo expand`로 매크로 전개 결과를 확인할 수 있다.
> - **원칙**: 함수 → 제네릭 → 트레이트 → 매크로 순으로 고려하라. 매크로는 강력하지만 읽기 어렵다.

### 탐정의 숙제

1. ★ `square!(x)`가 `x * x`를 계산하는 매크로를 만들어라. `square!(1 + 2)`가 9가 되도록(5가 아니라) 하려면 어떻게 해야 하는가?
2. ★★ `hashmap!{ "a" => 1, "b" => 2 }`처럼 `HashMap`을 만드는 매크로를 작성하라.
3. ★★★ `enum_str!(Color { Red, Green, Blue })`가 열거형 정의와 함께 `fn as_str(&self) -> &'static str`를 생성하도록 만들어라.

# 제14장 — 금지된 지하실

철제 뚜껑을 들어 올리자, 차가운 공기가 올라왔다. 계단은 어둠 속으로 이어져 있었다.

"여기서부터는 컴파일러의 눈이 닿지 않는다." 보로가 랜턴을 들며 말했다. "`unsafe` 블록 안에서는 컴파일러가 몇 가지 검사를 **우리에게 맡긴다.** 우리가 '이건 안전하다'고 서명하는 거지. 서명이 거짓이면… UB가 깨어난다."

"그럼 왜 이런 곳이 있어요? 다 막아 버리면 되잖아요."

"컴퓨터의 가장 밑바닥은 원래 안전하지 않기 때문이다. 운영체제를 부르고, 하드웨어 레지스터를 만지고, C로 쓰인 오래된 라이브러리를 쓰려면 누군가는 이 지하실에 내려와야 해. 사실 `Vec`도, `String`도, `Rc`도, `Mutex`도 **이 지하실 위에 지어진 건물**이다. 중요한 건 지하실을 없애는 게 아니라, **지하실의 문을 작고 단단하게 만드는 것**이지."

---

### unsafe가 허락하는 다섯 가지

계단 벽에 다섯 개의 문장이 새겨져 있었다.

> **unsafe의 다섯 가지 초능력**
>
> 1. 원시 포인터(`*const T`, `*mut T`)를 **역참조**한다.
> 2. `unsafe` 함수나 메서드를 **호출**한다.
> 3. 가변 정적 변수(`static mut`)에 **접근**한다.
> 4. `unsafe` 트레이트를 **구현**한다. (예: `Send`, `Sync`를 수동 구현)
> 5. `union`의 필드에 **접근**한다.

"그 외의 모든 것—빌림 검사, 타입 검사, 라이프타임 검사—은 `unsafe` 안에서도 **그대로** 작동한다. `unsafe`는 '규칙이 없는 곳'이 아니라 '**다섯 가지만** 네가 책임지는 곳'이야."

---

### 원시 포인터 — 열쇠 없는 주소

### 증거물 #44 — 원시 포인터

```rust
fn main() {
    let mut evidence = 42;

    // 원시 포인터를 '만드는' 것은 안전하다
    let p_read = &raw const evidence;   // *const i32
    let p_write = &raw mut evidence;    // *mut i32

    // '역참조'하는 것은 unsafe다: 유효한지 컴파일러가 보장할 수 없다
    unsafe {
        *p_write += 1;
        println!("읽기: {}", *p_read);
    }

    // 아무 주소나 만들 수도 있다 — 역참조하는 순간 UB!
    let _ghost = 0xDEAD_BEEF as *const i32;
    // unsafe { println!("{}", *_ghost); }  // ☠ 절대 하지 말 것
}
```

"원시 포인터는 빌림 규칙을 따르지 않아. 같은 데이터를 가리키는 `*mut`를 여러 개 만들 수도 있고, null일 수도 있고, 이미 해제된 메모리를 가리킬 수도 있지. 그래서 역참조할 때 **'이 포인터는 유효하고, 정렬되어 있고, 지금 다른 누구도 이걸 통해 쓰고 있지 않다'** 는 걸 네가 보증해야 해."

---

### 안전한 추상화 — 지하실의 문을 작게

계단 끝, 지하실 한가운데에 낡은 책상이 있었다. 그 위에 코드 한 장이 놓여 있었다. 표준 라이브러리의 `split_at_mut`를 흉내 낸 함수였다.

"이 함수를 봐라." 보로가 말했다. "하나의 슬라이스를 겹치지 않는 두 개의 가변 슬라이스로 쪼개는 함수다."

```rust
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len);
    (&mut values[..mid], &mut values[mid..])   // ❌ 컴파일 에러
}
```

"컴파일러는 이걸 거부해. `values`를 두 번 가변으로 빌린다고 보거든. 하지만 **우리는** 안다. 두 조각은 절대 겹치지 않는다는 걸. 컴파일러가 증명하지 못하는 진실이지. 이럴 때 지하실을 쓴다."

### 증거물 #45 — unsafe를 안전한 API로 감싸기

```rust
use std::slice;

/// 슬라이스를 `mid` 지점에서 겹치지 않는 두 가변 슬라이스로 나눈다.
///
/// # Panics
/// `mid > values.len()`이면 패닉한다.
pub fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    assert!(mid <= len, "mid({mid})가 길이({len})를 넘음");
    let ptr = values.as_mut_ptr();

    // SAFETY:
    // - ptr은 길이 len인 유효한 슬라이스에서 왔다.
    // - mid <= len을 위에서 검사했으므로 두 범위 [0, mid), [mid, len)은 모두 경계 안이다.
    // - 두 범위는 겹치지 않으므로, 두 &mut가 같은 메모리를 가리키지 않는다.
    // - 반환되는 두 슬라이스의 수명은 입력 values의 수명에 묶인다.
    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut clues = [1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut(&mut clues, 2);
    left[0] = 100;
    right[0] = 300;
    println!("{clues:?}");
}
```

"보이나?" 보로가 랜턴을 들이댔다. "**함수 자체는 안전하다.** 시그니처에 `unsafe`가 없지. 호출하는 사람은 지하실의 존재조차 몰라도 돼. `assert!`로 경계를 검사하고, `// SAFETY:` 주석으로 '왜 안전한지'를 증명해 뒀으니까. 이게 러스트의 핵심 기술이다."

> **안전한 추상화의 원칙**
>
> 1. `unsafe` 블록은 **가능한 한 작게.**
> 2. 모든 `unsafe` 블록에 **`// SAFETY:` 주석**으로 불변식을 증명하라.
> 3. `unsafe`를 **안전한 함수 안에 감싸서**, 어떤 입력으로 호출해도 UB가 일어나지 않게 하라.
> 4. 만약 호출자가 지켜야 할 조건이 있다면, 함수 자체를 `unsafe fn`으로 만들고 `# Safety` 문서에 조건을 적어라.
> 5. `cargo miri test`로 UB를 탐지하라. Miri는 지하실을 비추는 손전등이다.

### FFI — 다른 섬과의 국경

지하실 벽 한쪽에는 커다란 문이 있었다. 문 위에는 `extern "C"`라고 적혀 있었다.

"다른 섬, C 섬으로 통하는 국경이다." 보로가 말했다. "제3장의 도서관 사건 기억하나? C 섬 방문객이 우리 도서관을 엉망으로 만들었던 거. 그때 그자가 들어온 문이 바로 이거야."

### 증거물 #46 — C 라이브러리 호출

```rust
use std::ffi::{CStr, CString};
use std::os::raw::{c_char, c_int};

// C 표준 라이브러리 함수 선언 (Rust 2024: extern 블록은 unsafe로 표시)
unsafe extern "C" {
    safe fn abs(x: c_int) -> c_int;                 // 어떤 입력에도 안전 → safe로 표시 가능
    fn strlen(s: *const c_char) -> usize;           // 포인터가 유효해야 함 → unsafe
}

// 안전한 래퍼
fn c_string_length(s: &str) -> Result<usize, std::ffi::NulError> {
    let c = CString::new(s)?;                       // 내부에 \0이 있으면 에러
    // SAFETY: c는 null로 끝나는 유효한 C 문자열이고, 이 호출 동안 살아 있다.
    Ok(unsafe { strlen(c.as_ptr()) })
}

// 반대 방향: C에서 부를 수 있는 러스트 함수
#[unsafe(no_mangle)]
pub extern "C" fn rust_greet(name: *const c_char) -> c_int {
    if name.is_null() {
        return -1;
    }
    // SAFETY: 호출자(C)는 null로 끝나는 유효한 문자열을 넘겨야 한다는 계약을 따른다.
    let name = unsafe { CStr::from_ptr(name) };
    println!("러스트가 인사합니다: {}", name.to_string_lossy());
    0
}

fn main() {
    println!("abs(-7) = {}", abs(-7));
    println!("strlen = {:?}", c_string_length("UB 백작"));     // 바이트 수
    println!("내부 NUL = {:?}", c_string_length("UB\0백작").is_err());

    let me = CString::new("하랑").unwrap();
    rust_greet(me.as_ptr());
}
```

"FFI의 국경에서는 세 가지를 꼭 검사해야 해." 보로가 말했다. "**null인가? 수명은 누가 관리하나? 문자열 인코딩은 무엇인가?** C의 문자열은 `\0`으로 끝나고, 러스트의 문자열은 길이를 따로 가지고 UTF-8이지. 이 차이를 `CString`, `CStr`이 메워 준다. 실무에서는 `bindgen`(C 헤더 → 러스트 선언 자동 생성)과 `cbindgen`(러스트 → C 헤더) 도구를 많이 쓴다."

### UB 백작과의 조우

그때, 지하실의 어둠 속에서 목소리가 울렸다.

"훌륭하군, 검사관. 그리고 꼬마 견습생."

랜턴 불빛 끝에, 얼굴 없는 형체가 서 있었다. 그 몸은 계속해서 모양이 바뀌었다. 어떨 때는 사람, 어떨 때는 숫자의 흐름, 어떨 때는 그냥 공허였다.

"UB 백작." 보로가 말했다.

"나는 이 지하실의 주인이다. 너희가 `unsafe`라고 쓰는 모든 곳에 내가 있지." 백작이 웃었다. "봐라. 이 섬의 수많은 크레이트들이 지하실에 문을 뚫었다. 그중 하나만 약속을 어겨도, 나는 섬 전체로 퍼져 나갈 수 있어. 너희 컴파일러는 **unsafe 블록 안의 약속을 믿을 수밖에 없으니까.**"

백작이 손을 뻗자, 책상 위에 코드 한 장이 나타났다.

```rust
pub fn get_clue(clues: &[i32], i: usize) -> i32 {
    // "어차피 i는 항상 범위 안이야. 검사는 느리니까 생략하지."
    unsafe { *clues.get_unchecked(i) }
}
```

"이 함수는 시그니처가 **안전**하다. 누구든 아무 `i`로 부를 수 있지. 하지만 `i`가 범위를 벗어나면? 옆집 메모리를 읽는다. 바로 내가 깨어나는 순간이지." 백작이 웃었다. "이 섬의 어딘가에, 이런 코드가 숨어 있다. 찾을 수 있겠나?"

백작의 형체는 어둠 속으로 녹아들었다. 목소리만 남았다.

"법정에서 보자, 검사관. 내가 이 섬에 존재한다는 것을 증명해 주지."

---

하랑은 떨리는 손으로 백작이 남긴 코드를 들여다보았다. 그리고 문득 깨달았다.

"보로 씨. 이 함수, **건전하지 않아요(unsound).** 안전한 함수인데, 안전한 코드만으로 UB를 일으킬 수 있어요. `get_clue(&[1, 2, 3], 100)`처럼요. 고치려면 둘 중 하나예요. 범위를 검사하거나—"

```rust
pub fn get_clue(clues: &[i32], i: usize) -> Option<i32> {
    clues.get(i).copied()            // 안전하고, 대부분 최적화로 충분히 빠르다
}
```

"—아니면 `unsafe fn`으로 만들어서 **호출하는 사람에게 책임을 명시적으로 넘기거나요.**"

```rust
/// # Safety
/// `i < clues.len()`이어야 한다.
pub unsafe fn get_clue_unchecked(clues: &[i32], i: usize) -> i32 {
    // SAFETY: 호출자가 i < clues.len()을 보장한다.
    unsafe { *clues.get_unchecked(i) }
}
```

보로가 하랑의 어깨에 손을 얹었다.

"그게 핵심이다. **건전성(soundness)**. 안전한 인터페이스로는 **어떤 방법으로도** UB를 일으킬 수 없어야 한다. 이 원칙을 지키는 한, UB는 지하실 밖으로 나올 수 없다. 이제 법정에서 그걸 증명하기만 하면 돼."

> **단서 노트 — 제14장**
>
> - `unsafe`는 다섯 가지 능력만 연다: 원시 포인터 역참조, unsafe 함수 호출, `static mut` 접근, unsafe 트레이트 구현, union 필드 접근. **나머지 검사는 그대로**다.
> - 원시 포인터를 만드는 건 안전, **역참조**가 unsafe. `&raw const` / `&raw mut`로 만든다.
> - **안전한 추상화**: unsafe를 안전한 함수 안에 숨기고, 어떤 입력에도 UB가 나지 않게 하라. `// SAFETY:` 주석 필수.
> - **건전성(soundness)**: 안전한 코드만으로는 절대 UB를 일으킬 수 없어야 한다. 이를 어기면 unsound 버그.
> - 호출자에게 조건이 필요하면 `unsafe fn` + `# Safety` 문서.
> - **FFI**: `extern "C"`, `CString`/`CStr`, null·수명·인코딩 검사. `bindgen`/`cbindgen`.
> - **Miri**(`cargo +nightly miri test`)로 unsafe 코드의 UB를 탐지하라.
> - Rust 2024 에디션: `unsafe extern "C" { ... }`, `#[unsafe(no_mangle)]`, unsafe fn 안에서도 `unsafe { }` 블록 명시를 권장.

### 탐정의 숙제

1. ★ 증거물 #44에서 `p_read`와 `p_write`가 같은 주소를 가리키는지 `{:p}` 형식으로 출력해 확인하라.
2. ★★ `fn swap_first_last(v: &mut [i32])`를 `unsafe` 없이 작성하라. (힌트: `split_at_mut`이나 `swap`.) 왜 대부분의 경우 unsafe가 필요 없는지 생각해 보라.
3. ★★★ `struct MyVec<T> { ptr: *mut T, cap: usize, len: usize }`로 아주 작은 `Vec`을 직접 구현해 보라(`std::alloc` 사용). `push`, `get`, `Drop`만 있으면 된다. 그리고 *The Rustonomicon*의 "Implementing Vec" 장과 비교하라.

### 증거물 #47 — 모듈과 가시성으로 unsafe 격리하기

```rust
mod vault {
    // 공개 API: 바깥에서 쓸 수 있다
    pub struct ClueBox {
        items: Vec<i32>,            // 필드는 비공개 — 불변식을 지키기 위해
    }

    impl ClueBox {
        pub fn new(items: Vec<i32>) -> Self {
            ClueBox { items }
        }

        /// 안전한 공개 API. 어떤 i를 넣어도 UB가 없다.
        pub fn get(&self, i: usize) -> Option<i32> {
            if i < self.items.len() {
                // SAFETY: 바로 위에서 i < len을 확인했다.
                Some(unsafe { raw::read_unchecked(&self.items, i) })
            } else {
                None
            }
        }

        pub fn len(&self) -> usize {
            self.items.len()
        }
    }

    // 비공개 모듈: unsafe는 이 안에만 산다
    mod raw {
        /// # Safety
        /// `i < v.len()`이어야 한다.
        pub(super) unsafe fn read_unchecked(v: &[i32], i: usize) -> i32 {
            // SAFETY: 호출자가 i < v.len()을 보장한다.
            unsafe { *v.get_unchecked(i) }
        }
    }

    // pub(crate): 크레이트 안에서만 보인다
    pub(crate) fn audit_log() -> &'static str {
        "vault::raw 외부에는 unsafe 없음"
    }
}

use vault::ClueBox;

fn main() {
    let b = ClueBox::new(vec![10, 20, 30]);
    println!("{:?} {:?}", b.get(1), b.get(99));
    println!("길이 {}, 감사: {}", b.len(), vault::audit_log());
    // b.items;                         // ❌ 비공개 필드
    // vault::raw::read_unchecked(...); // ❌ 비공개 모듈
}
```

| 가시성 | 보이는 범위 |
|---|---|
| (없음) | 현재 모듈과 그 자식 모듈 |
| `pub(super)` | 부모 모듈까지 |
| `pub(crate)` | 현재 크레이트 전체 |
| `pub` | 어디서나 |

"러스트에서 모든 것은 기본적으로 **비공개**입니다." 하랑이 말했다. "`ClueBox`의 `items` 필드는 바깥에서 건드릴 수 없습니다. 그래서 '인덱스가 범위 안이어야 한다'는 불변식을 **모듈 안의 코드만** 지키면 됩니다. 지하실의 문은 `vault::raw`라는 방 하나에만 있고, 그 방은 `vault` 모듈 바깥에서는 보이지도 않습니다. 감사관은 섬 전체가 아니라 **이 작은 방 하나만** 검사하면 됩니다."

판사가 고개를 끄덕였다. "피고의 '섬 곳곳에'라는 주장은 기각합니다. 계속하시오."

### 증거물 #49 — 제로 코스트 추상화

```rust
// 버전 A: 손으로 짠 인덱스 루프
fn sum_of_even_squares_loop(v: &[u64]) -> u64 {
    let mut total = 0;
    let mut i = 0;
    while i < v.len() {
        let x = v[i];          // 매번 경계 검사가 필요할 수도 있다
        if x % 2 == 0 {
            total += x * x;
        }
        i += 1;
    }
    total
}

// 버전 B: 이터레이터 체인
fn sum_of_even_squares_iter(v: &[u64]) -> u64 {
    v.iter()
        .filter(|&&x| x % 2 == 0)
        .map(|&x| x * x)
        .sum()
}

fn main() {
    let data: Vec<u64> = (1..=1_000).collect();
    let a = sum_of_even_squares_loop(&data);
    let b = sum_of_even_squares_iter(&data);
    assert_eq!(a, b);
    println!("두 결과 모두 {a}");
}
```

페리는 그 아래에 `cargo build --release`로 만든 기계어를 비교한 그림을 붙였다. 이터레이터 버전에는 경계 검사가 **아예 없었고**, 컴파일러는 여러 숫자를 한 번에 처리하는 SIMD 명령어까지 써 놓았다.

보로가 설명을 이었다.

"재판장님. C++의 창시자 비야네 스트롭스트룹은 이렇게 말했습니다. **'쓰지 않는 것에는 비용을 치르지 않는다. 그리고 쓰는 것은, 손으로 짜도 그보다 더 잘 짤 수 없다.'** 러스트는 이 원칙을 계승했습니다."

| 추상화 | 실제 비용 |
|---|---|
| 이터레이터 체인 | 손으로 짠 루프와 동일, 경계 검사 제거되는 경우 많음 |
| 제네릭 | 단형화로 타입별 최적 코드, 실행 시간 비용 0 |
| 뉴타입 | 0 (메모리 표현 동일) |
| `Option<&T>`, `Option<Box<T>>` | 0 (null 포인터 최적화로 포인터와 같은 크기) |
| 소유권/빌림/라이프타임 | 0 (컴파일 시점에만 존재) |
| `async` 상태 기계 | 힙 할당 없이 구성 가능 |

"그리고 이걸 보십시오." 보로가 하나를 더 보여 주었다.

```rust
use std::mem::size_of;

fn main() {
    println!("&u64          : {} bytes", size_of::<&u64>());
    println!("Option<&u64>  : {} bytes", size_of::<Option<&u64>>());     // 같다!
    println!("Box<u64>      : {} bytes", size_of::<Box<u64>>());

```

"`None`을 표현하는 데 **단 1바이트도 더 쓰지 않습니다.** 참조는 절대 null이 될 수 없으니, 컴파일러가 null 값을 `None`으로 재활용하는 것이죠. 안전은 공짜로 얻은 겁니다."

> **성능 탐정의 도구 상자**
>
> - `cargo build --release`: 최적화 빌드. 디버그 빌드보다 수십 배 빠를 수 있다. **성능은 반드시 release로 측정하라.**
> - `Cargo.toml`의 `[profile.release]`: `lto = true`, `codegen-units = 1`, `panic = "abort"` 등으로 조정.
> - **`criterion`** 크레이트: 통계적으로 신뢰할 수 있는 벤치마크.
> - **`cargo flamegraph`**, `perf`, `samply`: 어디서 시간이 쓰이는지 시각화.
> - 흔한 최적화: 불필요한 `clone()` 제거, `Vec::with_capacity`로 재할당 방지, `&str`/`&[T]`로 빌리기, `String` 대신 `Cow`, 핫 루프에서 할당 피하기, `rayon`으로 병렬화.
> - **원칙: 추측하지 말고 측정하라.**

### 네 번째 변론 — 경위의 증언: Clippy

클리피 경위가 증인석에 올랐다.

"저는 이 섬을 매일 순찰합니다." 경위가 말했다. "`cargo clippy`라는 이름으로요. 컴파일러가 '틀렸다'고 말하는 것만 잡는다면, 저는 '**더 좋은 방법이 있다**'고 말합니다. 수백 가지 규칙으로요."

```rust
// 순찰 전

    if names.len() == 0 { return false; }
    let mut found = false;
    for i in 0..names.len() {
        if names[i] == "그림자".to_string() { found = true; }
    }
```

# 부록 A — 탐정 수첩: 러스트 핵심 요약표

### A-1. 소유권 한눈에 보기

| 표기 | 이름 | 소유? | 수정? | 동시에 몇 개? |
|---|---|---|---|---|
| `T` | 소유한 값 | O | (`mut`이면) O | 주인은 하나 |
| `&T` | 공유 참조 | X | X | 여러 개 |
| `&mut T` | 가변 참조 | X | O | **하나** |
| `Box<T>` | 힙 소유 | O | O | 하나 |
| `Rc<T>` / `Arc<T>` | 공유 소유 | 공동 | X | 여러 개 |
| `RefCell<T>` / `Mutex<T>` | 내부 가변성 | O | 실행 중 검사 | 빌림 하나 / 잠금 하나 |
| `Weak<T>` | 약한 참조 | X | X | 여러 개 |

### A-2. 어떤 스마트 포인터를 쓸까?

```text
데이터를 여러 곳에서 공유해야 하나?
├── 아니오 → 그냥 T, 또는 크기 문제가 있으면 Box<T>
└── 예 → 여러 스레드에서?
         ├── 아니오 → Rc<T>         (수정도 필요하면 Rc<RefCell<T>>)
         └── 예     → Arc<T>        (수정도 필요하면 Arc<Mutex<T>> / Arc<RwLock<T>>)
                                      (단순 숫자라면 Atomic* 타입)
순환이 생길 수 있나? → 한쪽 방향을 Weak<T>로
```

### A-3. 함수 인자는 무엇으로 받을까?

| 하고 싶은 일 | 인자 타입 |
|---|---|
| 문자열을 읽기만 | `&str` |
| 목록을 읽기만 | `&[T]` |
| 내용을 고쳐야 | `&mut T` / `&mut [T]` |
| 저장하거나 소비해야 | `T` (`String`, `Vec<T>`) |
| 무엇이든 문자열로 바꿀 수 있는 것 | `impl Into<String>` / `impl AsRef<str>` |
| 무엇이든 순회 가능한 것 | `impl IntoIterator<Item = T>` |

```rust
    let (even, odd): (Vec<i32>, Vec<i32>) = v.iter().partition(|&&x| x % 2 == 0);
```

# 부록 B — 컴파일러의 증언 사전

| 코드 | 메시지 요약 | 등장 | 흔한 원인과 해결 |
|---|---|---|---|
| **E0382** | use of moved value | 제2장 | 이동한 값을 다시 씀 → `&`로 빌리기, `.clone()`, 소유권 반환 |

| **E0499** | cannot borrow as mutable more than once | 제3·10장 | `&mut` 두 개 → 범위 분리, `split_at_mut`, 구조 재설계 |

| **E0505** | cannot move out because it is borrowed | 제3장 | 빌려준 상태에서 이동 → 빌림이 끝난 뒤 이동 |
| **E0106** | missing lifetime specifier | 제4장 | 반환 참조의 출처 불명 → 라이프타임 명시 또는 소유 타입 반환 |

**3번.**

```rust
struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn next_word(&mut self) -> Option<&'a str> {
        let rest = &self.input[self.pos..];
        let trimmed = rest.trim_start();
        if trimmed.is_empty() {
            return None;
        }
        let start = self.pos + (rest.len() - trimmed.len());
        let end = trimmed.find(' ').map(|i| start + i).unwrap_or(self.input.len());
        self.pos = end;
        Some(&self.input[start..end])
    }
}

fn main() {
    let text = String::from("단서 하나 단서 둘");
    let mut p = Parser { input: &text, pos: 0 };
    let first = p.next_word();
    let second = p.next_word();   // first를 쥔 채로 다시 &mut self 호출 가능!
    println!("{first:?} {second:?}");
}
```

반환 타입이 `&'a str`이면 결과는 **원본 문자열**의 수명에 묶이므로 파서를 계속 써도 된다. `&str`(즉 `&self`의 수명)로 쓰면 결과가 파서를 빌린 것으로 취급되어, 결과를 쥔 채로 `next_word`를 다시 부를 수 없다.

러스트를 처음 배울 때 가장 많이 듣는 말은 "컴파일러와 싸운다"는 표현입니다. 이 책은 그 표현을 뒤집어 보고 싶었습니다. 컴파일러는 적이 아니라 **가장 깐깐하고, 가장 정직하고, 한 번도 틀린 적 없는 탐정 파트너**라고요.

하랑이 그랬듯, 여러분도 에러 메시지를 만날 때마다 단서를 얻습니다. "왜 안 되지?"라는 질문이 "아, 이래서 안 되는구나"로 바뀌는 순간, 여러분은 이미 한 단계 위의 개발자가 되어 있을 것입니다.
