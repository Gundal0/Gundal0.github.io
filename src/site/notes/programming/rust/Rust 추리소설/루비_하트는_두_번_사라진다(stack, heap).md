# 제1장 — 책상과 창고

C++ 섬의 왕립 박물관은 웅장했다. 높은 천장, 대리석 바닥, 그리고 수십 년 된 코드로 움직이는 전시 관리 시스템.

스트라우 관장은 지친 얼굴로 그들을 맞았다.

"저는 아무 잘못도 하지 않았습니다." 관장이 말했다. "그저 루비 하트를 경비원에게 맡겼을 뿐이에요. 저도 계속 갖고 있고, 경비원도 갖고 있었죠. 그런데 행사 리허설이 끝나는 순간 시스템 전체가 쓰러졌습니다."

"'저도 갖고 있고, 경비원도 갖고 있었다'." 보로가 그 말을 천천히 되뇌었다. "바로 그게 문제입니다, 관장님."

하랑은 고개를 갸웃했다. "어떻게 하나의 보석을 두 사람이 동시에 가질 수 있어요?"

"그걸 이해하려면 먼저 이 섬의 지리부터 알아야 해." 보로가 페리를 돌아보았다. "지도를 그려 줘."

페리가 박물관 로비의 커다란 칠판 앞으로 기어가 집게발을 움직이기 시작했다.

### 1.1 프로그램이 사는 동네 — 메모리 지도

```text
 높은 주소
 ┌──────────────────────────────┐
 │  스택 (Stack)                 │  ← 함수가 호출될 때마다 아래로 자란다 ↓
 │  - 지역 변수, 함수 인자         │
 │  - 돌아갈 주소(return address) │
 ├──────────────────────────────┤
 │            ↓                 │
 │         (빈 공간)              │
 │            ↑                 │
 ├──────────────────────────────┤
 │  힙 (Heap)                    │  ← 요청할 때마다 위로 자란다 ↑
 │  - new / malloc / Box / Vec  │
 ├──────────────────────────────┤
 │  데이터 영역 (.data / .bss)     │  ← 전역 변수, static
 ├──────────────────────────────┤
 │  읽기 전용 데이터 (.rodata)      │  ← 문자열 리터럴 "루비 하트"
 ├──────────────────────────────┤
 │  코드 영역 (.text)              │  ← 기계어 명령어
 └──────────────────────────────┘
 낮은 주소
```

"프로그램이 실행되면 운영체제는 프로그램에게 이런 동네를 하나 내준다." 보로가 설명했다. "코드가 사는 구역, 전역 변수가 사는 구역, 그리고 우리가 오늘 수사할 두 구역. **스택**과 **힙**이다."

> 실제 운영체제에서는 보안을 위해 각 구역의 시작 주소를 실행할 때마다 무작위로 바꾼다(ASLR). 스택과 힙 사이도 그림처럼 단순하지 않고, 공유 라이브러리와 메모리 매핑 영역이 섞여 있다. 하지만 이 지도는 개념을 이해하는 데 충분하다.

---

### 1.2 스택 — 탐정의 책상

"스택은 **책상**이라고 생각해라." 보로가 말했다.

"함수 하나가 호출되면, 그 함수만을 위한 공간이 책상 위에 한 칸 쌓인다. 이걸 **스택 프레임(stack frame)** 이라고 해. 그 칸에는 지역 변수, 인자, 그리고 '일이 끝나면 어디로 돌아가야 하는지'가 적혀 있지. 함수가 끝나면? 그 칸을 통째로 걷어 낸다. 가장 나중에 올린 것을 가장 먼저 치우는 구조, **LIFO(Last In, First Out)** 다."

페리가 그림을 추가했다.

```text
 main() 이 investigate() 를 부르고,
 investigate() 가 check_alibi() 를 불렀을 때

 ┌──────────────────────────┐  ← 높은 주소
 │ main 의 프레임             │
 │   museum_id = 7           │
 ├──────────────────────────┤
 │ investigate 의 프레임      │
 │   돌아갈 곳: main 의 23번 줄 │
 │   suspect_count = 3       │
 ├──────────────────────────┤
 │ check_alibi 의 프레임      │
 │   돌아갈 곳: investigate…  │
 │   hour = 21               │
 ├──────────────────────────┤  ← 스택 포인터(SP): 지금 책상 맨 위
 │  (아직 안 쓴 공간)           │
 └──────────────────────────┘  ← 낮은 주소
```

"스택이 빠른 이유는 세 가지다." 보로가 손가락을 하나씩 폈다.

1. **할당이 공짜에 가깝다.** 공간을 확보하는 일은 CPU의 **스택 포인터 레지스터**를 숫자 하나만큼 옮기는 명령어 한 줄이다. 누구에게 허락받을 필요도, 빈자리를 찾을 필요도 없다.
2. **해제도 공짜에 가깝다.** 함수가 끝나면 스택 포인터를 되돌리기만 하면 된다. 그 칸에 무엇이 있었든 상관없다.
3. **캐시에 친절하다.** 책상 맨 위는 방금까지 쓰던 곳이라 CPU 캐시에 이미 올라와 있을 확률이 매우 높다.

"대신 대가가 있지."

- **크기가 컴파일할 때 정해져 있어야 한다.** 컴파일러는 함수의 프레임 크기를 미리 계산해야 하니까. "사용자가 입력할 이름"처럼 크기를 모르는 것은 올릴 수 없다.
- **책상 크기 자체가 작다.** 리눅스의 메인 스레드는 기본 8MiB, 윈도우는 기본 1MiB 정도다. Rust가 새로 만드는 스레드는 기본 2MiB다. 너무 깊이 재귀하거나 커다란 배열을 지역 변수로 만들면 **스택 오버플로**로 프로그램이 쓰러진다.
- **함수가 끝나면 사라진다.** 함수 밖으로 살아남아야 하는 데이터는 둘 수 없다.

### 1.3 힙 — 섬의 거대한 창고

"그럼 크기를 모르거나, 오래 살아야 하는 건요?" 하랑이 물었다.

"그건 **힙**, 섬의 거대한 창고에 맡긴다." 보로가 창밖의 물류 창고를 가리켰다. "창고에는 **창고지기**가 있다. 프로그래밍에서는 이걸 **메모리 할당자(allocator)** 라고 부르지. C의 `malloc`/`free`, C++의 `new`/`delete`, Rust의 `Box`/`Vec`/`String`은 모두 결국 이 창고지기에게 일을 시킨다."

창고에 짐을 맡기는 과정은 책상보다 훨씬 복잡하다.

```text
 프로그램: "13바이트짜리 칸 하나 주세요."
     │
     ▼
 창고지기(할당자):
   1) 빈 칸 목록(free list)에서 맞는 크기를 찾는다.
   2) 없으면 더 큰 칸을 쪼개거나, 운영체제에게 창고 증축을 요청한다(brk/mmap).
   3) 칸 앞에 '관리용 꼬리표'(크기, 상태)를 붙인다.
   4) 칸의 주소를 돌려준다.  →  0x5555_5556_b2c0
     │
     ▼
 프로그램: 주소를 스택의 변수에 적어 둔다.  (이 주소가 바로 '포인터')
```

"그래서 힙은 스택보다 느리다." 보로가 말했다. "빈 칸을 찾아야 하고, 꼬리표를 관리해야 하고, 여러 스레드가 동시에 요청하면 순서를 정해야 하지. 그리고 칸들이 여기저기 흩어져 있으니 캐시에도 불리하다. 오래 쓰다 보면 작은 빈 칸들이 띄엄띄엄 남는 **단편화(fragmentation)** 도 생기고."

"하지만 힙에는 두 가지 자유가 있다."

- **크기의 자유**: 실행 중에 원하는 만큼 요청할 수 있다. 사용자가 이름을 100글자 입력하든 1만 글자 입력하든.
- **수명의 자유**: 함수가 끝나도 칸은 그대로 남는다. **누군가 명시적으로 반납할 때까지.**

보로의 목소리가 낮아졌다.

"그리고 바로 그 마지막 문장이 이 사건의 핵심이다. **누군가 반납해야 한다.** 반납을 잊으면 창고가 차오르고(메모리 누수), 반납한 칸을 또 쓰면 남의 짐을 건드리고(use-after-free), **같은 칸을 두 번 반납하면 창고지기의 장부가 뒤엉킨다(double free).**"

### 1.4 증거물 #1 — 책상과 창고의 주소를 직접 보기

"말로만 들으면 감이 안 오지. 직접 확인해 봐." 보로가 하랑에게 노트북을 내밀었다.

**C++ 버전**

```cpp
// evidence1.cpp — g++ -std=c++17 evidence1.cpp && ./a.out
#include <cstdio>
#include <memory>

int global_counter = 0;                 // 데이터 영역

void inner() {
    int deeper = 2;                      // 더 깊은 스택 프레임
    std::printf("  inner 지역 변수 : %p\n", (void*)&deeper);
}

int main() {
    int on_desk = 42;                    // 스택
    auto in_warehouse = std::make_unique<int>(42);   // 힙
    const char* literal = "루비 하트";      // 읽기 전용 데이터

    std::printf("스택   (지역 변수) : %p\n", (void*)&on_desk);
    inner();
    std::printf("힙     (make_unique): %p\n", (void*)in_warehouse.get());
    std::printf("데이터 (전역 변수) : %p\n", (void*)&global_counter);
    std::printf("rodata (리터럴)   : %p\n", (void*)literal);
    std::printf("코드   (inner 함수): %p\n", (void*)&inner);
}
```

**Rust 버전**

```rust
// evidence1.rs — rustc evidence1.rs && ./evidence1
static GLOBAL_COUNTER: i32 = 0;          // 데이터 영역

fn inner() {
    let deeper = 2;                      // 더 깊은 스택 프레임
    println!("  inner 지역 변수 : {:p}", &deeper);
}

fn main() {
    let on_desk = 42;                    // 스택
    let in_warehouse = Box::new(42);     // 힙
    let literal: &'static str = "루비 하트"; // 읽기 전용 데이터

    println!("스택   (지역 변수) : {:p}", &on_desk);
    inner();
    println!("힙     (Box)      : {:p}", in_warehouse);   // Box가 가리키는 힙 주소
    println!("데이터 (static)   : {:p}", &GLOBAL_COUNTER);
    println!("rodata (리터럴)   : {:p}", literal.as_ptr());
    println!("코드   (main 함수) : {:p}", main as fn());
}
```

하랑이 두 프로그램을 실행했다. 출력은 대략 이랬다.

```text
스택   (지역 변수) : 0x7ffd5c3a1e2c
  inner 지역 변수 : 0x7ffd5c3a1dfc      ← 스택보다 '아래'(더 낮은 주소)
힙     (Box)      : 0x5d1f2a4f9b10
데이터 (static)   : 0x5d1f29e6a0c4
rodata (리터럴)   : 0x5d1f29e2d014
코드   (main 함수) : 0x5d1f29e14a30
```

"스택 주소는 `0x7ff...`로 아주 높고, 함수를 한 단계 더 들어가면 주소가 **낮아지네요!**" 하랑이 외쳤다. "페리 지도처럼 스택이 아래로 자라는 거예요. 그리고 힙이랑 전역 변수, 코드는 훨씬 낮은 주소에 모여 있어요."

"그렇다. 그리고 두 언어 모두 **똑같은 동네**에 산다는 것도 봐 둬라." 보로가 말했다. "Rust와 C++은 같은 하드웨어 위에서, 같은 스택과 같은 힙을 쓴다. 다른 건 단 하나. **창고 반납을 누가, 어떻게 책임지느냐**다."

> **단서 노트 — 제1장**
>
> | | 스택 (책상) | 힙 (창고) |
> |---|---|---|
> | 할당/해제 | 스택 포인터 이동, 사실상 공짜 | 할당자가 빈 칸 탐색, 상대적으로 비쌈 |
> | 크기 | 컴파일 시점에 고정되어야 함 | 실행 중 자유롭게 |
> | 전체 용량 | 작음 (보통 수 MiB) | 큼 (가상 메모리 한도까지) |
> | 수명 | 함수가 끝나면 자동 소멸 | **명시적으로 반납할 때까지** |
> | 캐시 효율 | 매우 좋음 | 흩어져 있으면 나쁨 |
> | 대표적 사고 | 스택 오버플로, 지역 변수 주소 반환 | 누수, use-after-free, **double free** |

# 제2장 — 문자열의 해부

"이제 피해자를 살펴보자." 보로가 말했다. "루비 하트. 정확히는, 루비 하트라는 **문자열**이다."

관장이 전시 관리 프로그램의 핵심 구조체를 보여 주었다. 그런데 그 전에, 보로는 두 섬의 '표준 문자열'부터 해부해 보자고 했다.

---

### 2.1 Rust의 `String` — 세 칸짜리 영수증

"Rust의 `String`은 사실 `Vec<u8>`을 감싼 것이다. 그리고 `Vec`은 스택에 딱 세 칸을 차지하지."

```text
   스택: let director = String::from("루비 하트");

  ┌─────────────────────┐            힙 (할당자가 준 칸)
  │ ptr      ───────────┼────────▶ ┌────┬────┬────┬────┬────┬────┬────┐
  │ len      = 13       │          │ EB │ A3 │ A8 │ EB │ B9 │ 84 │ 20 │ ...
  │ capacity = 13       │          └────┴────┴────┴────┴────┴────┴────┘
  └─────────────────────┘           '루'(3바이트)  '비'(3바이트)  ' '
       24바이트 (64비트)              총 13바이트: 한글 4자 × 3 + 공백 1
```

"`ptr`은 창고 칸의 주소, `len`은 지금 쓰고 있는 바이트 수, `capacity`는 창고 칸의 전체 크기다. 이 세 개가 스택에 있는 **영수증**이고, 진짜 글자들은 힙의 창고에 있다. 그래서 영수증만 보면 `String`은 언제나 24바이트야. 글자가 1개든 100만 개든."

> 세 필드가 메모리에 어떤 **순서**로 놓이는지는 Rust가 보장하지 않는다. 컴파일러가 최적화를 위해 바꿀 수 있다. 하지만 '포인터 하나 + 정수 둘 = 24바이트'라는 사실은 64비트 플랫폼에서 변하지 않는다.

### 2.2 C++의 `std::string` — 작은 건 주머니에

"C++의 `std::string`은 좀 다르다." 보로가 말했다. "C++ 섬 사람들은 영리한 최적화를 하나 해 두었지. **SSO(Small String Optimization)**, 작은 문자열 최적화다."

```text
 libstdc++ (g++) 의 std::string, 64비트 — 32바이트

 짧은 문자열 (15바이트 이하)                  긴 문자열 (16바이트 이상)
 ┌──────────────────────────┐              ┌──────────────────────────┐
 │ ptr  ───┐ (자기 자신을 가리킴)│              │ ptr  ──────────────────┼──▶ 힙
 │ size = 13│                 │              │ size = 40                │
 │ ┌────────▼───────────────┐│              │ capacity = 40            │
 │ │ '루비 하트' + '\0'         ││  ← 내부 버퍼 │ (사용 안 하는 8바이트)       │
 │ │ (최대 15바이트 + 널 문자)  ││              │                          │
 │ └────────────────────────┘│              └──────────────────────────┘
 └──────────────────────────┘
   힙 할당 없음!                               힙 할당 발생
```

"짧은 문자열은 아예 창고에 맡기지 않고 **영수증 안의 주머니**에 넣어 버린다. 힙 할당이 없으니 빠르지. libstdc++(g++)는 15바이트까지, libc++(clang/macOS)는 22바이트까지 주머니에 넣는다."

### 2.3 증거물 #2 — 두 문자열의 영수증 크기 재기

**C++ 버전**

```cpp
// evidence2.cpp — g++ -std=c++17 evidence2.cpp && ./a.out
#include <iostream>
#include <string>

bool on_heap(const std::string& s) {
    // 데이터 주소가 string 객체 '내부'면 SSO(스택), 바깥이면 힙
    auto obj_begin = reinterpret_cast<const char*>(&s);
    auto obj_end = obj_begin + sizeof(s);
    return !(s.data() >= obj_begin && s.data() < obj_end);
}

int main() {
    std::string small = "루비 하트";                              // 13바이트
    std::string large = "루비 하트는 C++ 섬 왕립 박물관의 보물이다";  // 16바이트 초과

    std::cout << "sizeof(std::string) = " << sizeof(std::string) << "\n";
    std::cout << "small: " << small.size() << "바이트, capacity "
              << small.capacity() << ", 힙? " << std::boolalpha << on_heap(small) << "\n";
    std::cout << "large: " << large.size() << "바이트, capacity "
              << large.capacity() << ", 힙? " << on_heap(large) << "\n";
}
```

```text
sizeof(std::string) = 32
small: 13바이트, capacity 15, 힙? false
large: 57바이트, capacity 57, 힙? true
```

**Rust 버전**

```rust
// evidence2.rs
use std::mem::size_of;

fn main() {
    let small = String::from("루비 하트");
    let large = String::from("루비 하트는 C++ 섬 왕립 박물관의 보물이다");

    println!("size_of::<String>() = {}", size_of::<String>());
    for (name, s) in [("small", &small), ("large", &large)] {
        println!(
            "{name}: len {}, capacity {}, 영수증 주소 {:p}, 창고 주소 {:p}",
            s.len(), s.capacity(), s, s.as_ptr()
        );
    }
    // Rust의 String은 SSO가 없다. 비어 있지 않으면 언제나 힙에 있다.
    // (빈 String::new()는 아예 할당하지 않는다.)
    println!("빈 String의 capacity: {}", String::new().capacity());
}
```

```text
size_of::<String>() = 24
small: len 13, capacity 13, 영수증 주소 0x7ffc8a5e0f28, 창고 주소 0x5a8e1c6f2b10
large: len 57, capacity 57, 영수증 주소 0x7ffc8a5e0f40, 창고 주소 0x5a8e1c6f2b30
빈 String의 capacity: 0
```

"흥미롭네요." 하랑이 두 출력을 비교했다. "C++에서는 '루비 하트'가 주머니에 들어가서 힙을 안 쓰는데, Rust는 짧아도 창고에 맡기네요."

"Rust의 표준 `String`은 단순함과 예측 가능성을 택했어. 언제나 '영수증 + 창고'지. SSO가 필요하면 `smol_str`이나 `compact_str` 같은 크레이트를 쓰면 된다. 어느 쪽이 무조건 낫다기보다는 **설계 철학의 차이**다."

보로가 안경을 고쳐 썼다.

"그런데 관장님의 프로그램은 `std::string`을 쓰지 않았다. 직접 만든 보석 클래스를 썼지. 그리고 바로 거기서 범죄가 일어났다."

> **단서 노트 — 제2장**
>
> - Rust `String` = `{ ptr, capacity, len }` 24바이트(64비트). 데이터는 **항상 힙**(빈 문자열은 할당 없음).
> - C++ `std::string` = 구현마다 다름. libstdc++ 32바이트(SSO 15바이트), libc++ 24바이트(SSO 22바이트).
> - 둘 다 "스택의 작은 관리 구조 + 힙의 실제 데이터"라는 **이중 구조**를 가진다. 이 이중 구조가 복사·이동·해제 문제의 근원이다.
> - UTF-8에서 한글 한 글자는 3바이트다. `"루비 하트"`는 13바이트다.

# 제3장 — 범행 재구성

관장의 전시 관리 시스템에서 루비 하트를 표현하는 클래스는 이랬다. 20년 전, C++ 표준 라이브러리가 지금처럼 풍부하지 않던 시절에 직접 만든 코드였다.

### 3.1 증거물 #3 — 범행에 쓰인 코드

```cpp
// crime_scene.cpp — ❌ 실행하면 이중 해제로 쓰러진다
#include <cstdio>
#include <cstring>

class Gem {
public:
    char*  ptr;       // 힙의 글자를 가리키는 주소
    size_t len;       // 길이
    size_t capacity;  // 창고 칸 크기

    explicit Gem(const char* name) {
        len = std::strlen(name);
        capacity = len + 1;
        ptr = new char[capacity];         // 창고에 칸을 하나 빌린다
        std::memcpy(ptr, name, capacity);
        std::printf("[생성] '%s' 창고 칸 %p\n", ptr, (void*)ptr);
    }

    ~Gem() {                              // 소멸자: 범위를 벗어나면 자동 호출
        std::printf("[반납] 창고 칸 %p\n", (void*)ptr);
        delete[] ptr;                     // 창고 칸을 반납한다
    }
    // 복사 생성자? 복사 대입 연산자? ... 아무것도 정의하지 않았다.
};

int main() {
    Gem director("루비 하트");
    {
        Gem guard = director;   // 경비원에게 '맡긴다' — 컴파일러가 만든 기본 복사 생성자 호출
        std::printf("경비원이 보는 보석: %s\n", guard.ptr);
    }                           // ← guard 소멸: 창고 칸 반납 (1번째)
    std::printf("관장이 보는 보석: %s\n", director.ptr);   // ← 이미 반납된 칸을 읽는다!
}                               // ← director 소멸: 같은 칸을 또 반납 (2번째) 💥
```

"이 코드는 **아무 경고 없이 컴파일된다.**" 보로가 말했다. "그게 C++ 섬의 무서운 점이지."

하랑은 코드를 한 줄씩 따라가다가 `Gem guard = director;`에서 멈췄다.

"관장님은 복사하는 방법을 정의하지 않았어요. 그럼 컴파일러는요?"

"컴파일러가 **기본 복사 생성자**를 대신 만들어 준다. 그리고 그 기본 복사는 각 필드를 그대로 복사하는 **멤버별 복사(memberwise copy)** 야. `ptr`, `len`, `capacity`. 스택의 세 칸만."

### 3.2 사건의 재구성 — 네 장면

페리가 칠판에 장면을 하나씩 그렸다.

**장면 1. 생성** — 관장이 창고에 칸을 빌린다.

```text
  스택                                   힙
  director { ptr ─────────────────────▶ [ 루 비 하 트 \0 ]  (칸 0x...b2c0)
             len = 13, cap = 14 }
```

**장면 2. 얕은 복사** — `Gem guard = director;` 스택의 세 칸만 복사된다.

```text
  director { ptr ──┐
             len = 13, cap = 14 }
                   ├──────────────────▶ [ 루 비 하 트 \0 ]  (칸 0x...b2c0)
  guard    { ptr ──┘
             len = 13, cap = 14 }

  ⚠ 두 영수증이 같은 창고 칸을 가리킨다. 그런데 둘 다 "이 칸은 내 것"이라고 믿는다.
```

**장면 3. 첫 번째 반납** — 안쪽 블록이 끝나며 `guard`의 소멸자가 `delete[]`를 호출한다.

```text
  director { ptr ─────────────────────▶ [ ░░ 반납됨 ░░ ]  (칸 0x...b2c0)
             len = 13, cap = 14 }          ↑ 창고지기 장부: "빈 칸"
  guard    (사라짐)

  ⚠ director는 이제 '철거된 칸'을 가리킨다: 댕글링 포인터.
     여기서 director.ptr을 읽으면 use-after-free (정의되지 않은 행동).
```

**장면 4. 두 번째 반납** — `main`이 끝나며 `director`의 소멸자가 **같은 칸**을 또 `delete[]`한다.

```text
  창고지기: "0x...b2c0 반납이요? 이미 빈 칸 목록에 있는데…"
            → 운이 좋으면: 이상 감지, 프로그램 강제 종료 (오늘 밤처럼)
            → 운이 나쁘면: 장부가 조용히 뒤엉킨다 (제6장)
```

"루비 하트는 **두 번 사라진** 거예요." 하랑이 낮게 말했다. "한 번은 경비원의 근무가 끝났을 때. 그리고 한 번 더, 이미 없는 보석을 관장님이 반납하려 했을 때."

### 3.3 법의학 감정 — 새니타이저 박사의 증언

C++ 섬 수사연구소의 새니타이저 박사가 도착했다. 박사는 같은 코드를 특수 옵션으로 다시 컴파일했다.

"ASan(AddressSanitizer)은 반납된 칸 주변에 **독이 묻은 경계선**을 쳐 두고, 누군가 그걸 건드리는 순간 잡아냅니다." 박사가 말했다. "보세요. 이중 해제보다 **먼저**, 관장님이 이미 반납된 칸을 읽은 순간(use-after-free)이 잡혔습니다. 언제 빌렸는지, 언제 반납했는지, 누가 다시 건드렸는지가 전부 기록돼 있죠."

"훌륭한 도구네요!" 하랑이 감탄했다.

"훌륭하죠. 하지만 한계가 있습니다." 박사가 씁쓸하게 웃었다. "ASan은 **실행된 경로만** 검사합니다. 테스트에서 그 코드를 한 번도 지나가지 않으면, 범인은 그대로 배포됩니다. 그리고 프로그램이 두세 배 느려지니 실제 서비스에서는 거의 끄고 돌리죠."

보로가 조용히 덧붙였다. "C++ 섬의 수사는 **사건이 일어난 뒤에** 시작된다. 크레이트 섬의 수사는 **코드가 실행되기도 전에** 끝나고."

> **단서 노트 — 제3장**
>
> - **얕은 복사(shallow copy)**: 포인터 값만 복사해서 두 객체가 같은 힙 메모리를 가리키게 되는 것.
> - **깊은 복사(deep copy)**: 힙 데이터까지 새로 할당해 복사하는 것.
> - C++은 복사 생성자를 정의하지 않으면 **멤버별 복사**를 자동 생성한다. 원시 포인터를 가진 클래스에서 이것은 곧 얕은 복사다.
> - 결과: **use-after-free**(반납된 칸 읽기) → **double free**(같은 칸 두 번 반납). 둘 다 C++에서 **정의되지 않은 행동(UB)** 이다.
> - **AddressSanitizer**(`-fsanitize=address`)는 실행 중에 이를 잡아내지만, 실행되지 않은 경로는 검사하지 못한다.

# 제4장 — C++ 섬의 방어술

"C++ 섬 사람들이 손 놓고 있었던 건 아닙니다." 스트라우 관장이 항변했다. "우리도 수십 년 동안 방어법을 발전시켜 왔어요."

"알고 있습니다, 관장님." 보로가 정중하게 고개를 숙였다. "C++의 방어술은 훌륭합니다. 오히려 Rust의 많은 아이디어가 C++에서 왔지요. 하랑, 잘 들어 둬라."

### 4.1 3의 법칙 → 5의 법칙

"첫 번째 방어술. **3의 법칙(Rule of Three)**." 관장이 말했다. "소멸자, 복사 생성자, 복사 대입 연산자. 이 셋 중 하나라도 직접 만들었다면, **나머지 둘도 반드시 직접 만들어라.** C++11 이후로는 이동 생성자와 이동 대입 연산자가 더해져 **5의 법칙**이 됐죠."

### 증거물 #4 — 5의 법칙을 지킨 Gem

```cpp
// rule_of_five.cpp — g++ -std=c++17 rule_of_five.cpp && ./a.out
#include <cstdio>
#include <cstring>
#include <utility>

class Gem {
    char*  ptr_ = nullptr;
    size_t len_ = 0;

public:
    explicit Gem(const char* name) : len_(std::strlen(name)) {
        ptr_ = new char[len_ + 1];
        std::memcpy(ptr_, name, len_ + 1);
    }

    // ① 소멸자
    ~Gem() { delete[] ptr_; }   // nullptr에 대한 delete[]는 안전하다

    // ② 복사 생성자: 깊은 복사 — 창고에 새 칸을 빌린다
    Gem(const Gem& other) : len_(other.len_) {
        ptr_ = new char[len_ + 1];
        std::memcpy(ptr_, other.ptr_, len_ + 1);
        std::printf("[깊은 복사] %p → %p\n", (void*)other.ptr_, (void*)ptr_);
    }

    // ③ 복사 대입: copy-and-swap 관용구 (자기 대입·예외에 안전)
    Gem& operator=(Gem other) noexcept {   // 값으로 받으면서 복사/이동이 일어난다
        swap(*this, other);
        return *this;
    }

    // ④ 이동 생성자: 영수증만 가져오고, 원래 주인의 포인터를 비운다
    Gem(Gem&& other) noexcept
        : ptr_(std::exchange(other.ptr_, nullptr)),
          len_(std::exchange(other.len_, 0)) {
        std::printf("[이동] 창고 칸 %p 의 소유권 이전\n", (void*)ptr_);
    }

    // ⑤ 이동 대입: ③이 값으로 받으므로 이동 대입도 함께 처리된다

    friend void swap(Gem& a, Gem& b) noexcept {
        std::swap(a.ptr_, b.ptr_);
        std::swap(a.len_, b.len_);
    }

    const char* name() const { return ptr_ ? ptr_ : "(빈 영수증)"; }
};

int main() {
    Gem director("루비 하트");

    Gem replica = director;              // 깊은 복사: 칸이 두 개
    std::printf("관장: %s / 복제품: %s\n", director.name(), replica.name());

    Gem guard = std::move(director);     // 이동: 칸은 하나, 주인만 바뀜
    std::printf("경비원: %s\n", guard.name());
    std::printf("관장: %s\n", director.name());   // ⚠ 컴파일된다! 이동된 객체에 접근
}   // 세 소멸자가 모두 실행되지만, 반납은 정확히 두 번(director는 nullptr)
```

관장: 루비 하트 / 복제품: 루비 하트
[이동] 창고 칸 0x5631e7a822b0 의 소유권 이전

"이렇게 하면 이중 해제는 사라집니다." 관장이 자신 있게 말했다.

"맞습니다. 하지만 관장님, 이 클래스 하나를 안전하게 만드는 데 몇 줄이 필요했는지 보세요." 보로가 말했다. "그리고 이 다섯 개 중 **하나만 깜빡해도** 컴파일러는 아무 말 하지 않습니다. 오늘 밤의 사건처럼요."

### 4.2 0의 법칙 — 가장 좋은 방어는 직접 하지 않는 것

"그래서 현대 C++은 한 걸음 더 나아갔습니다." 관장이 인정했다. "**0의 법칙(Rule of Zero)**. 자원 관리는 표준 라이브러리의 전문가 클래스에 맡기고, 내 클래스는 다섯 개 중 **아무것도** 직접 만들지 않는 거죠."

### 증거물 #5 — 0의 법칙과 unique_ptr

```cpp
// rule_of_zero.cpp — g++ -std=c++17 rule_of_zero.cpp && ./a.out
#include <iostream>
#include <memory>
#include <string>
#include <utility>

struct Gem {
    std::string name;   // std::string이 깊은 복사·이동·해제를 전부 책임진다
};

struct Vault {
    std::unique_ptr<Gem> gem;   // 단독 소유: 복사 불가, 이동만 가능
};

int main() {
    Gem a{"루비 하트"};
    Gem b = a;                                   // std::string의 깊은 복사 — 안전
    std::cout << a.name << " / " << b.name << "\n";

    Vault director{std::make_unique<Gem>(Gem{"루비 하트"})};
    // Vault guard = director;                   // ❌ 컴파일 에러: unique_ptr은 복사할 수 없다
    Vault guard = std::move(director);           // 이동은 가능

    std::cout << "경비원: " << guard.gem->name << "\n";
    std::cout << "관장의 금고가 비었나? " << std::boolalpha
              << (director.gem == nullptr) << "\n";

    // ⚠ 그러나 아래 줄은 경고 없이 컴파일된다. 실행하면 널 포인터 역참조(UB).
    // std::cout << director.gem->name << "\n";
}
```

"`unique_ptr`의 복사 생성자는 **삭제(`= delete`)** 되어 있습니다. 그래서 `Vault guard = director;`는 컴파일 에러죠. 이중 해제의 길이 막힙니다." 관장이 말했다.

"훌륭합니다." 보로가 고개를 끄덕였다. "하지만 마지막 줄을 보세요."

### 4.3 남은 구멍 — 이동 후 사용(use-after-move)

"C++의 `std::move`는 사실 아무것도 **옮기지 않습니다.**" 보로가 말했다. "그저 '이 값은 옮겨도 된다'는 표시(`static_cast<T&&>`)일 뿐이죠. 그리고 옮겨진 뒤에도 원래 변수는 **여전히 거기 있고, 여전히 이름으로 부를 수 있습니다.**"

```cpp
// use_after_move.cpp — 경고 없이 컴파일된다
#include <iostream>
#include <memory>
#include <string>
#include <utility>

int main() {
    std::string director = "루비 하트는 C++ 섬 왕립 박물관의 보물이다";
    std::string guard = std::move(director);
    // 표준: 이동된 std::string은 "유효하지만 명시되지 않은(valid but unspecified)" 상태
    std::cout << "[" << director << "]\n";   // 대부분 빈 문자열이 나오지만, 보장은 없다

    auto vault = std::make_unique<int>(42);
    auto taken = std::move(vault);
    // std::cout << *vault;                  // 컴파일 OK, 실행하면 널 역참조 → UB
    std::cout << (vault ? "있음" : "비었음") << "\n";
}
```

| C++ 방어술 | 막아 주는 것 | 남는 구멍 |
|---|---|---|
| 3/5의 법칙 | 얕은 복사로 인한 이중 해제 | 하나만 빠뜨려도 컴파일러가 침묵 |
| 0의 법칙 (`std::string`, `vector`) | 대부분의 수동 관리 실수 | 원시 포인터·참조를 꺼내 쓰면 다시 위험 |
| `unique_ptr` | 실수로 인한 복사 | **이동 후 사용**은 컴파일됨 |
| `shared_ptr` | 공유 소유의 수명 관리 | 순환 참조 누수, 원자적 카운트 비용 |
| ASan / Valgrind | 실행된 경로의 메모리 오류 | 실행되지 않은 경로, 성능 비용 |
| 정적 분석기 (clang-tidy 등) | 많은 패턴 | 완전하지 않음, 경고를 끌 수 있음 |

"C++ 섬의 방어술은 **규칙과 도구**입니다." 보로가 정리했다. "규칙을 아는 사람이, 규칙을 지키고, 도구를 돌릴 때 안전해지죠. 하지만 언어 자체가 그것을 **강제하지는** 않습니다."

관장은 한참 동안 말이 없었다. 그러다 조용히 물었다.

"그럼 당신들 섬에서는, 이 사건이 어떻게 됐을 것 같습니까?"

> **단서 노트 — 제4장**
>
> - **5의 법칙**: 소멸자 / 복사 생성자 / 복사 대입 / 이동 생성자 / 이동 대입 중 하나를 정의하면 나머지도 고려하라.
> - **0의 법칙**: 자원 관리는 `std::string`, `std::vector`, `std::unique_ptr`에 맡기고 다섯 개 중 아무것도 정의하지 마라. 현대 C++의 권장 방식.
> - `std::move`는 캐스트일 뿐이다. 이동된 객체는 **여전히 접근 가능**하며, 표준 라이브러리 타입은 "유효하지만 명시되지 않은 상태"가 된다.
> - `unique_ptr`은 복사를 막지만 **이동 후 사용**은 막지 못한다.
> - C++의 안전은 **규칙 + 도구 + 규율**에 달려 있다.

# 제5장 — 크레이트 섬의 판결

보로는 노트북을 열고, 관장의 범행 코드를 **그대로** Rust로 옮겼다.

### 5.1 증거물 #6 — 같은 범행, 다른 섬

```rust
// crime_in_rust.rs — ❌ 컴파일되지 않는다
fn main() {
    let director = String::from("루비 하트");
    {
        let guard = director;                        // 경비원에게 맡긴다
        println!("경비원이 보는 보석: {guard}");
    }                                                // guard drop: 창고 칸 반납 (1번)
    println!("관장이 보는 보석: {director}");          // ❌
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0382]: borrow of moved value: `director`
>  --> crime_in_rust.rs:8:27
>   |
> 3 |     let director = String::from("루비 하트");
>   |         -------- move occurs because `director` has type `String`,
>   |                  which does not implement the `Copy` trait
> 4 |     {
> 5 |         let guard = director;
>   |                     -------- value moved here
> ...
> 8 |     println!("관장이 보는 보석: {director}");
>   |                              ^^^^^^^^^^ value borrowed here after move
>   |
> help: consider cloning the value if the performance cost is acceptable
>   |
> 5 |         let guard = director.clone();
>   |                             ++++++++
> ```

"범행은 **실행되기도 전에** 막혔다." 보로가 말했다.

하랑이 에러 메시지를 짚었다. "'value moved here'. Rust에서도 `let guard = director;`는 스택의 세 칸을 복사하는 거죠? C++의 기본 복사랑 똑같이요."

"그렇다. 기계어 수준에서 하는 일은 **똑같다.** 24바이트를 복사할 뿐이지. 다른 건 단 하나다. 복사가 끝난 순간, 컴파일러가 **`director`라는 이름을 무효로 만든다.** 영수증은 `guard`에게 넘어갔고, `director`는 이제 빈손이야. 빈손으로 보석을 보려 하면 컴파일러가 거부하고, 빈손이 창고를 반납하려 하지도 않는다. 그래서 반납은 **정확히 한 번**만 일어나지."

### 5.2 증거물 #7 — 이동은 정말 '영수증만' 옮길까?

"직접 증명해 봐라." 보로가 말했다.

```rust
// proof_of_move.rs
fn main() {
    let director = String::from("루비 하트");
    let receipt_addr = &director as *const String;   // 스택의 영수증 위치
    let warehouse_addr = director.as_ptr();          // 힙의 창고 칸 위치
    println!("이동 전 — 영수증 {:p}, 창고 칸 {:p}", receipt_addr, warehouse_addr);

    let guard = director;                            // 이동!
    println!("이동 후 — 영수증 {:p}, 창고 칸 {:p}", &guard, guard.as_ptr());

    assert_eq!(warehouse_addr, guard.as_ptr());      // 창고 칸은 그대로다
    println!("창고 칸이 같은가? {}", warehouse_addr == guard.as_ptr());

    let replica = guard.clone();                     // 깊은 복사
    println!("복제 후 — 원본 칸 {:p}, 복제품 칸 {:p}", guard.as_ptr(), replica.as_ptr());
}
```

```text
이동 전 — 영수증 0x7ffe0b1c3f58, 창고 칸 0x5b0c2e8a1b10
이동 후 — 영수증 0x7ffe0b1c3f70, 창고 칸 0x5b0c2e8a1b10
창고 칸이 같은가? true
복제 후 — 원본 칸 0x5b0c2e8a1b10, 복제품 칸 0x5b0c2e8a1b30
```

"영수증의 **위치**는 바뀌었는데, 영수증이 가리키는 **창고 칸**은 그대로예요!" 하랑이 외쳤다. "이동은 13바이트짜리 보석을 옮기는 게 아니라, 24바이트짜리 영수증만 옮기는 거네요. 그리고 `clone()`을 하면 창고에 새 칸이 생기고요."

"그래서 Rust의 이동은 **싸다.** 그리고 깊은 복사는 반드시 `.clone()`이라고 **써야만** 일어나지. 비용이 큰 일은 코드에 눈에 보이게 남는다. C++에서는 `Gem b = a;` 한 줄이 깊은 복사일 수도, 얕은 복사일 수도, 이동일 수도 있어. 클래스 정의를 열어 보기 전에는 모르지."

| 코드 | C++ (`std::string`) | Rust (`String`) |
|---|---|---|
| `b = a` | **깊은 복사** (암묵적, 비용 있음) | **이동** (원본 무효화, 비용 거의 0) |
| 깊은 복사 | `b = a` | `b = a.clone()` (명시적) |
| 이동 | `b = std::move(a)` (원본은 여전히 접근 가능) | `b = a` (원본은 **컴파일러가 접근 금지**) |
| 이동 후 원본 사용 | 컴파일됨, 상태 미지정 | **컴파일 에러 E0382** |

### 5.3 증거물 #8 — 관장의 Gem을 Rust로 직접 만든다면

"관장님처럼 소멸자를 직접 쓰는 타입을 만들면 어떻게 될까요?" 하랑이 물었다. "C++에서는 복사 생성자를 깜빡한 게 문제였잖아요."

```rust
// gem.rs
struct Gem {
    name: Box<str>,   // 힙에 있는 고정 길이 문자열
}

impl Gem {
    fn new(name: &str) -> Self {
        let g = Gem { name: name.into() };
        println!("[생성] '{}' 창고 칸 {:p}", g.name, g.name.as_ptr());
        g
    }
}

impl Drop for Gem {   // C++의 소멸자에 해당
    fn drop(&mut self) {
        println!("[반납] 창고 칸 {:p}", self.name.as_ptr());
        // 실제 메모리 반납은 Box<str>이 이 함수 직후 자동으로 한다
    }
}

fn hand_over(g: Gem) -> Gem {
    println!("경비원이 보는 보석: {}", g.name);
    g   // 소유권을 돌려준다
}

fn main() {
    let director = Gem::new("루비 하트");
    let director = hand_over(director);   // 넘겼다가 돌려받는다
    println!("관장이 보는 보석: {}", director.name);
}   // [반납]은 정확히 한 번
```

```text
[생성] '루비 하트' 창고 칸 0x55d1a3b0eb10
경비원이 보는 보석: 루비 하트
관장이 보는 보석: 루비 하트
[반납] 창고 칸 0x55d1a3b0eb10
```

"복사 생성자를 따로 만들 필요가 없네요."

"Rust에는 '암묵적인 사용자 정의 복사'라는 개념 자체가 없다. 대입은 언제나 **비트 단위 이동**이고, 이동된 원본은 쓸 수 없지. 그러니 '복사 생성자를 깜빡하는' 실수가 존재할 수 없어."

### 5.4 증거물 #9 — `Copy`와 `Drop`은 함께할 수 없다

"그럼 누군가 일부러 Gem을 `Copy`로 만들면요? 정수처럼 대입할 때마다 복사되게요."

보로가 미소를 지었다. "해 봐라."

```rust
// copy_and_drop.rs — ❌ 컴파일되지 않는다
#[derive(Clone, Copy)]
struct Gem {
    name: Box<str>,
}

fn main() {
    let director = Gem { name: "루비 하트".into() };
    let guard = director;
    let _ = (director.name.len(), guard.name.len());
}
```

> **컴파일러의 증언**
>
> ```text
> error[E0204]: the trait `Copy` cannot be implemented for this type
>  --> copy_and_drop.rs:2:17
>   |
> 2 | #[derive(Clone, Copy)]
>   |                 ^^^^
> 3 | struct Gem {
> 4 |     name: Box<str>,
>   |     -------------- this field does not implement `Copy`
> ```

그리고 `Drop`을 직접 구현한 타입에 `Copy`를 붙이면 또 다른 증언이 나온다.

> ```text
> error[E0184]: the trait `Copy` cannot be implemented for this type;
>               the type has a destructor
> ```

"이게 Rust의 핵심 설계다." 보로가 칠판에 크게 적었다.

> **`Copy`(비트 복사가 안전함)와 `Drop`(소멸 시 정리가 필요함)은 한 타입에 공존할 수 없다.**

"소멸자가 있다는 건 '내가 정리해야 할 자원을 소유하고 있다'는 뜻이다. 그런 타입을 비트 단위로 복사하면? 정리 담당자가 둘이 된다. 정확히 오늘 밤의 사건이지. Rust는 이 조합을 **타입 시스템 차원에서 금지**했다. C++의 3의 법칙이 '지켜야 할 관례'라면, Rust에서는 '어길 수 없는 법'이다."

### 5.5 그렇다면 Rust에서는 이중 해제가 절대 불가능한가?

관장이 마지막으로 물었다. "정말 절대로요?"

"**안전한 Rust 코드만으로는** 불가능합니다." 보로가 정확하게 답했다. "`unsafe` 블록 안에서 원시 포인터로 같은 메모리를 두 번 해제하면 Rust에서도 이중 해제는 일어납니다. 하지만 그런 코드는 반드시 `unsafe`라는 표지판 아래에만 존재할 수 있고, 그래서 감사해야 할 곳이 처음부터 표시되어 있지요. C++에서는 모든 줄이 잠재적인 `unsafe`입니다. Rust에서는 `unsafe`라고 쓴 줄만 그렇습니다."

> **단서 노트 — 제5장**
>
> - Rust의 대입·함수 전달은 기본적으로 **이동**이다. 기계어로는 스택 칸의 비트 복사지만, **원본 이름이 컴파일 시점에 무효화**된다.
> - 이동 후 원본을 쓰면 **E0382**. 이동 후 사용(use-after-move)이 원천 차단된다.
> - 깊은 복사는 오직 **`.clone()`** 으로만, 명시적으로.
> - 사용자 정의 복사 생성자가 없다. 따라서 "복사 생성자를 깜빡하는" 실수가 존재하지 않는다.
> - **`Copy`와 `Drop`은 배타적**이다(E0184). 힙 자원을 가진 필드가 있으면 `Copy` 불가(E0204).
> - 이중 해제는 **`unsafe` 안에서만** 가능하다. 감사 범위가 언어 차원에서 좁혀진다.

# 제6장 — 열쇠를 얻은 해커

사건은 해결되었다. 그러나 보로는 바로 섬을 떠나지 않았다.

"관장님, 오늘 밤 프로그램이 스스로 쓰러진 건 **행운**이었습니다." 보로가 말했다. "그 이유를 하랑에게도 알려 줘야겠군요."

### 6.1 창고지기의 장부

"제1장에서 창고지기에게 '빈 칸 목록(free list)'이 있다고 했지. 많은 할당자는 이 목록을 **반납된 칸 자체 안에** 적어 둔다. 빈 칸은 어차피 아무도 안 쓰니까, 그 안에 '다음 빈 칸의 주소'를 적어 연결 리스트를 만드는 거야."

```text
 정상 상태: 빈 칸 목록
   head ──▶ [칸 A | next ─]──▶ [칸 B | next ─]──▶ null

 칸 X 를 반납하면:
   head ──▶ [칸 X | next ─]──▶ [칸 A | ...]──▶ [칸 B | ...]──▶ null
```

### 6.2 같은 칸을 두 번 반납하면

```text
 1번째 free(X):  head ──▶ X ──▶ A ──▶ B
 2번째 free(X):  head ──▶ X ──▶ X ──▶ X ──▶ ...   (X가 자기 자신을 가리키는 고리!)

 이후 malloc 두 번:
   p1 = malloc()  → X 를 받는다
   p2 = malloc()  → 또 X 를 받는다   ⚠ 서로 다른 두 객체가 같은 칸을 쓴다
```

"서로 다른 두 객체가 **같은 메모리**를 쓰게 된다. 한쪽에 사용자 이름을 쓰면, 다른 쪽의 데이터가 덮어써지지. 그리고 공격자가 그 이름을 조작할 수 있다면? 빈 칸 목록의 `next` 주소를 자기가 원하는 곳으로 바꿀 수 있어. 그럼 다음 할당에서 창고지기는 **공격자가 지정한 주소**를 '빈 칸'이라고 내줄 거고, 프로그램은 거기에 데이터를 쓰게 되지."

하랑의 얼굴이 하얗게 질렸다. "그럼… 프로그램이 해커가 원하는 곳에 아무거나 쓰게 되는 거예요?"

"그게 '**임의 쓰기(arbitrary write)**'라 불리는 능력이다. 공격자는 이걸 발판으로 프로그램의 흐름을 빼앗을 수 있지. 그래서 이중 해제는 단순한 프로그램 종료가 아니라 **보안 취약점**으로 분류된다."

"그래서 요즘 할당자들은 방어 장치를 넣는다." 관장이 덧붙였다. "glibc는 오늘 밤처럼 같은 칸이 빈 칸 목록 맨 앞에 이미 있는지 검사하고, 포인터를 암호화하듯 섞어 저장하기도 하죠(safe-linking). 하지만 그건 **흔한 패턴을 잡는 그물**일 뿐, 모든 경우를 막지는 못합니다. 공격자들은 그물을 피하는 법을 연구하니까요."

### 6.3 숫자로 보는 사건의 무게

보로가 마지막 자료를 꺼냈다.

> - Microsoft는 2019년, 자사 제품에서 해마다 보안 업데이트로 고친 취약점의 **약 70%** 가 메모리 안전성 문제라고 발표했다.
> - Google Chromium 팀도 2020년, 심각도 높은 보안 버그의 **약 70%** 가 메모리 안전성 문제라고 밝혔다.
> - 이후 미국 사이버보안 기관(CISA)과 백악관 국가사이버국장실 등은 **메모리 안전 언어**로의 전환을 권고하는 문서를 잇달아 냈다.

"use-after-free, double free, 버퍼 넘침… 이름은 달라도 뿌리는 같다." 보로가 말했다. "**힙 메모리의 주인이 누구인지, 언제까지 유효한지를 언어가 모른다**는 것."

> **단서 노트 — 제6장**
>
> - 할당자는 반납된 칸 안에 빈 칸 목록의 포인터를 저장하는 경우가 많다.
> - 이중 해제는 이 목록을 오염시켜, **서로 다른 객체가 같은 메모리를 받거나** 공격자가 지정한 주소가 할당되게 만들 수 있다.
> - 할당자의 검사(glibc tcache 검사, safe-linking 등)는 피해를 줄이지만 근본 해결책은 아니다.
> - 근본 해결책은 **소유권을 언어가 추적하는 것**: Rust는 컴파일 시점에, C++은 규칙·RAII·도구로.

# 에필로그 — 두 섬의 다리

개장 행사는 하루 늦게 무사히 열렸다. 박물관의 전시 관리 시스템은 `Gem` 클래스를 0의 법칙에 따라 `std::string` 하나로 다시 쓰는 것으로 고쳐졌다. 그리고 관장은 새로 만들 결제 모듈만큼은 Rust로 작성해 C++ 시스템과 연결해 보기로 했다.

돌아가는 배 위에서, 하랑은 수첩에 오늘의 사건을 정리했다.

```text
사건명   : 루비 하트 이중 해제 사건
피해     : 같은 힙 칸이 두 번 반납됨
직접 원인 : 원시 포인터를 가진 클래스의 기본(얕은) 복사
근본 원인 : "이 힙 칸의 주인은 누구인가?"를 언어가 추적하지 않음

C++ 섬의 방어 : 3/5/0의 법칙, RAII, unique_ptr, ASan, 정적 분석 — 규칙과 도구
Rust 섬의 방어 : 이동 시 원본 무효화, Copy/Drop 배타성, 명시적 clone — 컴파일러의 법
```

"보로 씨." 하랑이 물었다. "C++이 나쁜 언어인 건 아니죠?"

보로는 멀어지는 C++ 섬을 바라보았다. 섬의 불빛 아래에서는 지금도 운영체제, 게임 엔진, 브라우저, 그리고 수많은 산업 시스템이 돌아가고 있었다.

"전혀. RAII도, 이동 의미론도, 스마트 포인터도 C++ 섬에서 태어났다. Rust는 그 지혜를 물려받아서, 사람이 지켜야 했던 규칙을 **컴파일러가 지키게** 만들었을 뿐이야." 그가 말했다. "C++은 **'믿을 테니 책임져라'** 고 말하는 언어고, Rust는 **'증명하면 믿어 주겠다'** 고 말하는 언어다. 어느 쪽이든, 스택과 힙이 어떻게 생겼는지 아는 사람만이 그 말의 무게를 이해할 수 있지."

페리가 칠판에 마지막 한 줄을 적었다.

`사라진 것: 0 / 반납: 정확히 1회`

**— 끝 —**

# 부록 — 수사 보고서

### A. 스택과 힙

| 항목 | 스택 | 힙 |
|---|---|---|
| 관리 주체 | 컴파일러가 생성한 코드 (스택 포인터) | 할당자 (`malloc`, `operator new`, Rust의 `GlobalAlloc`) |
| 할당 비용 | 명령어 1~2개 | 빈 칸 탐색, 메타데이터 관리, 동기화 |
| 크기 결정 | 컴파일 시점 | 실행 시점 |
| 수명 | 스코프(함수/블록)에 묶임 | 해제할 때까지 |
| 스레드 | 스레드마다 별도 | 프로세스 전체가 공유 |
| 전형적 크기 | 수 MiB (Linux 메인 8MiB, Windows 1MiB, Rust 스레드 2MiB) | 수 GiB 이상 |
| 대표 버그 | 스택 오버플로, 지역 변수 주소 반환 | 누수, use-after-free, double free, 단편화 |
| C++에서 | 지역 변수, 값 타입 객체 | `new`, `make_unique`, `vector`·`string`의 내부 버퍼 |
| Rust에서 | 지역 변수, 값 타입 | `Box`, `Vec`, `String`, `Rc`, `Arc`의 내부 |

### B. "관리 구조는 스택, 데이터는 힙" 타입들

| C++ | Rust | 스택에 있는 것 (64비트) |
|---|---|---|
| `std::string` | `String` | C++: 32B(libstdc++, SSO) / Rust: 24B (ptr, cap, len) |
| `std::vector<T>` | `Vec<T>` | 24B (포인터/길이/용량) |
| `std::unique_ptr<T>` | `Box<T>` | 8B (포인터 하나) |
| `std::shared_ptr<T>` | `Arc<T>` | C++: 16B (객체 포인터 + 제어 블록 포인터) / Rust: 8B |
| `std::string_view` | `&str` | 16B (포인터 + 길이), 소유하지 않음 |

### C. 복사·이동·해제 비교

| 질문 | C++ | Rust |
|---|---|---|
| 대입의 기본 의미 | 복사 (타입마다 정의) | 이동 (`Copy` 타입만 복사) |
| 사용자 정의 복사 | 복사 생성자 (암묵적 호출) | `Clone::clone` (명시적 호출) |
| 이동 후 원본 | 접근 가능, 상태는 타입이 정함 | 컴파일러가 접근 금지 |
| 소멸 시점 | 스코프 끝 (RAII) | 스코프 끝 (RAII, `Drop`) |
| 이동된 객체의 소멸자 | **호출됨** (그래서 비워 둬야 함) | **호출되지 않음** (소유권이 없으므로) |
| 이중 해제 방지 | 규칙(3/5/0), 스마트 포인터, 도구 | 타입 시스템 (안전한 코드에서는 불가능) |
| 이중 해제 가능 지점 | 어디서나 | `unsafe` 블록 안 |

### D. 사건에서 등장한 도구

| 도구 | 언어 | 용도 |
|---|---|---|
| AddressSanitizer (`-fsanitize=address`) | C/C++ (Rust nightly도 지원) | 실행 중 메모리 오류 탐지 |
| Valgrind (memcheck) | 모든 네이티브 바이너리 | 재컴파일 없이 메모리 오류 탐지 (느림) |
| clang-tidy, 컴파일러 경고 | C++ | 정적 분석 (`-Wall -Wextra`) |
| rustc 빌림 검사기 | Rust | 컴파일 시점 소유권·수명 검증 |
| Miri (`cargo +nightly miri test`) | Rust | `unsafe` 코드의 UB 탐지 |
